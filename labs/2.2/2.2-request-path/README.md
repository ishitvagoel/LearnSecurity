# Lab: 2.2-request-path

**Module:** `2.2`
**Authorized scope:** this directory only. Local FastAPI fixture; no live CDN, no DNS resolution, no real TLS handshake, no third-party target.
**Tier:** 2 (component). A real FastAPI request/response cycle through `fastapi.testclient.TestClient`, with server-side state (`_ORIGIN_STORE`, `_CACHE`) that persists across calls within one test and resets between tests. The TLS-hop check (`hop_is_trustworthy`, C3) is a pure predicate colocated in the same app and exercised through `POST /internal/relay` rather than a bare function call, because this fixture never performs an actual TLS handshake — see `lab-realism.mdc`; a real handshake is out of this module's local-fixture scope, so the check it would gate is tested as a request instead.

**Invariant (C1):** A shared cache entry may be returned only when the key includes the company the caller is bound to, not the path alone.
**Invariant (C2):** The company used for an authorization decision must come only from the caller's own credential, never from a client-supplied `X-Company` (or other forwarded-identity) header.
**Invariant (C3):** A hop-authentication check must require a trusted CA, an exact hostname match, and an accepted TLS version together; a missing or unrecognized input fails closed.
**Root cause class:** trust (C2: identity read from a client-controlled channel) and shared mechanism (C1: a cache with no company dimension in its key; C3: a check that stops at "some cert validated").
**Non-goals:** live CDNs, DNS hijacking, a real TLS handshake, poisoning a public cache.

## Reset

No persistent state between tests. `conftest.py` loads a fresh module and calls `reset()` before every test. Optional: `git checkout -- labs/2.2/2.2-request-path`.

## Vulnerable behavior (local only)

`_resolve_company` returns a client-supplied `X-Company` header when present, instead of only the company `API_KEYS[api_key]` names. `_CACHE` is a `dict[str, str]` keyed on `note_id` alone. `hop_is_trustworthy` returns `cert_trusted_ca is True` and nothing else — it never looks at `presented_hostname` or `tls_version`.

## Structural fix

`_resolve_company` never reads `x_company`. `_CACHE` becomes `dict[tuple[str, str], str]` keyed on `(note_id, company)`. `hop_is_trustworthy` requires `cert_trusted_ca is True` **and** `presented_hostname == expected_hostname` **and** `tls_version` in `{"1.2", "1.3"}`.

Thirty-seven tests across two files: `test_cache_key.py` (C1, C2 — normal case, both forbidden outcomes, a malformed-credential case, a boundary case, and one anti-fake test per claim using company and note-id values never written elsewhere in the file) and `test_tls_hop.py` (C3 — normal case, the hostname-mismatch forbidden outcome, a TLS-version boundary at 1.2, an unknown-trust-state failure case, an explicitly-untrusted-CA failure case distinct from the unknown-state case, four hostname anti-fake tests (a prefix fake, a substring-anywhere fake, a suffix-without-boundary fake, and a Unicode-confusable fake), four version-string anti-fake tests each isolating one specific, historically real fake (a sorts-lexicographically-high fake, a hand-written forward-compatible allow-list fake, a parses-to-a-float-in-range fake, and an incidental-whitespace fake), and one seventeen-case parametrized sweep test asserting rejection across a broad, systematically-chosen set of version-string near-misses, one of them a non-ASCII digit sequence — the seventeen sweep cases, together with the new dedicated hostname Unicode-confusable test, are what take the file's raw test count from nineteen to thirty-seven).

Verified against twelve constructed fakes, each isolating exactly one gap, every count checked by reconstructing the exact fake and running the real suite rather than incrementing an old number: keying the cache correctly while leaving the `X-Company` override in place, matching `vulnerable/app.py`'s own check order (API key validity decided first, then the header) — passes 35 of 37 and fails exactly the C2 forbidden-outcome test and its anti-fake pair; the malformed-credential case (an unregistered key with a company header) still passes, because the key check runs and fails before the header is ever consulted. Removing the header override while leaving the cache keyed on path alone passes 35 of 37 and fails exactly the C1 forbidden-outcome test and its anti-fake pair. `presented_hostname.startswith(expected_hostname)` in place of equality passes 36 of 37 and fails only its own anti-fake test. `expected_hostname in presented_hostname` passes 34 of 37 and fails all three ASCII hostname anti-fake tests, not only the two it was originally built against — "origin.internal" is a substring of "evil-origin.internal" exactly as it is a substring of a prefix or middle-placed attacker string, so a check that only asks "does the expected name appear anywhere" cannot tell any of the three shapes apart. `presented_hostname.endswith(expected_hostname)` in place of equality — the same mistake from the third boundary position, catching a name glued onto the end with no separator — passes 36 of 37 and fails only its own anti-fake test. `if cert_trusted_ca is None: return False` in place of `if cert_trusted_ca is not True: return False` — a plausible reading of "fails closed on an unrecognized trust state" that only checks for the *unknown* case and lets an explicitly-resolved-untrusted certificate (`False`) fall through to the hostname/version checks — passes 36 of 37 and fails only `test_explicitly_untrusted_ca_is_rejected_even_with_matching_hostname_and_version`. A hand-written `{"1.2", "1.3", "1.4"}` in place of `_ACCEPTED_TLS_VERSIONS` itself — a plausible "let's allow the next version too" guess that adds a version this fixture has never actually accepted — passes 36 of 37 and fails only `test_anti_fake_forward_compatible_allow_list_still_rejects_an_unaccepted_version`, since none of the near-miss sweep's seventeen strings is `"1.4"` either. The remaining three previously-closed version fakes each fail every dedicated version anti-fake test built against them AND some or all of the seventeen near-miss sweep cases, since the sweep independently rediscovers each of them from a different angle — including, for two of the three, the sweep's newest, non-ASCII case, which none of these fakes was ever tested against before: `tls_version < "1.2"` as a lexicographic lower bound fails all four dedicated version anti-fake tests plus twelve of the seventeen sweep cases, the fullwidth-digit case among them, since a fullwidth `"１.２"` sorts by Unicode code point above ASCII `"1.2"` exactly as `"1.9"` and `"1.4"` already did (16 failures; 21 of 37 still pass). Parsing `tls_version` as a float and checking `1.2 <= version_num <= 1.3` fails both dedicated tests it was ever isolated with plus twelve sweep cases, the fullwidth case among them, since Python's `float()` accepts fullwidth Unicode digits and parses `"１.２"` to `1.2` (14 failures; 23 of 37 still pass) — `float()` silently accepts leading/trailing whitespace, a leading `+` sign, exponential notation, a leading zero, AND fullwidth digits, so nearly every near-miss in the sweep, ASCII or not, parses to a value inside `[1.2, 1.3]`. And the whitespace-stripping fake fails its one dedicated test plus four sweep cases that place whitespace in a position the dedicated test's single case never covered — `"\t1.2"`, `"1.3\t"`, and `"1.2\r\n"` among them, but NOT the fullwidth case, since `.strip()` only removes whitespace and a fullwidth digit is not whitespace (6 failures; 31 of 37 still pass).

**The eleventh fake, found in a sixth independent review round, was the first one this module's sweep test caught on its own before a dedicated test for it ever existed — and it turns out to fail a third sweep case beyond the two the sixth review named, discovered only by re-deriving its count against the current suite rather than trusting the prior count.** A sixth review round constructed an `.isdigit()`-guarded `(major, minor)` integer-tuple parse — deliberately hardened past the whitespace-stripping fake, so that `"1.2\n".isdigit()` correctly returns `False` and that specific fake is rejected — but `int("01")` and `int("02")` both discard a leading zero, so `"01.2"` and `"1.02"` both parse to `(1, 2)` and are wrongly accepted; `"1.02"` was added as a sixteenth sweep case at the time to cover both of that review's named examples. Re-deriving this fake's count against the current suite (with the seventeenth, fullwidth case now added for an unrelated, later finding) shows it ALSO wrongly accepts `"１.２"`, since `"１".isdigit()` and `"２".isdigit()` are both `True` — Python's `str.isdigit()` accepts fullwidth Unicode digits, not only ASCII ones — and `int("１")`, `int("２")` parse to `1`, `2` exactly as their ASCII counterparts do. The fake now fails exactly these three sweep cases and none of the (now nine) dedicated anti-fake tests (three failures; 34 of 37 still pass) — the same "recompute, don't increment" discipline this module has needed at every single round so far.

**The twelfth fake, found in a seventh independent review round, is a different technique from all eleven before it — normalizing the string under Unicode canonical-compatibility rules before comparing, rather than parsing or partially matching it — and it is the first fake found to affect BOTH the version check and the hostname check with the same one-line change to each.** `unicodedata.normalize("NFKC", tls_version)` before membership, and `unicodedata.normalize("NFKC", presented_hostname) == unicodedata.normalize("NFKC", expected_hostname)` in place of the bare `==`, is a defensive habit standard Unicode security guidance actively recommends for untrusted strings in general — at least as plausible a good-faith choice as the already-closed whitespace-strip fake, and arguably better-motivated. Isolated to the version check alone, this fake fails only the sweep's fullwidth case (one failure; 36 of 37 pass), since NFKC normalization is a no-op on every ASCII string any test sends and `unicodedata.normalize("NFKC", "１.２") == "1.2"` is exactly what it exploits. Isolated to the hostname check alone, it fails only the new dedicated Unicode-confusable hostname test (one failure; 36 of 37 pass), since none of the three ASCII hostname anti-fake tests (prefix, substring-anywhere, suffix-without-boundary) uses a non-ASCII character. Combined — the fake as a reviewer would plausibly write it, applying the same defensive habit to both string comparisons in the same function — it fails exactly these two tests and no others (two failures; 35 of 37 still pass).

None of the twelve fakes above was constructed in response to the sweep test itself; the sweep was added proactively after four structurally distinct fakes had been found across four independent review rounds. The eleventh fake was found in a sixth round after the sweep already existed and was caught by it on first contact; the twelfth was found in a seventh round and closed by extending the sweep with one more case plus one new dedicated hostname test, the same "extend rather than isolate anew" pattern the eleventh fake established. `test_anti_fake_version_near_miss_sweep_is_rejected` (seventeen cases) asserts rejection across a systematically-chosen set of near-misses — whitespace in positions the dedicated tests do not cover, leading and trailing zeros in either version position, an extra version segment, a sign prefix, exponential notation, an accepted-looking substring embedded in a longer string, and a non-ASCII digit sequence — in one pass. Constructing two further fakes never found by any review round confirms the sweep's value is not limited to shapes a human reviewer has actually found: a regex check, `re.search(r"1\.[23]", tls_version)` in place of exact membership, would have passed all nineteen tests that existed before the sweep but fails all fifteen ASCII-only sweep cases — not the leading-zero or fullwidth ones, since neither contains the literal substring `"1.2"` or `"1.3"` — plus two of the dedicated version anti-fake tests (seventeen failures total; 20 of 37 pass), because an unanchored search matches "1.23", "1.234", and even "TLSv1.2" and "1.2 or 1.3" as containing the pattern; and parsing `tls_version` into an `(major, minor)` integer tuple with no digit-only guard at all — a step short of the eleventh fake above, and correspondingly easier to catch, since `int()` alone (with no `.isdigit()` pre-check) already accepts fullwidth digits — fails ten sweep cases (the leading-zero pair AND the fullwidth case) plus one dedicated test (eleven failures total; 26 of 37 pass). Neither of these two is one of the twelve fakes counted above, because no review round ever constructed either one; they are included here only to demonstrate that the sweep's value was never limited to the shapes reviewers happened to find by hand.
