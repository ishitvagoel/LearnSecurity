# Lab: 2.2-request-path

**Module:** `2.2`
**Authorized scope:** this directory only. Local FastAPI fixture; no live CDN, no DNS resolution, no real TLS handshake, no third-party target.
**Tier:** 2 (component). A real FastAPI request/response cycle through `fastapi.testclient.TestClient`, with server-side state (`_ORIGIN_STORE`, `_CACHE`) that persists across calls within one test and resets between tests. The TLS-hop check (`hop_is_trustworthy`, C3) is a pure predicate colocated in the same app and exercised through `POST /internal/relay` rather than a bare function call, because this fixture never performs an actual TLS handshake — see `lab-realism.mdc`; a real handshake is out of this module's local-fixture scope, so the check it would gate is tested as a request instead.

**Invariant (C1):** A shared cache entry may be returned only when the key includes the company the caller is bound to, not the path alone.
**Invariant (C2):** The company used for an authorization decision must come only from the caller's own credential, never from a client-supplied `X-Company` (or other forwarded-identity) header.
**Invariant (C3):** A hop-authentication check must require a trusted CA, an exact hostname match, and an accepted TLS version together; a missing or unrecognized input fails closed.
**Root cause class:** trust (C2: identity read from a client-controlled channel) and shared mechanism (C1: a cache with no company dimension in its key; C3: a check that stops at "some cert validated").
**Non-goals:** live CDNs, DNS hijacking, a real TLS handshake, poisoning a public cache.

## Reset

No persistent state between tests. `conftest.py` loads a fresh module and calls `reset()` before every test. Optional: `git checkout -- labs/2.2/2.2-request-path`.

## Vulnerable behavior (local only)

`_resolve_company` returns a client-supplied `X-Company` header when present, instead of only the company `API_KEYS[api_key]` names. `_CACHE` is a `dict[str, str]` keyed on `note_id` alone. `hop_is_trustworthy` returns `cert_trusted_ca is True` and nothing else — it never looks at `presented_hostname` or `tls_version`.

## Structural fix

`_resolve_company` never reads `x_company`. `_CACHE` becomes `dict[tuple[str, str], str]` keyed on `(note_id, company)`. `hop_is_trustworthy` requires `cert_trusted_ca is True` **and** `presented_hostname == expected_hostname` **and** `tls_version` in `{"1.2", "1.3"}`.

## Verify

```bash
python3 -m pytest labs/2.2/2.2-request-path/tests --impl vulnerable   # 6 of 35 pass
python3 -m pytest labs/2.2/2.2-request-path/tests --impl fixed        # 35 of 35 pass
```

If `fastapi`/`httpx` are not already installed: `pip install -r labs/2.2/2.2-request-path/requirements.txt`.

Thirty-five tests across two files: `test_cache_key.py` (C1, C2 — normal case, both forbidden outcomes, a malformed-credential case, a boundary case, and one anti-fake test per claim using company and note-id values never written elsewhere in the file) and `test_tls_hop.py` (C3 — normal case, the hostname-mismatch forbidden outcome, a TLS-version boundary at 1.2, an unknown-trust-state failure case, an explicitly-untrusted-CA failure case distinct from the unknown-state case, three hostname anti-fake tests (a prefix fake, a substring-anywhere fake, and a suffix-without-boundary fake), four version-string anti-fake tests each isolating one specific, historically real fake (a sorts-lexicographically-high fake, a hand-written forward-compatible allow-list fake, a parses-to-a-float-in-range fake, and an incidental-whitespace fake), and one sixteen-case parametrized sweep test asserting rejection across a broad, systematically-chosen set of version-string near-misses — the sixteen parametrized cases are what take the file's raw test count from nineteen to thirty-five).

Verified against eleven constructed fakes, each isolating exactly one gap, every count checked by reconstructing the exact fake and running the real suite rather than incrementing an old number: keying the cache correctly while leaving the `X-Company` override in place, matching `vulnerable/app.py`'s own check order (API key validity decided first, then the header) — passes 33 of 35 and fails exactly the C2 forbidden-outcome test and its anti-fake pair; the malformed-credential case (an unregistered key with a company header) still passes, because the key check runs and fails before the header is ever consulted. Removing the header override while leaving the cache keyed on path alone passes 33 of 35 and fails exactly the C1 forbidden-outcome test and its anti-fake pair. `presented_hostname.startswith(expected_hostname)` in place of equality passes 34 of 35 and fails only its own anti-fake test. `expected_hostname in presented_hostname` passes 32 of 35 and fails all three hostname anti-fake tests, not only the two it was originally built against — "origin.internal" is a substring of "evil-origin.internal" exactly as it is a substring of a prefix or middle-placed attacker string, so a check that only asks "does the expected name appear anywhere" cannot tell any of the three shapes apart. `presented_hostname.endswith(expected_hostname)` in place of equality — the same mistake from the third boundary position, catching a name glued onto the end with no separator — passes 34 of 35 and fails only its own anti-fake test. `if cert_trusted_ca is None: return False` in place of `if cert_trusted_ca is not True: return False` — a plausible reading of "fails closed on an unrecognized trust state" that only checks for the *unknown* case and lets an explicitly-resolved-untrusted certificate (`False`) fall through to the hostname/version checks — passes 34 of 35 and fails only `test_explicitly_untrusted_ca_is_rejected_even_with_matching_hostname_and_version`. A hand-written `{"1.2", "1.3", "1.4"}` in place of `_ACCEPTED_TLS_VERSIONS` itself — a plausible "let's allow the next version too" guess that adds a version this fixture has never actually accepted — passes 34 of 35 and fails only `test_anti_fake_forward_compatible_allow_list_still_rejects_an_unaccepted_version`, since none of the near-miss sweep's sixteen strings is `"1.4"` either. The remaining three previously-closed version fakes each fail every dedicated version anti-fake test built against them AND some or all of the sixteen near-miss sweep cases, since the sweep independently rediscovers each of them from a different angle: `tls_version < "1.2"` as a lexicographic lower bound fails all four dedicated version anti-fake tests plus eleven of the sixteen sweep cases (15 failures; 20 of 35 still pass) — a string sharing every character `"1.2"` has and then adding more (a trailing space, a decimal point and zero, an `e0` suffix) is never lexicographically smaller than `"1.2"` itself, so the sweep catches this fake eleven different ways beyond the one dedicated test it was originally isolated with. Parsing `tls_version` as a float and checking `1.2 <= version_num <= 1.3` fails both dedicated tests it was ever isolated with plus eleven sweep cases (13 failures; 22 of 35 still pass) — `float()` silently accepts leading/trailing whitespace, a leading `+` sign, exponential notation, and a leading zero, so nearly every numeric-looking near-miss in the sweep parses to a value inside `[1.2, 1.3]`. And the whitespace-stripping fake fails its one dedicated test plus four sweep cases that place whitespace in a position the dedicated test's single case never covered — `"\t1.2"`, `"1.3\t"`, and `"1.2\r\n"` among them (6 failures; 29 of 35 still pass).

**The eleventh fake, found in a sixth independent review round, is the first one this module's sweep test caught on its own, before a dedicated test for it was ever written.** A sixth review round constructed an `.isdigit()`-guarded `(major, minor)` integer-tuple parse — deliberately hardened past the whitespace-stripping fake, so that `"1.2\n".isdigit()` correctly returns `False` and that specific fake is rejected — but `int("01")` and `int("02")` both discard a leading zero, so `"01.2"` and `"1.02"` both parse to `(1, 2)` and are wrongly accepted. Reconstructing this exact fake against the sweep as it stood at that review (fifteen cases, missing `"1.02"`) showed it already failed on `"01.2"` alone, since that near-miss was chosen for exactly this leading-zero-normalization shape; `"1.02"` — the review's other named example, zero-padding the minor version instead of the major one — was added as a sixteenth sweep case to close the finding by the same margin the review demanded, rather than leave one of its two named divergent inputs untested. The completed fake fails only these two sweep cases and none of the eight dedicated anti-fake tests (two failures; 33 of 35 still pass) — confirming the sixth review's own observation that this fake is the first to defeat every dedicated test in the file while still failing the broader sweep, exactly the situation the sweep was added to guard against.

None of the eleven fakes above was constructed in response to the sweep test itself; the sweep was added proactively after four structurally distinct fakes had been found across four independent review rounds, and the eleventh fake — found in a fifth review round after the sweep already existed — was caught by that same sweep on the first attempt, with one case added afterward to match the review's own second named example. `test_anti_fake_version_near_miss_sweep_is_rejected` (sixteen cases) asserts rejection across a systematically-chosen set of near-misses — whitespace in positions the dedicated tests do not cover, leading and trailing zeros in either version position, an extra version segment, a sign prefix, exponential notation, and an accepted-looking substring embedded in a longer string — in one pass. Constructing two further fakes never found by any review round confirms the sweep's value is not limited to shapes a human reviewer has actually found: a regex check, `re.search(r"1\.[23]", tls_version)` in place of exact membership, would have passed all nineteen tests that existed before the sweep but fails all sixteen sweep cases plus two of the dedicated version anti-fake tests (eighteen failures total; 17 of 35 pass), because an unanchored search matches "1.23", "1.234", and even "TLSv1.2" and "1.2 or 1.3" as containing the pattern; and parsing `tls_version` into an `(major, minor)` integer tuple with no digit-only guard at all — a step short of the eleventh fake above, and correspondingly easier to catch — would have passed every pre-sweep test but fails nine sweep cases plus one dedicated test (ten failures total; 25 of 35 pass). Neither of these two is one of the eleven fakes counted above, because no review round ever constructed either one; they are included here only to demonstrate that the sweep's value was never limited to the shapes reviewers happened to find by hand.
