# Lab: 2.2-request-path

**Module:** `2.2`
**Authorized scope:** this directory only. Local FastAPI fixture; no live CDN, no DNS resolution, no real TLS handshake, no third-party target.
**Tier:** 2 (component). A real FastAPI request/response cycle through `fastapi.testclient.TestClient`, with server-side state (`_ORIGIN_STORE`, `_CACHE`) that persists across calls within one test and resets between tests. The TLS-hop check (`hop_is_trustworthy`, C3) is a pure predicate colocated in the same app and exercised through `POST /internal/relay` rather than a bare function call, because this fixture never performs an actual TLS handshake — see `lab-realism.mdc`; a real handshake is out of this module's local-fixture scope, so the check it would gate is tested as a request instead.

**Invariant (C1):** A shared cache entry may be returned only when the key includes the company the caller is bound to, not the path alone.
**Invariant (C2):** The company used for an authorization decision must come only from the caller's own credential, never from a client-supplied `X-Company` (or other forwarded-identity) header.
**Invariant (C3):** A hop-authentication check must require a trusted CA, an exact hostname match, and an accepted TLS version together; a missing or unrecognized input fails closed.
**Root cause class:** trust (C2: identity read from a client-controlled channel) and shared mechanism (C1: a cache with no company dimension in its key; C3: a check that stops at "some cert validated").
**Non-goals:** live CDNs, DNS hijacking, a real TLS handshake, poisoning a public cache.

## Reset

No persistent state between tests. `conftest.py` loads a fresh module and calls `reset()` before every test. Optional: `git checkout -- labs/2.2/2.2-request-path`.

## Vulnerable behavior (local only)

`_resolve_company` returns a client-supplied `X-Company` header when present, instead of only the company `API_KEYS[api_key]` names. `_CACHE` is a `dict[str, str]` keyed on `note_id` alone. `hop_is_trustworthy` returns `cert_trusted_ca is True` and nothing else — it never looks at `presented_hostname` or `tls_version`.

## Structural fix

`_resolve_company` never reads `x_company`. `_CACHE` becomes `dict[tuple[str, str], str]` keyed on `(note_id, company)`. `hop_is_trustworthy` requires `cert_trusted_ca is True` **and** `presented_hostname == expected_hostname` **and** `tls_version` in `{"1.2", "1.3"}`.

python3 -m pytest labs/2.2/2.2-request-path/tests --impl fixed        # 39 of 39 pass

Thirty-nine tests across two files: `test_cache_key.py` (C1, C2 — normal case, both forbidden outcomes, a malformed-credential case, a boundary case, and one anti-fake test per claim using company and note-id values never written elsewhere in the file) and `test_tls_hop.py` (C3 — normal case, the hostname-mismatch forbidden outcome, a TLS-version boundary at 1.2, an unknown-trust-state failure case, an explicitly-untrusted-CA failure case distinct from the unknown-state case, five hostname anti-fake tests (a prefix fake, a substring-anywhere fake, a suffix-without-boundary fake, a Unicode-confusable fake, and a zero-width-character fake), four version-string anti-fake tests each isolating one specific, historically real fake (a sorts-lexicographically-high fake, a hand-written forward-compatible allow-list fake, a parses-to-a-float-in-range fake, and an incidental-whitespace fake), and one nineteen-case parametrized sweep test asserting rejection across a broad, systematically-chosen set of version-string near-misses, including a non-ASCII digit sequence and a zero-width-character case — the sweep cases, together with the dedicated hostname Unicode-confusable and zero-width-character tests, are what take the file's raw test count from nineteen to thirty-nine).

Verified against thirteen constructed fakes, each isolating exactly one gap, every count checked by reconstructing the exact fake and running the real suite rather than incrementing an old number: keying the cache correctly while leaving the `X-Company` override in place, matching `vulnerable/app.py`'s own check order (API key validity decided first, then the header) — passes 37 of 39 and fails exactly the C2 forbidden-outcome test and its anti-fake pair; the malformed-credential case (an unregistered key with a company header) still passes, because the key check runs and fails before the header is ever consulted. Removing the header override while leaving the cache keyed on path alone passes 37 of 39 and fails exactly the C1 forbidden-outcome test and its anti-fake pair. `presented_hostname.startswith(expected_hostname)` in place of equality passes 38 of 39 and fails only its own anti-fake test. `expected_hostname in presented_hostname` passes 36 of 39 and fails all three ASCII hostname anti-fake tests, not only the two it was originally built against — "origin.internal" is a substring of "evil-origin.internal" exactly as it is a substring of a prefix or middle-placed attacker string, so a check that only asks "does the expected name appear anywhere" cannot tell any of the three shapes apart. `presented_hostname.endswith(expected_hostname)` in place of equality — the same mistake from the third boundary position, catching a name glued onto the end with no separator — passes 38 of 39 and fails only its own anti-fake test. `if cert_trusted_ca is None: return False` in place of `if cert_trusted_ca is not True: return False` — a plausible reading of "fails closed on an unrecognized trust state" that only checks for the *unknown* case and lets an explicitly-resolved-untrusted certificate (`False`) fall through to the hostname/version checks — passes 38 of 39 and fails only `test_explicitly_untrusted_ca_is_rejected_even_with_matching_hostname_and_version`. A hand-written `{"1.2", "1.3", "1.4"}` in place of `_ACCEPTED_TLS_VERSIONS` itself — a plausible "let's allow the next version too" guess that adds a version this fixture has never actually accepted — passes 38 of 39 and fails only `test_anti_fake_forward_compatible_allow_list_still_rejects_an_unaccepted_version`, since none of the near-miss sweep's nineteen strings is `"1.4"` either. Parsing `tls_version` as a float and checking `1.2 <= version_num <= 1.3` fails both dedicated tests it was ever isolated with plus twelve sweep cases, the fullwidth case among them, since Python's `float()` accepts fullwidth Unicode digits (14 failures; 25 of 39 still pass), but NOT the zero-width case, since `float()` raises `ValueError` on a string containing U+200B rather than silently accepting it. And the whitespace-stripping fake fails its one dedicated test plus four sweep cases that place whitespace in a position the dedicated test's single case never covered (6 failures; 33 of 39 still pass), also NOT reaching either non-ASCII case, since `.strip()` removes neither a fullwidth digit nor a zero-width/format character.

The lexicographic-lower-bound fake (`tls_version < "1.2"`) fails all four dedicated version anti-fake tests plus thirteen of the nineteen sweep cases — every ASCII near-miss that sorts at or above `"1.2"`, the fullwidth-digit case (a fullwidth digit's code point sorts above any ASCII digit), AND the zero-width case, since `"1.2​"` shares every character `"1.2"` has and then adds one more, and a string that is a proper superset-by-extension of another is never lexicographically smaller than it (17 failures; 22 of 39 still pass) — the same "recompute, don't increment" pattern this module has needed for every one of its non-ASCII additions, since neither the fullwidth nor the zero-width case was in the suite when this fake was originally closed.

**The eleventh fake, found in a sixth independent review round, was the first one this module's sweep test caught on its own before a dedicated test for it ever existed — and its count has grown twice since, purely from re-deriving it against the current suite rather than trusting the prior count.** A sixth review round constructed an `.isdigit()`-guarded `(major, minor)` integer-tuple parse — deliberately hardened past the whitespace-stripping fake — but `int("01")` and `int("02")` both discard a leading zero, so `"01.2"` and `"1.02"` both parse to `(1, 2)` and are wrongly accepted. It also wrongly accepts the fullwidth case (`str.isdigit()` and `int()` both treat fullwidth digits the same as ASCII ones), but NOT the zero-width case, since `"2​".isdigit()` is `False` — a zero-width character is not a digit, so this fake's own digit-only guard correctly rejects it. The fake fails exactly three sweep cases and none of the (now ten) dedicated anti-fake tests (three failures; 36 of 39 still pass) — unchanged from the prior round, since the zero-width case does not add a fourth failure here.

**The twelfth fake, found in a seventh independent review round, is a different technique from all eleven before it — normalizing the string under Unicode canonical-compatibility rules before comparing — and the first fake found to affect BOTH the version and hostname checks with the same one-line change to each.** `unicodedata.normalize("NFKC", ...)` before each comparison is a defensive habit standard Unicode security guidance actively recommends for untrusted strings. It fails only the sweep's fullwidth case and the dedicated Unicode-confusable hostname test (two failures; 37 of 39 still pass) — NOT the zero-width sweep case or the new zero-width hostname test, since NFKC normalization does not remove or fold Unicode category Cf (format/zero-width) characters at all, confirmed directly: `unicodedata.normalize("NFKC", "1.2​") == "1.2​"`, unchanged.

**The thirteenth fake, found in an eighth independent review round, is a third distinct technique — stripping every Unicode category-Cf (format, zero-width, bidi-control) character before comparing — and the second fake found to affect both checks with the same one-line change to each, but a technique the twelfth fake's own fix does nothing against, and vice versa.** `"".join(ch for ch in s if unicodedata.category(ch) != "Cf")` applied to both comparisons, in place of the bare membership/equality tests, is the same class of mitigation standard guidance recommends against invisible-character-smuggling ("trojan source") attacks. It fails only the sweep's zero-width case and the new dedicated zero-width hostname test (two failures; 37 of 39 still pass) — NOT the fullwidth sweep case or the Unicode-confusable hostname test, since fullwidth digits and letters are categories Nd/Lo/Ll, not Cf, so Cf-stripping leaves them untouched and this fake agrees with the real fix on them by coincidence, exactly as the NFKC fake agreed with every ASCII test by coincidence before round 7 found it. This is the module's own recorded stopping point for hand-picked Unicode-normalization-adjacent fakes: `spec.md`'s "Known residuals" section now names any further not-yet-constructed technique in this class as an accepted non-goal rather than an open search, since two independent, non-overlapping Unicode techniques found in two consecutive rounds is enough evidence that this specific sub-space does not converge by one-category-at-a-time hand construction any better than the ASCII near-miss space already showed it didn't after round 4.

None of the thirteen fakes above was constructed in response to the sweep test itself; the sweep was added proactively after four structurally distinct fakes had been found across four independent review rounds. The eleventh fake was found in a sixth round after the sweep already existed and was caught by it on first contact; the twelfth and thirteenth were each found in their own review round and closed by extending the sweep with one more case plus one new dedicated hostname test, the same "extend rather than isolate anew" pattern the eleventh fake established. `test_anti_fake_version_near_miss_sweep_is_rejected` (nineteen cases) asserts rejection across a systematically-chosen set of near-misses — whitespace in positions the dedicated tests do not cover, leading and trailing zeros in either version position, an extra version segment, a sign prefix, exponential notation, an accepted-looking substring embedded in a longer string, a non-ASCII digit sequence, and a zero-width/format character — in one pass. Constructing two further fakes never found by any review round confirms the sweep's value is not limited to shapes a human reviewer has actually found: a regex check, `re.search(r"1\.[23]", tls_version)` in place of exact membership, would have passed all nineteen tests that existed before the sweep but fails all fifteen ASCII-only sweep cases plus the zero-width case (since `"1.2"` is a literal substring of `"1.2​"`, an unanchored search still matches it) — not the leading-zero or fullwidth ones — plus two of the dedicated version anti-fake tests (eighteen failures total; 21 of 39 pass); and parsing `tls_version` into an `(major, minor)` integer tuple with no digit-only guard at all fails ten sweep cases (the leading-zero pair and the fullwidth case, but NOT the zero-width case, since bare `int()` raises `ValueError` on it rather than silently accepting it) plus one dedicated test (eleven failures total; 28 of 39 pass). Neither of these two is one of the thirteen fakes counted above, because no review round ever constructed either one; they are included here only to demonstrate that the sweep's value was never limited to the shapes reviewers happened to find by hand.
