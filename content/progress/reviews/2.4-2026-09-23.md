## Blocker 1 — the anti-fake coverage does not catch a correctly-shared, single-process lock, even though the module's own teaching claim (C4) and its own assessment item (#5) both assert this exact distinction matters *(Safe executable lab — critical)*

The task asked me to construct my own adversarial fake distinct from the shipped Candidate-A shape — specifically "a per-process lock that would work single-instance but not across multiple app instances/workers" — and check whether the suite catches it. I built exactly this: a module-level `threading.Lock()` (constructed once, at import time, genuinely shared by every request in the process — unlike `candidate_fix.py`'s per-call lock), wrapping a check-then-act `SELECT`/`INSERT` pair, with no database `UNIQUE` constraint, plus a fail-closed `except sqlite3.Error` around the connection call. ```

**All seven tests pass, including `test_concurrent_first_requests_with_a_never_seen_key_still_produce_one_share`.** This is not a hypothetical gap — it is the exact scenario `spec.md`'s C4 claim and `items.md` item 5's own answer key describe as broken: "even a correctly *shared* lock only serializes callers inside one process — it does nothing for two separate `uvicorn` worker processes, which is the default condition for any deployment this course assumes" (`spec.md` C4), and `keys/2.4.md` item 5's answer states this even more explicitly: "a module-level lock shared across every call within one process still only serializes threads *inside that one process's memory space*; it does nothing for a second, third, or fourth `uvicorn` worker process." **Both of these are true statements about production reality — but the shipped test suite cannot and does not test the distinction they describe**, because `test_concurrent_first_requests_with_a_never_seen_key_still_produce_one_share` fires eight threads from a `ThreadPoolExecutor` against a single `impl.app` object in a single Python process (`conftest.py`'s `client`/`impl` fixtures load exactly one module per test). A single shared lock genuinely closes the race for eight threads in one process — Python's own GIL cooperation aside, the lock itself is sufficient here — so this fake is not "getting lucky against a weak test"; it is a **structurally correct answer to the only concurrency scenario this lab's fixture can express**, while still being the same class of wrong fix the module spends an entire lesson (`04-build.md`), a design-exercise assessment item (#5), and part of `08-review.md`'s seeded review teaching learners to reject.

Restored the original `fixed/app.py` immediately after (`git checkout --`; `md5sum` confirmed match to the `HEAD` blob).

This is the same defect class the 0.2 review's Blocker 1 found (a hand-constructed fake reproduces the module's own named forbidden distinction and passes every test, including the test built specifically to catch it) — here it shows up not in an app-level predicate but in the lab's own concurrency-testing *technique*: a same-process, multi-threaded test can never, by construction, distinguish "atomic because the database enforces it" from "atomic because a correctly-shared in-process lock enforces it," and this module explicitly teaches that distinction as load-bearing (it is the entire subject of item 5 and half of `08-review.md`'s reasoning). A learner who ships the "wrong" answer — a correctly-shared lock instead of the `UNIQUE` constraint — would pass this lab's full suite.

**To close:** either (a) add a test that genuinely exercises cross-process/cross-worker concurrency (e.g., running two separate OS processes, or two separate module instances with independent lock objects, against the same on-disk SQLite file, and asserting the row count), which is the only way to make the distinction the lesson teaches actually checkable in code; or (b) if that is judged out of scope for a Tier-2 local fixture, honestly narrow the claim in `spec.md`'s coverage contract and `05-verify.md` to state plainly that the concurrency test verifies atomicity *within one process* and cannot, by construction, verify the cross-process claim C4 and item 5 make — the same honesty pattern this module already uses correctly for C5 ("not directly code-testable... modeled in prose"). Currently the module states the cross-process claim as if the lab's green suite were evidence for it, which it is not.
