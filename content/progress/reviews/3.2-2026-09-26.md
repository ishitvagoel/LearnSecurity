## Blocker 1 — C3's placeholder-mitigation check does not do what item 4 / the examiner key say it does

`fixed/app.py`'s check is an **exact-match** membership test:

```python
mitigation = str(top.get("mitigation", "")).strip().lower()
if mitigation in _PLACEHOLDER_MITIGATIONS:   # {"", "tbd", "todo", "pending", "n/a", "later"}
```

`assessment/items.md` item 4 presents this exact scenario: `"mitigation": "pending security review"` on the top-priority row, and asks the learner to explain "why this row should not pass this module's priority/mitigation check." `content/assessment/keys/3.2.md`'s answer to item 4 states: *"a check that only rejects a short list of exact literal strings (`"tbd"`, `""`, `"pending"`) would catch this specific example (`fixed/app.py`'s own placeholder list includes `"pending"`)."*

This is factually false, and I verified it two ways. First, directly:

```python
>>> _PLACEHOLDER_MITIGATIONS = {"", "tbd", "todo", "pending", "n/a", "later"}
>>> "pending security review".strip().lower() in _PLACEHOLDER_MITIGATIONS
False
```

Second, against the live `evaluate_gate`, submitting the exact document item 4 describes (all three mandatory threats present, owned, triggered, flowed, and prioritized; `cross-tenant-read` — the top-priority threat — carrying `mitigation: "pending security review"`):

```python
result = evaluate_gate(model, True, [])
# {'gate': 'pass', 'reasons': [], 'scanner_extra_findings': [], 'scanner_green': True}
```

The real, shipped `fixed/app.py` **passes** this model with an empty `reasons` list. It does not reject the placeholder-in-substance mitigation the module's own assessment item exists to test. `"pending security review"` is a different string from the literal `"pending"`; the set membership test requires an exact match on the whole trimmed/lowered string, not a substring or token match, so a placeholder padded with any other words defeats it — which is exactly the near-miss `lessons/04-build.md` itself warns about in prose ("a real answer to a real answer looks-like question... an exact-match denylist... cannot know what a real answer is supposed to look like") but which the actual code and the actual assessment key do not treat consistently with each other.

This is not a hypothetical fake I constructed — it is the real, currently-shipped `fixed/app.py`, exercised with the exact scenario the module's own assessment item and examiner key present as a case the check should (and, per the key, does) reject. No test in `test_property.py` exercises a placeholder-in-substance mitigation that isn't a literal denylist entry (`test_top_priority_threat_without_real_mitigation_fails` only ever uses the literal string `"TBD"`), so this gap shipped through a green 10/10 suite undetected.

**This fails the review task's explicit requirement to verify "the examiner key's answers are correct against the real code."** They are not, for item 4. Either `fixed/app.py`'s placeholder check needs to become substring/token-aware (so it actually catches `"pending security review"`, matching what item 4 and the key claim), or item 4's scenario and the key's answer need to be rewritten to state honestly that this specific example is *not* caught by the current denylist-based check — i.e., to become the demonstration of the residual limitation, not a claim that the mechanism resolves it. Either fix is legitimate; leaving the current mismatch is not, because a learner (or an examiner) who actually runs the code against the key's own worked example gets a contradictory result.

## Blocker 2 — C2's flow-coverage check has the same class of anti-fake gap the pre-review pass just fixed for C4

The pre-review pass (`a63621a`) found and closed a real gap in C4: every existing `revisited_after` test used a list containing *exactly* the fired trigger's own name, so a fake checking "is this list merely non-empty" passed the whole suite. The task instructions asked me to look for the same *class* of gap — a suite that only tries the "correct-shaped" positive case and a strict-subset negative case, never a same-size-but-wrong-content negative case — elsewhere in the module, specifically suggesting C2's flow-tracing check as a place to look.

I found exactly that. Every existing test's `declared_flows` is either the complete, correct 3-item set, or a 2-item strict subset missing exactly `worker-share-redelivery` (`test_untraced_worker_flow_fails_even_with_all_ids_present`). No test ever supplies three declared flows where the count is right but one entry is a wrong or unrelated name. A gate that checks `len(declared_flows) < len(REQUIRED_FLOWS)` instead of `REQUIRED_FLOWS - declared_flows` (set membership) passes all ten existing tests (confirmed above, Fake 1) and — confirmed directly against the fake — passes a threat model whose diagram never traces the worker-redelivery path at all, as long as some other, irrelevant flow name pads the count back to three. This is precisely the forbidden outcome `module.yaml`'s `labSpec.forbiddenOutcomes` names ("A required flow (worker-share-redelivery) is untraced while the gate still passes") and precisely the shape of failure `lessons/05-verify.md` calls "this module's most important test."

The real, shipped `fixed/app.py` does *not* currently have this defect — it correctly uses set difference, not length comparison — so this is a test-suite coverage gap, not a shipped-code correctness bug (unlike Blocker 1). But it is exactly the standard the module itself was just held to for C4: the task's brief explicitly treats "every existing test only tries the correct-shaped case, never a same-size-but-wrong-content near-miss" as disqualifying until closed with a dedicated test, and I don't think it would be consistent to apply that bar to C4 and not to the symmetric case in C2. A test in the same shape as the new C4 test (e.g. `test_flow_coverage_is_checked_by_membership_not_by_count`, submitting three declared flows where one is a decoy and `worker-share-redelivery` is absent) would close this.
