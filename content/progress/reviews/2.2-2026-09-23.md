## Blocker

**A different, independently-constructed adversarial fake for C3 passes the entire 14-test suite, including every anti-fake test — the module's own "five constructed fakes" review missed a sixth gap in the same check it had just repaired for a different signal.**

Per the task's instruction to build my own fake rather than only re-running the documented ones, I replaced `fixed/app.py`'s version check:

```python
# real fixed code
if tls_version not in _ACCEPTED_TLS_VERSIONS:   # _ACCEPTED_TLS_VERSIONS = {"1.2", "1.3"}
    return False
```

with a plausible alternate "fix" using a lexicographic lower bound instead of exact set membership:

```python
if tls_version < "1.2":
    return False
```

This passes both existing version-related tests (`"1.2"` accepted, `"1.1"` rejected — `"1.1" < "1.2"` is true lexicographically) exactly as the real fix does. I ran the full suite against it:

```
$ python3 -m pytest labs/2.2/2.2-request-path/tests --impl fixed
14 passed
```

**All fourteen tests pass, including both hostname anti-fake tests and the newly-added untrusted-CA anti-fake test.** No test in either file sends a `tls_version` value outside `{"1.1", "1.2", "1.3"}`, so nothing distinguishes "exact membership in the accepted set" from "lexicographically at or above the oldest accepted version" — a string like `"9"`, `"2.0"`, or `"A"` sorts above `"1.2"` in Python string comparison (`"9" > "1.2"` is `True`; so is `"A" > "1.2"`, since `'A'` (65) > `'1'` (49) in ASCII) and would be accepted as trustworthy by this fake even though it is not one of the two versions this module's own claim, README, and lessons name as accepted. This is the identical *shape* of gap the module's own second-pass changelog found and fixed for the CA-trust check (a plausible alternate implementation that agrees with the real fix on every input the suite happens to try, and disagrees on inputs it does not) — except this instance is in the version check, and it was not found. I restored the file afterward (`git status --porcelain` clean, confirmed).

I also independently reconstructed one of the module's own documented fakes (the cache-only fix leaving the header override open) to confirm the module's account of its own verification work is not fabricated — it reproduces exactly: 12 of 14 pass, and the two failures are precisely C2's forbidden-outcome test and its anti-fake pair, as `README.md` and `keys/2.2.md` both claim.

**Severity:** this is a real gap in the one thing a Tier-2 lab's anti-fake suite exists to guarantee for a critical claim (C3, hop authentication) — that a plausible-but-wrong alternate implementation cannot pass by agreeing with the real fix only on the inputs the suite happens to try. `04-build.md` (L52) explicitly names hostname-comparison near-misses as the exact class of mistake the anti-fake tests exist to catch, and the module's own second-pass changelog treats an analogous CA-trust gap as worth a dedicated new test — but the identical class of gap in the version check, one line away in the same function, was not looked for.
