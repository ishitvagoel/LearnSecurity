# Examiner notes — 2.1 (not learner-facing)

## Property

The same request bytes must yield one company/tenant meaning, used identically by the who-is-allowed check and by storage. If two readers of those bytes would disagree, ingest refuses. The failure is disagreement between readers, not a missing authentication check. Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

## Lab

- `labs/2.1/2.1-parser-boundaries/vulnerable/` must fail 6 of 9 tests: `test_duplicate_tenant_keys_are_one_meaning`, `test_middle_duplicate_is_not_silently_dropped`, `test_missing_tenant_field_is_rejected`, `test_checker_rejects_a_different_ambiguous_object`, `test_non_string_duplicate_is_not_invisible_to_the_checker`, `test_nested_tenant_is_not_mistaken_for_the_top_level_claim`.
- `labs/2.1/2.1-parser-boundaries/fixed/` must pass all 9.
- Root cause: two readers (a first-key regex scan and CPython's last-key-wins `json.loads`) never have their outputs compared. The fixed implementation retires the second reader and asks `json.loads`'s own `object_pairs_hook` for every top-level occurrence of `tenant`, refusing unless the full set has exactly one distinct value — this closes both the 3+-occurrence gap (endpoints coinciding while a middle value disagrees) and the non-string-value gap a regex-based collector cannot see. Occurrences are scoped to the hook's *last* invocation only (always the root object, since nested objects resolve first) specifically because an earlier version of this fix collected occurrences from every nesting depth and could be satisfied by a `tenant` key buried in an unrelated nested field, with no top-level claim at all.
- Anti-fake pair (`test_checker_rejects_a_different_ambiguous_object`, `test_checker_accepts_a_different_unambiguous_object`) constructs objects never seen in the `AMBIGUOUS`/`CLEAN` module constants. Verified: a fake that special-cases the exact `AMBIGUOUS` string (returning a hardcoded refusal for that literal text, else deriving both `acl_tenant` and `stored_tenant` from one shared read) fails 6 of 9 tests, including the anti-fake test — the trivial "derive both fields from the same read" trick that would otherwise slip past a looser assertion is specifically why `test_checker_rejects_a_different_ambiguous_object` asserts strict refusal rather than the forbidden-outcome test's looser "or the tenants happen to match" form.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **B** is the rule. **A** and **D** are tools. **C** is a false assurance.

**Why each is categorized this way:**
- **A** ("we use Pydantic v2") is a tool claim: Pydantic validates a value's shape *after* some reader has already collapsed any duplicates, so it cannot by itself guarantee the collapsing was done safely. To become evidence for the rule, it would need to be paired with a demonstration of what Pydantic sees when duplicates exist upstream.
- **D** ("a regex filter for the string tenant twice") is a tool claim, and a weaker one than A: it is a denylist that fails against whitespace variation, Unicode escapes, or a second `Content-Type` boundary, none of which changes the literal substring match it depends on. To become evidence, it would need to be replaced with an implementation that inspects the parsed structure rather than the raw text.
- **C** ("RFC 8259 says unique, so it's not a concern") is a false assurance: the RFC uses "should," not "must," and different real parsers demonstrably handle a violation differently — citing the spec's aspiration is not evidence about what any specific reader in this system actually does.

**Banding:** *developing* — sorts B correctly but cannot explain why C is false rather than merely weak. *competent* — sorts all four correctly with at least one specific reason each. *transfer-ready* — additionally explains why C is more dangerous than A or D: it actively discourages someone from writing the check at all, on the reasoning that the specification has already handled it.

### Item 2 — property vs. mechanism for parser agreement

**Answer:** **D** states the property. **A**, **B**, and **C** are mechanism or proxy claims, ranked C (closest to real evidence) > A > B (furthest).

**Why each falls short, ranked:**
- **C** ("`ingest_note` collects every occurrence and refuses unless the set has one value") is the closest to evidence: it is a claim about *this specific* implementation's actual behavior, verifiable by reading the code. It still falls short of being the property itself — it describes one implementation's mechanism, not the general requirement that mechanism exists to satisfy.
- **A** ("we validate against a JSON Schema") is weaker: a schema can constrain a value's shape after parsing, but nothing about schema validation inspects whether duplicate keys were resolved consistently before validation ran — schema validation happens too late in the chain to catch this class of defect.
- **B** ("no duplicate-key error in six months of logs") is the weakest: absence of an observed error is not evidence the check exists, only that no input has yet triggered whatever behavior is currently present, safe or not. It says nothing about the mechanism at all.

**Banding:** *developing* — picks D but cannot rank A/B/C. *competent* — picks D and correctly separates C (implementation evidence) from A and B (weaker proxies). *transfer-ready* — explains that B is not merely weak but actively misleading, since a system with no check at all would produce the identical absence of observed errors as a system with a correct one, until the day an adversarial or malformed input arrives.

### Item 3 — a different checker's gap

**Answer:** Root cause: the function compares only the first and last regex matches (`values[0]` and `values[-1]`), never inspecting any value in between, so a middle occurrence that disagrees with both endpoints is invisible to the comparison. Precondition: an object with three or more occurrences of the same key, where the first and last happen to coincide. Impact: `ingest_note` returns `accepted: True` with `acl_tenant == stored_tenant == "tA"`, silently discarding the middle claim of `"tC"` — the object is accepted as though it were unambiguous, when a genuine three-way disagreement occurred.

**Banding:** *developing* — identifies that the function is wrong without tracing the specific input through it. *competent* — correctly traces `first="tA"`, `last="tA"`, and states the accepted result. *transfer-ready* — additionally connects this to the general pattern: any check comparing a fixed, small number of positions (first/last, or first/second) rather than the full set of occurrences has this same shape of gap, regardless of how many positions it checks, unless it checks all of them.

### Item 4 — reading a candidate fix

**Answer:** It does **not** pass. Tracing `{"tenant":"tA","body":"x","tenant":"tC","tenant":"tA"}` through this function: `_first_tenant` finds the first regex match, `"tA"`. `_last_tenant` uses `json.loads`, which keeps the last duplicate assignment, also `"tA"`. Since `acl == stored == "tA"`, the `if acl != stored` condition is false, and the function falls through to `accepted: True`. The middle occurrence of `"tC"` is never inspected by this function at all.

**Banding:** *developing* — says it passes, or says it fails but cites the wrong reason. *competent* — correctly traces the values and concludes it fails, citing the missing middle-value inspection. *transfer-ready* — additionally notes this fix is functionally identical to Item 3's checker in its failure mode, despite using different helper function names, because both compare exactly two positions rather than the full set.

### Item 5 — which operation is missing

**Answer:** **Canonicalization** is missing. Validation (step 1) confirms the tenant value matches an allow-list, but validation runs on whatever value a prior reader already produced — it has no way to know that a *different* reader, consuming the same raw bytes, might have produced a different value. Sanitization (step 2) and encoding (step 3) both operate on the note body for output contexts entirely separate from the tenant-identity question. None of the three present operations asks "was exactly one representation of this value chosen, before any decision was made, from among however many occurrences the raw bytes contained" — that question is canonicalization's alone, and it has to run *before* validation, not alongside or after it.

**Banding:** *developing* — names canonicalization as missing without explaining why the other three cannot substitute. *competent* — explains why validation specifically cannot substitute (it trusts whatever value it is handed). *transfer-ready* — explains why canonicalization must run *before* validation, using this module's own vocabulary distinction, and why this ordering constraint (not merely the *existence* of canonicalization) is the actual requirement.

### Item 6 — two candidate fixes under a constraint

**Answer:** Engineer B's fix should be chosen. Engineer A's fix fails the stated constraint directly: with three or more duplicate occurrences, comparing only the first and last cannot detect a disagreeing middle value, as Items 3 and 4 both demonstrate concretely. Engineer B's fix (collect every occurrence, require the full set to have exactly one distinct value) handles an arbitrary number of duplicates correctly, because set-based agreement does not depend on which two positions happen to be compared. Where Engineer B's fix still falls short: it operates on one reader's notion of "every occurrence" (a regex scan across the raw text); it does not verify that a completely independent reader — a different JSON library, or a database's own JSON handling — would extract the same set of occurrences from the same bytes. Cross-technology agreement remains an open question this fixture does not test.

**Banding:** *developing* — picks B without addressing the constraint explicitly. *competent* — explains why A fails the constraint and B satisfies it. *transfer-ready* — additionally names the specific residual (cross-technology agreement) rather than claiming B's fix is complete.

### Item 7 — the worker re-parse gap

**Answer (indicative, not exhaustive):** A worker-safe design needs the worker to either (a) reuse the exact same parse result the ingest path already produced and stored, rather than re-parsing the raw bytes independently, or (b) if the worker must re-parse, run the identical agreement check ingest used and refuse or quarantine on any disagreement, exactly as ingest does. The specific failure mode "the data was already validated once" cannot catch: a library version change between ingest time and worker-run time, where the ingest-time library and the worker-time library disagree on duplicate-key handling even though neither individually changed its behavior on any single occasion — the disagreement is between two different points in time, not between two readers running simultaneously.

**Distractor pattern:** An answer that proposes "re-validate the tenant field's format" without re-checking agreement across occurrences repeats Item 5's confusion between validation and canonicalization, applied to a new context — band as developing. An answer that proposes re-running the full agreement check, but does not name a residual, is competent. An answer that also names the "library version drifted between two points in time" failure mode specifically is transfer-ready.

### Item 8 — clinic REST and GraphQL

**Answer:** C1 (one meaning used by every consumer) and C4 (refuse-or-single-reader, never guess) transfer essentially unchanged — the mechanism is agnostic to which payload carries the disagreement. C2 (the reader chain) needs a materially different treatment: a GraphQL `variables` payload is not merely another link in one chain, it is a second JSON document, sent over the same wire, that must independently satisfy the same one-meaning requirement before GraphQL's own variable coercion ever runs. **The mechanism is not GraphQL field aliasing.** GraphQL coerces a declared variable's value once per operation, so every reference to `$patient_id` inside one query necessarily uses the identical value — a variable cannot disagree with itself the way a JSON object's duplicate key can, and an answer that claims otherwise (for instance, that two aliased selections referencing the same variable can resolve to different values) is factually wrong about the GraphQL specification and should be banded no higher than developing regardless of how well-argued it otherwise reads. The real gap is one level below the type system: the `variables` JSON a client sends is ordinary JSON, and ordinary JSON can carry a duplicate `patient_id` key that some JSON decoder silently collapses before GraphQL ever sees "one coerced value." A check that only inspects the declared variable by name, after coercion, is validation running after canonicalization already happened invisibly — it never re-parses the raw `variables` text the way `fixed/parse_note.py`'s `object_pairs_hook` approach re-parses a note body.

**Banding:** developing restates "the same rules apply" without identifying where the JSON ambiguity actually lives, **or incorrectly claims GraphQL variables can disagree with themselves via aliasing** — this specific error caps the answer at developing even if the rest of the reasoning is otherwise strong. competent correctly locates the gap in the `variables` JSON payload rather than in variable coercion or aliasing, and connects it to C2. transfer-ready additionally explains, unprompted, why C1 and C4 do not need restating while C2 does, and explicitly distinguishes "the type system prevents a coerced variable from disagreeing with itself" (true) from "the transport JSON beneath the type system prevents a duplicate key" (false) as the crux of the whole item.

### Item 9 — the deny-line signal

**Answer:** Must carry: a `request_id`, an `ingest_reject_duplicate_key` counter increment, and a reason code (e.g. `reason=duplicate_tenant_key`). Must never carry: the note body, or the raw JSON text that was refused — either one would turn the deny event into exactly the kind of leak the refusal exists to prevent. A metric alone is insufficient because it only measures the path it is wired to; a bypassing code path (a worker, an alternate ingest route) that writes a row without going through the same instrumentation produces no metric signal at all, even while a disagreeing row sits in storage. A quarantine procedure is what catches rows a metric never saw.

**Banding:** developing includes the required fields but also includes a forbidden one, or proposes a metric with no quarantine story at all. competent gets both field lists right and explains why a metric alone is insufficient in general terms. transfer-ready gives the specific "bypassing code path" mechanism by which a metric-only design fails, matching Lesson 06's worked example.
