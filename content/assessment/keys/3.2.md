## Item key

**1.** A = false assurance (a scanner result answers "did a known pattern match," not "was the design walked for what can go wrong"). B = mechanism, and it is the rule's own observable behavior when it is proven to run — the gate's actual returned `reasons` list is the evidence, not the code's existence. C = false assurance (a workshop's quality at one point in time says nothing about whether the model stayed current, and "everyone agreed" is not a checkable claim). D = false assurance (a comment is not code any function reads or executes). Banding: *developing* — calls the scan or the workshop "the model," or misreads B as merely "having a model" rather than the check that consults it. *competent* — correctly sorts all four and states that B's own returned reasons, not the code's presence, is the actual evidence. *transfer-ready* — additionally ties B to C1's "regardless of what the scanner reports" clause and states that A becomes informative (not false) the moment it is combined with B, but is false assurance on its own.

**2.** Excerpt B is the one this item is built around: every threat id, owner, and trigger is present and correct, and yet `stolen-worker`'s coverage claim is unfalsifiable, because `worker-share-redelivery` never appears in `declared_flows` — nothing in the submission traces the path the threat depends on. C is also broken (missing owner), but for the more direct, C1-shaped reason the gate's presence-and-ownership check already catches on its own; it does not require the id-versus-flow distinction this item is testing. A strong answer names B specifically and states the distinction in these terms: a threat id is a claim; a declared flow is what would let a reviewer or a gate check that claim against the actual system, and B has the claim with nothing to check it against. Banding: *developing* — flags C only, or flags B without explaining why "id present" differs from "flow traced." *competent* — correctly identifies B as the best answer and states the id-versus-flow distinction. *transfer-ready* — additionally states that C's defect (no owner) would be caught by the gate's very first check, while B's defect requires the flow-coverage check specifically to exist at all, making B the sharper test of whether that second check was actually built.

**3.** A constructed document that defeats this check: a threat model whose only entry is `{"id": "generic-scan-finding", "mitigation": "supersedes a prior cross-tenant-read concern raised in Q2"}` — no threat entry anywhere has `id == "cross-tenant-read"`, but the literal substring `"cross-tenant-read"` appears inside the `mitigation` text of an unrelated entry. Root cause: the check tests whether each mandatory id string appears *anywhere* in the model's stringified representation, not whether a threat entry's own `id` field equals that string — it conflates "this text occurs somewhere in the document" with "this specific structured entry exists." Precondition: any free-text field (a mitigation, an old note, a comment embedded in the JSON) contains one of the three mandatory id strings for a reason unrelated to naming that threat. Impact: a threat model that has never actually named `cross-tenant-read` as a checkable row — no owner, no trigger, no priority, no mitigation resolved for it — passes the mandatory-id check, which is precisely the forbidden outcome this module's core property (C1) exists to prevent, reintroduced through a check that resembles the real one closely enough to pass a casual read. Banding: *developing* — states the check is "wrong" without constructing a document that demonstrates the gap, or without separating the three answers. *competent* — constructs a valid defeating document and gives three distinct, correct answers. *transfer-ready* — additionally states this is the same class of failure `labs/3.1/3.1-lab`'s anti-fake tests are built to catch (a check that resembles the real mechanism structurally but tests the wrong thing), and connects it to why `fixed/app.py` looks up `_threats_by_id(model)` — a dictionary keyed by each entry's actual `id` field — rather than ever stringifying the model.

**4.** Root cause: `"pending security review"` is a placeholder in substance — it names no mechanism, no owning module, and no decision — even though it is a complete, non-empty sentence rather than a bare `"TBD"`; a check that only rejects a short list of exact literal strings (`"tbd"`, `""`, `"pending"`) would catch this specific example (`fixed/app.py`'s own placeholder list includes `"pending"`), but a narrower or differently-worded placeholder (`"still deciding"`, `"revisit after Q3 planning"`) would slip past any check built as an exact-match denylist rather than one reasoning about what a real mitigation has to contain. Precondition: a reviewer reads the row, sees a grammatically complete, plausible-sounding sentence in the `mitigation` field, and reasonably assumes a decision was made, without asking whether that sentence names a specific mechanism or owner. Impact: the highest-priority threat in the entire model has no actual plan behind it, so if `cross-tenant-read` is the threat most likely to cause real harm, the team's prioritization exercise has correctly identified the most urgent problem and then produced nothing usable about what to do about it. Banding: *developing* — says the mitigation "looks fine" because it is non-empty, or does not distinguish this from a bare `"TBD"`. *competent* — correctly identifies the placeholder-in-substance problem and gives three distinct, correct answers. *transfer-ready* — additionally proposes that placeholder detection should reason about whether the text names a specific, checkable mechanism (a module, a function, an owning team's decision) rather than relying solely on a denylist of known-bad literal strings, and states the residual: no automated check can fully verify a mitigation's substance from text alone.

**5.** Expected direction: argue for candidate A (the merge-time gate). Under this item's constraint — pull requests every fifteen minutes, and a failing check blocks only the developer whose PR failed — the batch-audit alternative's core weakness gets worse, not better: at this cadence, dozens of pull requests can land between one nightly audit run and the next, so a regression introduced early in the day compounds across every subsequent change built on top of it before the audit even runs once. The stated cost of the merge-time gate (it blocks a developer) is also explicitly scoped in this constraint to affect *only that developer*, which directly answers `lessons/04-build.md`'s original concern about the batch alternative's advantage (decoupling audit from merge so one slow check does not block everyone) — that advantage matters less here, because the merge-time gate was never blocking "everyone" to begin with, only the author of the specific pull request that regressed the model. A flaky or slow audit is *more* costly under this constraint than under a lower-frequency-merge assumption, because the same audit interval now has to account for a much larger number of merges it might miss between runs. Banding: *developing* — picks A without engaging the fifteen-minute cadence, or picks B and defends it only in general terms. *competent* — argues for A and connects the argument specifically to merge frequency and to the "blocks only that developer" framing. *transfer-ready* — additionally states the one condition under which this item's answer could flip (a codebase whose CI infrastructure itself is slow or unreliable enough that blocking any individual merge on a live gate check is intolerable — at which point the batch alternative's cost profile becomes relatively more attractive, though still not "cost-free").

**6.** Removing a required flow is not automatically a defect — if the worker feature genuinely no longer exists, requiring a diagram to trace a flow that no longer exists would itself be a stale requirement. The defect this item tests for is procedural: this module's claims require that a threat row's disposition be a *deliberate, visible, owned* decision, not an artifact of two independent edits drifting apart. Before this removal ships, the `stolen-worker` threat row itself must be resolved in the same change — either removed alongside the flow with a stated reason (the capability it named no longer exists), or explicitly marked retired with an owner's sign-off — rather than left present in the model, still claiming a priority and a mitigation, referencing a flow the model no longer requires anyone to trace. Distinguish this from item 2's case: there, the underlying feature still exists and a submission merely omitted tracing it, which is a completeness bug the flow-coverage check already catches; here, the feature's necessity has itself changed, which is a design decision the gate's mechanical checks cannot evaluate and a human reviewer must. Banding: *developing* — calls the flow removal itself the bug, or does not notice the orphaned `stolen-worker` row. *competent* — correctly states the removal can be legitimate and identifies that `stolen-worker`'s row must be resolved in the same change. *transfer-ready* — additionally distinguishes this case from item 2's in the terms above and proposes what "resolved" should require (an owner's explicit sign-off recorded on the row, not merely the row's silent disappearance).

**7.** See `lessons/07-transfer.md`'s own four success criteria, restated here with banding. A strong answer names at least three channel-specific always-name threats (for example: `sms-content-leak`, a template including chart text; `number-swap`, a reused or reassigned phone number receiving another patient's reminder; `vendor-questionnaire-as-model`, treating a HIPAA-certification claim as equivalent to a threat walk) and states for each why no vendor questionnaire or HTTP-style scan could surface it. Banding: *developing* — reuses `cross-tenant-read` or another original-module id unmodified, or names threats without explaining why a questionnaire misses them. *competent* — derives new, channel-specific always-name threats, names at least one genuinely new flow type (the clinic-to-vendor-to-carrier-to-handset chain), and resolves a real mitigation on the top-priority row. *transfer-ready* — additionally names a channel-specific review trigger and states precisely what a `revisited_after`-equivalent record would need to contain for that trigger, and — only if the rewritten claim actually depends on a human-mediated opt-out step — correctly scopes an accessibility requirement to that step rather than to the classification decision itself.

**8.** Expected signals: (a) `missing_mandatory_threat reason=not_revisited id=cross-tenant-read trigger=new-share-path owner=authz` and (b) `missing_mandatory_threat reason=no_owner id=hostile-browser owner=unassigned` — note that case (b) cannot name a real owner to page, because the missing owner *is* the defect, so a strong answer recognizes this and states that the signal must route to a fallback recipient (a default security-champion queue, not a silently-dropped alert) rather than assuming an `owner` field is always available to route through. Threshold reasoning: scoping the alert to fire only when a *specific row's specific fired trigger* lacks a matching revisit entry produces a false-positive rate bounded by how many rows actually have a trigger fire against them; scoping it to fire whenever *any* trigger has ever fired anywhere in the model's history would re-alert on every subsequent, unrelated merge for as long as that trigger remains in the fired set, producing a false-positive rate that only grows over time and trains the recipient to ignore the channel — `lessons/06-operate.md` argues for the first (per-row, per-trigger) design specifically for this reason. Banding: *developing* — writes one generic signal without differentiating `reason`, or does not notice case (b)'s missing-owner routing problem. *competent* — both signals correctly shaped, the two designs correctly distinguished, and `lessons/06-operate.md`'s per-row scoping correctly identified as the intended design. *transfer-ready* — additionally states the routing problem in case (b) and proposes the fallback-recipient design, connecting it to `lessons/06-operate.md`'s residual-risk section on what happens when an alert has nobody to reach.

## Transfer

Reject Top 10 / CWE and "the vendor is HIPAA certified" as substitutes for the channel-specific derivation. Acceptable direction: `sms-content-leak`, `number-swap`, and a vendor-questionnaire-as-false-assurance threat, each with its own flow, priority, and mitigation, parallel in structure (not in content) to `cross-tenant-read`, `hostile-browser`, and `stolen-worker`. WCAG 2.2 applies only if the rewritten claim depends on a human-mediated step (for example, an opt-out flow); it does not apply to the classification or prioritization decisions themselves.

## Operate

Accept detect/recover designs that never carry a note body, session token, or mitigation text in the alert line itself — only a `reason` code, a threat `id`, and (when available) an `owner`. Reject a design that pastes the mitigation description into the alert "so the on-call engineer has context," and reject any design that computes staleness from a self-reported date field rather than from `revisited_after`. Recovery for a stale row requires adding the actual re-review record, never rewriting a date to make the row look current.
