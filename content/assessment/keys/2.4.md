## Seeded review — intended findings

`lessons/08-review.md` hands the learner `review/candidate_fix.py` as a PR claiming to add "idempotency check and thread-safety," with a four-question reading order rather than a stated answer. Applied to the file as it stands:

1. **Where does authority over the row get resolved?** `SELECT id FROM shares WHERE idempotency_key = ?` followed by a separate `INSERT` — two statements, not one atomic operation the database enforces. This is Candidate A's exact shape.
2. **Where does state actually change, and under what protection?** `lock = threading.Lock()` is the *first line inside* `share_note`'s body — a brand-new lock object on every single call. No two calls ever contend for the same lock, so the `with lock:` block provides no serialization whatsoever; this is the file's highest-severity finding, and the same underlying defect as question 1 viewed from a different angle (the lock was the author's own, failed, attempt to close the check-then-act gap).
3. **What happens on the failure path?** A bare `except Exception as exc:` catches everything and returns `{"accepted": True, "share_id": None}` — fails open, reopening C3's forbidden outcome independently of the concurrency defect. Fixing one of these two findings does not fix the other.
4. **What does the failure path make visible, and to whom?** `print(f"share failed for note={note_id} key={idempotency_key}: {exc}")` writes the *raw* idempotency key to standard output — lower severity on its own (it does not create a duplicate share) but compounds the fail-open finding, since it is exactly the failure path that is now also leaking key material.

**Plausible non-issue:** `note_id: str` accepts any string with no format check. This is not a finding for this module's property — authority over whether a given note id may be shared at all belongs to 1.2, not to this workflow's retry/race/fail-closed behavior. A learner who reports this as a headline finding has confused a general good practice with a defect in this specific diff.

A learner who names both the unshared lock and the fail-open `except`, distinguishes them as two independent findings (not one restated), and correctly dismisses the `note_id` non-issue has passed this review. `candidate_fix.py` is not wired into `pytest`; it must not be imported or run, per its own file docstring and `lessons/08-review.md`'s closing note.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **B** is the rule. **D** is a tool (Candidate A: correct for one call at a time, fails under real concurrency). **A** is a false assurance dressed as a tool. **C** is a false assurance.

**Why each is categorized this way:**
- **D** ("`SELECT` then `INSERT`") is a real, partial mechanism: it correctly closes the *sequential* retry case and is exactly `04-build.md`'s Candidate A. It needs the check and the record to become the same atomic operation (a `UNIQUE` constraint, or an equivalent database-enforced serialization) to become the rule.
- **A** ("a `threading.Lock()` created at the top of the handler") *looks* like a direct, on-topic response to a concurrency concern, which is exactly why it is dangerous rather than merely weak: a lock instantiated fresh inside the function body is a new, uncontended object on every call, so it provides the appearance of thread-safety while providing none of its substance. This is the identical defect `08-review.md`'s seeded `candidate_fix.py` carries. To become a tool at all (not yet the rule), the lock would need to be constructed once, outside the handler, and shared across every call — and even then it would need item 5's further correction to work across separate worker processes.
- **C** ("three months with no observed duplicate") is a false assurance: absence of an observed failure is not evidence a check exists, only that no input yet has exposed whatever behavior is currently present, safe or not.

**Banding:** *developing* — sorts B correctly but cannot explain why A is more dangerous than a merely-incomplete answer. *competent* — sorts all four correctly with a specific reason for each. *transfer-ready* — additionally explains why A is worse than C: A actively signals to a reviewer that the concurrency concern has been addressed, discouraging further scrutiny, in a way C's silence does not.

### Item 2 — property vs. mechanism for fail-closed

**Answer:** **B** states the property (C3). **A** is the closest mechanism (correct for the case it covers, but only as good as its own scope). **D** is a weaker mechanism (helps only for a *transient* failure, not a sustained one). **C** is a false assurance.

**Why each falls short, ranked:**
- **A** ("outer `try`/`except sqlite3.Error` returns `accepted: false`") is real evidence for half of C3 — it denies — but by itself says nothing about whether anything was *also* persisted somewhere on that same failure path; C3 needs both halves confirmed together, which is exactly what `test_store_unreachable_is_denied_not_accepted`'s second assertion (`share_count() == 0`) checks and a reviewer reading only "does it return false" would miss.
- **D** ("retry twice with backoff") addresses availability, not correctness: it changes how often the failure path is reached, not what the failure path does once reached, and a store that is down for longer than the backoff window still needs the fail-closed answer this statement never provides.
- **C** ("99.99% uptime SLA") is a false assurance for the same reason item 1's option C is: an SLA describes an expectation about frequency, not a guarantee about behavior during the (however rare) window when it is violated, and 0.01% of a high-traffic endpoint's calls is not a negligible number of opportunities for the forbidden outcome.

**Banding:** *developing* — picks B but treats A as fully sufficient without noting it only states half of C3. *competent* — picks B, correctly notes A covers only the "deny" half, and separates D (availability) from C3 (correctness under failure). *transfer-ready* — additionally explains why D is a common real-world distractor: retry-with-backoff is genuinely good practice, and being good practice for a *different* problem (transient availability) is exactly what makes it easy to mistake for evidence of a fail-closed guarantee it does not provide.

### Item 3 — a narrower failure path

**Answer:** Root cause (retry/race, C1/C2): the handler never checks whether `idempotency_key` has already been recorded, and the schema carries no `UNIQUE` constraint, so nothing about this variant differs from `vulnerable/app.py`'s missing-check defect for the sequential and concurrent cases. Precondition: any retry, or any two calls whose execution genuinely overlaps, carrying the same key. Impact: an unbounded number of duplicate rows, exactly as in `vulnerable/app.py`.

Root cause (store failure, C3): the `except` clause catches only `sqlite3.OperationalError`, not the broader `sqlite3.Error` hierarchy `vulnerable/app.py` and `fixed/app.py` both catch — a store failure that raises a *different* `sqlite3.Error` subtype (for example `sqlite3.DatabaseError` from a corrupted file, which is not an `OperationalError`) propagates as an unhandled exception rather than reaching either branch. Precondition: a storage failure whose exception class is not `OperationalError`. Impact: not fail-open in the `vulnerable/app.py` sense (it does not report `accepted: true`), but not fail-closed either in any controlled sense — an unhandled 500 gives the caller no documented `accepted: false` contract to check for, and a caller that only checks `response.json().get("accepted") is False` (as `fixed/app.py`'s own contract promises) may not even receive parseable JSON back.

**Banding:** *developing* — identifies the missing `UNIQUE` constraint but not the narrower `except` clause, or vice versa. *competent* — correctly names both defects as three distinct answers each (root cause, precondition, impact) rather than one restated description. *transfer-ready* — additionally notes that narrowing an `except` clause to "the one exception type I saw in testing" is a general anti-pattern this specific case illustrates: a handler tested only against a directory-not-found failure will reliably see `OperationalError`, and a reviewer who only reruns that same failure mode will never discover the gap.

### Item 5 — a mechanism choice under a deployment constraint

**Answer:** Engineer B's proposal (the `UNIQUE` constraint) should be chosen. Engineer A's proposal fails the stated constraint even if implemented correctly — a module-level lock shared across every call within one process still only serializes threads *inside that one process's memory space*; it does nothing for a second, third, or fourth `uvicorn` worker process, each with its own separate Python interpreter and its own separate lock object, since an OS-level process has no visibility into another process's in-memory objects at all. Four workers means four independent locks, each uncontended by the other three — the same practical outcome as `candidate_fix.py`'s per-call lock, for a different reason (per-process instead of per-call). Engineer B's constraint is enforced by the database engine, which every one of the four worker processes connects to as a genuinely shared, external resource, so the serialization holds regardless of how many application processes are racing it.

**Banding:** *developing* — picks B without explaining why a correctly-shared lock still fails, or conflates this failure with `candidate_fix.py`'s per-call defect without distinguishing "not shared within a process" from "not shared across processes." *competent* — correctly explains that a lock's scope is bounded by one process's memory and names the database as the one resource every worker process actually shares. *transfer-ready* — additionally states that this reasoning generalizes past `threading.Lock` to any in-process synchronization primitive (a semaphore, an in-memory cache used as a mutex) — the failure is process-boundary, not the specific primitive chosen.

### Item 6 — a count-bounded resource under a constraint

**Answer:** Engineer A's `UNIQUE` constraint on `(note_id, invite_id)` answers "does this specific patient-and-slot pair already exist," which correctly stops the *same* invite from being recorded twice — but it says nothing about whether a *sixth, distinct* invite should be admitted once five already exist, because uniqueness is an existence question about one row's own value, not a question about how many other, different rows already exist. A sixth invite with a new, never-seen `invite_id` inserts without violating any uniqueness constraint at all, exactly the way `07-transfer.md` traces for the clinic's last slot. The cap needs Engineer B's mechanism — a maintained count, checked and incremented as one atomic operation under serializable isolation (or an equivalent database check constraint against a maintained counter) — because "fewer than five already pending" is a question about the current size of a set, which no single column's uniqueness constraint can express.

**Banding:** *developing* — states that Engineer A's fix is wrong without naming the specific question a uniqueness constraint answers versus the question a cap needs answered. *competent* — correctly distinguishes "does this exact value exist" from "how many distinct values already exist," and identifies that Engineer B's mechanism is required. *transfer-ready* — additionally connects this back to C4's own limit as stated in `spec.md` and traces a concrete two-request race the way item 7 and `07-transfer.md` do for the clinic slot, rather than only restating the distinction abstractly.

### Item 7 — the clinic's last appointment slot

**Answer:** `07-transfer.md` names C1 and C3 as surviving the change unchanged (C1: the uniqueness question about one patient's own retry is unaffected by how many other patients exist; C3: fail-closed is a property of the system's response to its own uncertainty, independent of which resource is at stake) and C4 as breaking (a bare `UNIQUE` constraint on the slot column cannot distinguish "the first booking for this slot" from "a second, over-capacity booking," because it would reject the *first* patient's own retry-with-a-different-key attempt too, once any row for that slot exists).

Tracing the naive count-check: patient A's `SELECT COUNT(*) WHERE slot=S9` returns 0 (cap is 1) and proceeds; patient B's identical `SELECT COUNT(*)` also returns 0, because it runs before patient A's `INSERT` has committed; patient A's `INSERT` succeeds, now 1 booked; patient B's `INSERT` succeeds too, because nothing at the column level stops a second row for a different, still-unique row identifier — now 2 booked against a cap of 1. The resulting row count is **2**, not 1, and no plain `UNIQUE` constraint on the slot column would have prevented this specific pair (it would have prevented a *third* attempt, once two rows already existed for that slot, but the second one is what breaks the cap).

**Banding:** *developing* — states that C4 breaks and the others survive without tracing the two-patient race concretely, or gets the row count wrong. *competent* — correctly traces the race to a row count of 2 and names the uniqueness-vs-capacity distinction. *transfer-ready* — additionally explains why a bare `UNIQUE` constraint on the slot column is not simply "not enough" but actively cannot express the cap question at all — it answers a different question, one that happens to coincide with the right answer only when the cap is exactly one and no legitimate second row of any kind is ever expected.

### Item 8 — the replay signal and its residual

**Answer:** `share_replay reason=concurrent_race note_id=<id> key_id=sha256:<hash of the raced key> winner_share_id=<id> actor=<id> request_id=<id>` for each of the seven callers told `replayed: true`; `key_id` is a hash, never the raw idempotency key, and the line carries no note content. This signal cannot detect a worker redelivering a share job after revocation because that failure produces **no replay event at all** from this module's point of view: the redelivered job carries the same key it always carried, the row for that key already exists exactly once (correctly, by this module's own guarantee), and the handler correctly returns the existing row rather than inserting a new one — there is nothing here that looks anomalous to a system watching only for duplicate-key events, because the row count invariant this module tests and this signal monitors is, in fact, still satisfied. The problem in that scenario is not a row-count violation; it is that the *authority* behind an already-correctly-deduplicated key has since changed, which is a fact this signal was never designed to observe and C5 names explicitly as the residual this module does not close.

**Banding:** *developing* — writes a plausible signal but does not explain why it cannot see the redelivery-after-revocation case, or claims the signal "would probably catch it eventually." *competent* — writes a correctly-shaped signal (hashed key, no raw key or note content, a reason field) and correctly states that the redelivery case produces no anomalous row count. *transfer-ready* — additionally explains the general principle this illustrates: a detection signal built around one invariant (row count) is structurally blind to a failure of a *different* invariant (authority validity) even when both failures involve "the same request arriving more than once," and states that closing C5 needs a mechanism that checks authority at the time of *use*, not at the time of *dedup*.
