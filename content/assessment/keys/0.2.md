# Examiner notes — 0.2 (not learner-facing)

## Property

A diagnostic score, however high, cannot satisfy Gate 1's evidence requirement (C1). A tooling-bridge skip may be granted only by the diagnostic's own observed gap evidence, never by a job title, vendor certification, or LMS badge (C2). Modules 1.2, 1.3, and 1.4 are a fixed required set that no score, fast-track flag, or bridge assignment may shrink (C3). The NICE Secure Systems Development work role is informative placement vocabulary, not this course's syllabus or Gate 1 evidence (C4). A signal proving a skip was denied must identify the learner and module without carrying the diagnostic's item text, answer content, or a badge image (C5). Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

Standards anchors, live-checked on 2026-09-18: NIST SP 800-181 Rev. 1 (final, `csrc.nist.gov/pubs/sp/800/181/r1/final`) — "Secure Systems Development" is a NICE **work role** (Design and Development category), not a "competency" (C4). NIST CSF 2.0 (final) `GV` as outcome-taxonomy vocabulary only. WCAG 2.2 (final) SC 1.4.1 Use of Color (Level A), quoted exactly in `lessons/01-property.md`'s Standards line.

## Seeded review — intended findings

`lessons/08-review.md` hands the learner `vulnerable/diagnostic.py` as a PR described as adding "tooling-bridge credential support and fast-track routing," with a four-question checklist rather than a stated answer. Applied to the file as it stands:

1. **What would falsify the "hasn't changed" claim about `quiz_score_grants_phase1_skip`?** `quiz_score_grants_phase1_skip(100)` returns `True`, not `False` — the function has always had this defect in this file; "hasn't changed" is true about its age and irrelevant to whether it is correct.
2. **What does `tooling_bridge_required` actually check, versus "credentials count toward the decision"?** It checks `job_title`, `vendor_cert`, and `lms_badge` *before* `diagnostic_gap`, and returns `False` immediately if any is truthy — a credential does not add weight to a decision that still consults the diagnostic; it replaces the decision outright, skipping the diagnostic's own field entirely on that path.
3. **A disagreement, with concrete inputs.** `tooling_bridge_required({"job_title": "Senior Engineer", "diagnostic_gap": True})` returns `False` on this file, despite the diagnostic itself having recorded a real gap.
4. **The requested change and the test that proves it.** Remove the credential short-circuit entirely; read only `diagnostic_gap`. The test that fails today and passes after the change is `test_tooling_bridge_forbidden_outcome_job_title_does_not_override_a_real_gap`.

**The non-issue.** `gaps = tooling_gaps or {}` inside `phase1_modules_for_learner` is not a finding. It feeds only `bridge`, an additive evidence-gated set that this file computes correctly; `required` is untouched by this line. A learner who flags it as a defect, on pattern-similarity to `tooling_bridge_required`'s missing-key problem, without tracing which set it actually feeds, has over-applied a real lesson to a line it does not describe. Banding treats correctly recognizing this as a non-issue as part of *competent*, not merely a bonus.

A learner who reports all four answers, specifically names the credential short-circuit as the finding (not "the function reads several fields," which is true but not itself a defect), and correctly clears the `tooling_gaps or {}` line has passed this review.

**Transfer submission** (`lessons/08-review.md` §Use it somewhere new — a clinic hiring-diagnostic PR claiming a vendor certification "should reasonably count toward" skipping a threat-model review): the correct finding is that "should reasonably count toward" is not itself evidence for C2, using the same four-question checklist. Banding: *developing* answers accept "should reasonably count toward" as sufficient description; *competent* answers trace which return path the credential takes and find the same short-circuit shape; *transfer-ready* answers additionally name why "reasonably" is doing the persuasive work in the sentence — it invites the reviewer to substitute a plausibility judgment for a traced code path, exactly as item 1's false-assurance option does.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **A** is the rule. **B** and **D** are tools. **C** is a false assurance.

**Why each is categorized this way:**
- **D** ("deny specifically when `score == 100`") is a tool: a denylist of the one value this module's own example uses, checked and then falling through to the old logic for every other score — real in the narrow sense that it blocks that one input, but far narrower than the rule, since a caller supplying 99 or 101 is untouched by it.
- **B** ("a banner above 90%, plus a manager approval click") is a tool that adds a real gate (a human click) but still keys the *offer* of a skip to a score threshold, and the description does not establish that the manager's approval is itself evidence of anything C1 requires — it is a narrower, human-gated mechanism, not the rule.
- **C** ("our LMS already tracks completion percentage... so Gate 1 is effectively tracked too") is a false assurance: it treats a percentage as interchangeable with the reviewed artifact Gate 1 requires, which is this module's central refuted claim, restated as though it were a fact about the LMS's capabilities rather than a category error.

**Banding:** *developing* — sorts A correctly but cannot explain why C is false rather than merely weak. *competent* — sorts all four correctly with at least one specific reason each. *transfer-ready* — additionally explains why C is more dangerous than B or D: it suggests Gate 1 is already handled, discouraging anyone from building the actual reviewed-evidence process at all.

### Item 2 — property vs. mechanism for tooling-bridge evidence

**Answer:** **A** states the property (C2). **B**, **C**, and **D** are mechanism or proxy claims, ranked C (closest to real evidence) > B (weaker, self-reported) > D (weakest, unverifiable).

**Why each falls short, ranked:**
- **C** ("a vendor certification, passed last year") is the closest of the three to real evidence — a different organization did apply some assessment standard — but it is still not *this diagnostic's* observation, and its standard is unknown and unaudited by this course, which is exactly [Claim 2](../../modules/0/0.2/lessons/02-model.md)'s objection.
- **B** ("five years on a resume") is weaker: a self-reported duration is not evidence of current capability at all, only of exposure, and exposure without a diagnostic result is silent on whether a gap remains.
- **D** ("a manager vouches privately") is weakest: it is unverifiable hearsay with no assessment standard behind it at all, and accepting it would make the bridge decision depend on who happens to have a manager willing to send a message, which is not diagnostic evidence by any definition.

**Banding:** *developing* — picks A but cannot rank B/C/D. *competent* — picks A and correctly explains why C (the strongest-looking distractor) still fails. *transfer-ready* — additionally states the general principle: a proxy's *quality* does not change its *category* — even a highly reliable credential from a different authority is still not this diagnostic's own observation, so ranking B/C/D is about how tempting each is, not about how close any of them actually comes to satisfying C2.

### Item 3 — a third implementation's gap

**Answer:** Root cause: the function treats "no `diagnostic_gap` key present" and "a genuine diagnosed absence of a gap" as the same signal only when a credential field happens to be present — for `evidence = {"vendor_cert": True}`, the first branch is skipped (the key is genuinely absent, so `.get(...) is not None` is `False`), and the second branch then lets `vendor_cert` alone determine the answer. Precondition: any evidence record where no diagnostic ever ran (`diagnostic_gap` absent) but at least one credential field is present. Impact: `tooling_bridge_required` returns `False` — bridge waived — for a learner the diagnostic never actually assessed, based solely on a credential claim, reproducing C2's forbidden outcome through a narrower door than the original vulnerable file's.

**Banding:** *developing* — identifies that this function is still wrong without tracing the specific input through it. *competent* — correctly traces the two-branch structure and names the missing-key-plus-credential combination as the trigger. *transfer-ready* — additionally explains why this variant is a more dangerous fake than the original vulnerable file: it looks like a fix (it does read `diagnostic_gap` first, and does fail safe to `True` when *no* credential field is present), which makes it more likely to survive a rushed review than a version with no `diagnostic_gap` handling at all.

### Item 4 — reading a candidate fix

**Answer:** For `quiz_score=95, fast_track=True`: `fast_track and quiz_score >= 90` evaluates `True and True`, which is `True`, so `required.discard("1.4")` executes. The returned `required` set is `{"1.2", "1.3"}` — it does **not** contain `"1.4"`. The "both together" condition is stricter than either alone, which makes it harder to trigger by accident, but it is not a structural fix: it is a narrower version of the identical defect, still gated by `quiz_score` and `fast_track`, just requiring both instead of either.

**Banding:** *developing* — says the fix works because "it requires more conditions now," without tracing the specific input. *competent* — correctly traces the boolean `and` and concludes `"1.4"` is still absent for this input. *transfer-ready* — additionally states the general pattern: narrowing a forbidden condition (from `or` to `and`, or by adding a second gate) reduces how often a bug fires without removing the bug, and a test suite that only tries values on one side of the new, narrower gate would call this fix's forbidden-outcome case a pass.

### Item 5 — staleness vs. a different authority, under a constraint

**Answer:** Option A should be chosen. Option A's 30-day-old result is still an observation *this diagnostic* made — the constraint ("traceable back to an observation this diagnostic made") is satisfied by construction, and staleness is a real but different concern (the skill might have regressed, or been newly acquired, in the intervening 30 days) that a re-run policy can manage without touching C2 at all. Option B fails the stated constraint directly: a different course's instructor, however credible, is a different authority making a different observation under evidence standards this diagnostic did not set — exactly the shape [Claim 2](../../modules/0/0.2/lessons/02-model.md) forbids, only with a person's name attached instead of a vendor's. Where Option A stops working: if the interval is long enough that the underlying skill plausibly changed (a tool's interface changed, or the learner has not touched Git since), 30 days stops being a reasonable proxy for "still true today," and the honest fix is shortening the interval or re-running the probe, not accepting a longer-lived stale result.

**Banding:** *developing* — picks A without addressing why B fails the stated constraint specifically. *competent* — explains why A satisfies "traceable to this diagnostic's own observation" and B does not. *transfer-ready* — additionally names a concrete condition under which even Option A's staleness becomes unacceptable, rather than treating 30 days as safe by assumption.

### Item 6 — a label under a constraint

**Answer:** Option A satisfies the constraint; Option B does not, as written. Option A's label states exactly what was observed and when, which a reader can check against the diagnostic's own record. Option B's label implies a broader claim — that this learner satisfies an entire NICE work role — from evidence that only ever diagnosed one narrow tooling gap; nothing in this module's diagnostic evidences the full scope of "Secure Systems Development" as NICE itself describes it. For Option B to become acceptable, it would need to either name the specific diagnosed gap it is standing in for (converging on Option A) or be removed entirely as a completion label and kept only as internal vocabulary for choosing which bridge unit to assign, per [Claim 4](../../modules/0/0.2/lessons/02-model.md).

**Banding:** *developing* — picks A without explaining what Option B would need to change to become acceptable. *competent* — correctly identifies the scope mismatch (one diagnosed gap versus an entire work role) and states at least one path to making B acceptable. *transfer-ready* — additionally connects this to C1's original error: a broad label standing in for narrow evidence is the same shape as a score standing in for an authority map, just at the level of what a summary display claims rather than what a skip function grants.

### Item 7 — the clinic's onboarding quiz and the vendor certificate

**Answer:** C1, C2, and C3 transfer with only the subject-matter nouns changed — the quiz's topic (secure coding basics instead of tooling placement) and the required-review set (the clinic's architecture threat-model review and data-handling walkthrough instead of modules 1.2–1.4) — while the underlying evidence-source reasoning is identical in each case. **C4 needs its standard reference swapped**: this course cites the NICE Secure Systems Development work role; the clinic's analogous error would more plausibly cite a cloud-security vendor's own certification scope, or an unrelated hiring framework, as though it defined what the clinic's own review checks. The clinic's forbidden outcome, parallel in shape to this module's: a 92% internal quiz score, or a vendor's cloud-security certification, being read as authorization to skip the architecture threat-model review before the new hire gets production database access holding patient contact information.

**Banding:** *developing* — restates "the same rules apply" without substituting the specific nouns for at least C1–C3. *competent* — correctly substitutes nouns for C1–C3 and states the clinic's forbidden outcome in parallel form. *transfer-ready* — additionally identifies C4's standard swap specifically, rather than treating C4 as transferring unchanged like C1–C3.

### Item 8 — the skip-denial signal

**Answer:** `phase1_skip_denied learner_id=<id> module_requested=<id> basis=credential timestamp=<ts>`. The `basis=credential` field distinguishes this from a score-based or required-set attempt, which matters operationally because a spike concentrated in credential-based attempts points at a hiring process leaning on this diagnostic in a way it should not, while a spike in score-based attempts points at the diagnostic UI itself. The deliberately omitted field is the credential's own content — the job title text, the certification's image, or any quoted claim — because none of it changes whether the deny fired correctly, and logging it pastes an unverified, potentially identifying claim into a governance record that was never scoped to hold it. The recipient is whoever owns the cohort export and the diagnostic's configuration, not the learner's manager and not a public dashboard, either of which would turn a governance signal into a performance one. The threshold: a single occurrence for one learner is the system working as intended (a hurried attempt, correctly denied); a spike across many learners in a short window is what should trigger a review of who is coaching the attempts and why.

**Banding:** *developing* — writes a signal without a `basis` field, or includes the credential's own content. *competent* — writes a signal with a basis/reason field, correctly excludes the credential content, and names a plausible recipient. *transfer-ready* — additionally states the specific operational distinction a `basis` field enables (credential-pattern spike vs. score-pattern spike implying different root causes) rather than only naming that a reason field exists.
