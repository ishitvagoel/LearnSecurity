# Examiner notes — 2.3 (not learner-facing)

## Property

For SecureCollab's `sc_session` cookie and `/notes` endpoint: page script in the origin cannot read the session value once `HttpOnly` is set (browser-enforced); a cross-origin, credentialed caller cannot get a readable answer from `/notes` unless its exact origin was checked against a fixed allow-list first (server decides, browser enforces the resulting grant); and `Content-Security-Policy-Report-Only` never blocks anything, however clean its reports look. Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

ASVS anchors: `v5.0.0-3.3.4` (HttpOnly for session tokens), `v5.0.0-3.3.1` (Secure), `v5.0.0-3.4.2` (CORS `Access-Control-Allow-Origin` fixed or allow-list-validated), `v5.0.0-3.4.3` (enforcing CSP with `object-src 'none'`/`base-uri 'none'` as the floor), `v5.0.0-3.4.6` (`frame-ancestors`). `v5.0.0-3.3.2` (SameSite) is a related purpose control, not this lab's oracle.

## Lab

- `labs/2.3/2.3-browser-policy/vulnerable/` must fail 6 of 9 tests: `test_forbidden_outcome_session_cookie_missing_httponly`, `test_secure_attribute_is_also_present`, `test_forbidden_outcome_attacker_origin_gets_no_credentialed_access`, `test_origin_vs_site_boundary_subdomain_scheme_and_port_are_each_denied`, `test_anti_fake_lookalike_domain_is_not_treated_as_the_trusted_origin`, `test_csp_is_enforced_not_only_reported`.
- `labs/2.3/2.3-browser-policy/fixed/` must pass all 9.
- Root cause: two independent defects. (1) `login` calls `set_cookie` with none of `httponly`/`secure`/`samesite` set. (2) `notes`'s CORS branch is `if origin:` — it reflects any `Origin` header value with no comparison against a trusted set at all — paired with `Content-Security-Policy-Report-Only` standing in for an enforcing `Content-Security-Policy` that was never sent.
- Anti-fake test (`test_anti_fake_lookalike_domain_is_not_treated_as_the_trusted_origin`) uses `https://evilsecurecollab.example`, a domain sharing no dot-delimited label with `securecollab.example` but containing it as a trailing substring. Verified against an actual constructed fake: a "fixed" `notes` handler using `origin.endswith("securecollab.example")` (no leading dot) instead of exact `frozenset` membership passes 6 of 9 tests — it defeats the plain reflected-origin case — but fails exactly this anti-fake test and `test_origin_vs_site_boundary_subdomain_scheme_and_port_are_each_denied`, because the same unanchored suffix check also wrongly trusts `https://evil.securecollab.example`, a real but unauthorized sibling subdomain the boundary test separately exercises. This confirms the two tests catch two overlapping but distinct shapes of the same underlying mistake (bare substring vs. dot-anchored-suffix), not one shape twice.
- A second latent lab bug was found and fixed during this pass's own independent verification: the original `test_forbidden_outcome_session_cookie_missing_httponly`/`test_secure_attribute_is_also_present` read the raw `Set-Cookie` header with `"httponly" in set_cookie.lower()` / `"secure" in set_cookie.lower()`. Both are substring searches over the *whole* header, including the cookie's value, so `response.set_cookie("sc_session", "tok-HttpOnly-Secure")` — a call that sets neither flag — satisfied both tests. Verified directly: constructing that exact fake and running it against the original tests passed both. The tests now parse the header into its `;`-delimited attribute tokens (excluding the leading `name=value` pair) before checking, and `test_anti_fake_httponly_text_inside_the_cookie_value_does_not_count` pins the parsing helper down so a regression to a raw substring search would be caught here even before touching `app.py`.

## Seeded review — intended findings

`lessons/08-review.md` hands the learner `vulnerable/SECURITY.md` and `vulnerable/app.py`, with a falsifiability question rather than a stated answer. Applied to the files as they stand, the five bullets resolve as:

1. **"The web client mirrors `sc_session` into `document.cookie`... for a second tab."** Inaccurate as a security claim, and actively self-defeating: this design choice, if implemented, would itself require the cookie to be script-readable, directly contradicting bullet 2's claim that the cookie is `HttpOnly`. It is also not implemented anywhere in `vulnerable/app.py`, which contains no client-side script at all — the bullet describes a client the repository does not contain.
2. **"Because `sc_session` is `HttpOnly`, ... safe by construction."** Inaccurate on two levels: `login` does not set `httponly=True` (falsifiable by reading the one line that sets the cookie), and even if it did, `HttpOnly` denying one reader (page script via `document.cookie`) is not the same claim as "stored or reflected XSS cannot be used to steal a session" — XSS can still call `/notes` as the signed-in member without ever reading the cookie's value. This is the module's C1 misconception, seeded verbatim.
3. **"CORS on /notes reflects the caller's Origin with credentials enabled on purpose... mobile team's staging builds."** Inaccurate: `notes`'s CORS branch (`if origin: ... response.headers[...] = origin`) contains no reference to a mobile team, no staging allow-list, and no comment marking a deliberate trade-off — it unconditionally grants every caller the identical credentialed access. This is a plausible-sounding justification invented for code that never made the trade-off it describes; see the worked example in `lessons/08-review.md`.
4. **"Content-Security-Policy-Report-Only is deployed and is actively blocking... CSP is on."** Inaccurate and internally contradictory: Report-Only headers never block anything by definition; "actively blocking" describes the enforcing header's behavior, not the one actually sent. This is the module's C4 misconception, seeded verbatim.
5. **"Secure is not yet set on sc_session; tracked separately as low-priority..."** Accurate as far as it goes — `login` genuinely omits `secure` — but the "low-priority" judgment is worth challenging given `HttpOnly` is also missing on the same cookie; this is the module's intended example of an accurate-but-incomplete claim, distinct from the four false ones above (see the Counterexample section of `lessons/08-review.md`).

A learner who correctly labels bullets 1–4 as false (not merely "concerning") and bullet 5 as accurate-but-worth-challenging, with the specific code line supporting each label, has passed this review. A learner who labels all five as uniformly "bad" without distinguishing bullet 5's different shape has not yet met the bar the Counterexample section sets.

**Transfer submission** (`lessons/07-transfer.md`, WebView bridge): the correct finding is that `HttpOnly` is enforced by the *browser's* cookie jar specifically, and a WebView bridge is code the mobile team wrote running in a different execution context — nothing about verifying the browser tab's `HttpOnly` behavior constrains whether a bridge method exposes the same cookie value to injected JavaScript inside the WebView. Banding: *developing* asserts the bridge "inherits" the browser's cookie protection without argument; *competent* correctly states the bridge is a separate reader requiring its own check; *transfer-ready* additionally identifies the specific mechanism (a bridge method calling `document.cookie` or an equivalent native API from inside the WebView's JS context, bypassing the browser tab's own script sandbox) by which the original defect recurs.

## Item answers, distractor rationales, and banding

### Item 1 — guarantee, detection signal, or false assurance

**Answer:** **A** and **D** are guarantees. **B** is a false assurance. **C** is a false assurance (a guarantee is claimed — "that's fine" — resting on a mechanism, the session cookie requirement, that the same statement's own first clause already defeats).

**Why each is categorized this way:**
- **A** is a guarantee: `HttpOnly` really is browser-enforced, and the statement correctly attributes enforcement to the browser's cookie jar rather than to application code.
- **B** is a false assurance: "report volume has been zero for three months" is evidence about report delivery or policy permissiveness, not about whether anything is being blocked; a Report-Only header cannot block regardless of report volume, and "effectively on" asserts a property Report-Only structurally cannot provide.
- **C** is a false assurance: it correctly identifies the mechanism (session cookie requirement) but ignores that the same paragraph's CORS misconfiguration is precisely what lets a cross-origin caller's request carry that exact cookie automatically — the "but that's fine because" clause treats an independent defense as intact when the sentence right before it just described breaking it.
- **D** is a guarantee: an enforcing `Content-Security-Policy` with a real allow-list floor is browser-enforced exactly as described.

**Banding:** *developing* — sorts A and D correctly but cannot explain why C is false rather than merely incomplete. *competent* — sorts all four correctly with a specific reason each. *transfer-ready* — additionally explains why C is the more dangerous distractor of the two false ones: B's error is visible to anyone who knows what Report-Only means, while C's error requires connecting two clauses of the same sentence to each other, which a skimming reviewer is less likely to do.

### Item 2 — property vs. mechanism for the CORS grant

**Answer:** **D** states the property. **A**, **B**, and **C** are mechanism or proxy claims, ranked C (closest to real evidence) > A > B (furthest).

**Why each falls short, ranked:**
- **C** is closest to evidence: it is a claim about *this specific* implementation's actual behavior (exact set membership, no CORS header when absent), verifiable by reading the code. It still describes one implementation's mechanism rather than the general requirement that mechanism exists to satisfy.
- **A** is weaker: "validate that Origin is present" checks for the header's existence, not its value against anything — it would be satisfied by the vulnerable fixture's own `if origin:` branch, which this module's Lesson 03 shows grants everyone.
- **B** is weakest: absence of an unrecognized-origin observation in staging traffic says nothing about whether a check exists; a system with no check at all produces the identical absence of surprising log lines as a system with a correct one, until an attacker actually tries a new origin.

**Banding:** *developing* — picks D but cannot rank A/B/C. *competent* — picks D and separates C (implementation evidence) from A and B (weaker proxies). *transfer-ready* — explains that A is a specific, named trap: it is nearly the literal vulnerable-fixture condition (`if origin:`) restated as though it were a security check, which is exactly the mistake Lesson 03 traces line by line.

### Item 3 — a different checker's gap

**Answer, `https://evilsecurecollab.example`:** Root cause: `endswith(ALLOWED_SUFFIX)` is a bare-substring suffix test with no delimiter requirement, so any string ending in the literal characters `securecollab.example` passes, including one with no shared dot-delimited label at all. Precondition: an attacker registers any domain name ending in that literal character sequence — no relationship to the real `securecollab.example` domain is required. Impact: `is_trusted` returns `True`, granting this attacker-registered, entirely unrelated domain the same credentialed access as the real SecureCollab app.

**Answer, `https://evil.securecollab.example`:** Root cause: the same `endswith` call also accepts a genuine subdomain of the real registrable domain, because it does not require a leading-dot boundary to distinguish "is a subdomain of" from "merely ends with the same characters." Precondition: an attacker controls, or has compromised, any subdomain of `securecollab.example` that the security team did not intend to trust with this access — a materially more realistic precondition than the first case, since it does not require tricking anyone into visiting a lookalike domain at all. Impact: a legitimately-provisioned but lower-trust subdomain (a staging environment, a third-party-managed support portal) silently gains the same credentialed access as the first-party app.

**Banding:** *developing* — identifies that the function is wrong for one of the two origins without tracing both. *competent* — correctly traces both origins to the same `endswith` mechanism with two distinct preconditions. *transfer-ready* — additionally states that a dot-anchored version (`endswith(".securecollab.example")`) would close the first gap but not the second, since the second origin is a genuine subdomain regardless of the leading dot.

### Item 4 — reading a candidate fix

**Answer:** It does **not** pass. The call is missing `secure=True`; FastAPI/Starlette's `set_cookie` defaults `secure` to `False` when the keyword is omitted, so the resulting `Set-Cookie` header carries `HttpOnly` but no `Secure` attribute, and `"secure" in set_cookie.lower()` is false. The specific unprotected behavior: the browser may still send `sc_session` over an unencrypted HTTP connection if one is ever reached (a downgrade, a misconfigured redirect, a captive portal), exposing the value to network interception — a threat `HttpOnly` does not address at all, since `HttpOnly` and `Secure` are independent flags enforced by independent browser checks, exactly as `lessons/01-property.md`'s rejected-alternatives section states.

**Banding:** *developing* — says it passes, or says it fails but cites the wrong missing argument (for example, `samesite`). *competent* — correctly names `secure=True` as missing and states the general risk (plaintext transmission). *transfer-ready* — additionally explains why this specific omission is independent of `HttpOnly`, rather than a lesser version of the same protection.

### Item 5 — two candidate origin checks under a constraint

**Answer:** Engineer A's fix (`origin in ALLOWED_ORIGINS`, a literal `frozenset`) should be chosen. Engineer B's proposal fails the stated constraint directly: `.endswith(".securecollab.example")` would automatically grant every future subdomain, including a compromised or unreviewed one, which is precisely the risk the constraint names as realistic — "automatic coverage" and "no unreviewed grant" are in direct tension for this threat model. Engineer A's fix requires an explicit one-line addition to `ALLOWED_ORIGINS` for every new legitimate origin, which is the cost of the safer design, not a flaw in it. Where Engineer A's fix still falls short: it protects the exact-origin comparison correctly, but it does not itself prevent a *compromised* origin that is already on the list (for example, if `app.securecollab.example` itself were compromised) from abusing its own legitimate CORS grant — that failure mode is outside what an origin allow-list, however precisely implemented, can address.

**Banding:** *developing* — picks A without addressing the constraint explicitly. *competent* — explains why B fails the stated constraint and A satisfies it. *transfer-ready* — additionally names the specific residual (a compromised already-listed origin) rather than claiming Engineer A's fix is a complete guarantee.

### Item 6 — CSP Report-Only as a rollout tool vs. a substitute

**Answer:** During the proposed quarter, Report-Only protects nothing: it asks the browser to send violation reports, but every load and execution the eventual enforcing policy would have blocked continues to happen exactly as it would with no CSP header at all. The plan's stated goal — "see what breaks before turning on the real thing" — is a legitimate use of Report-Only, but only as a *rehearsal run alongside* an already-enforcing baseline policy, not as the only header sent while the enforcing policy is deferred. A design that gets the same rollout-safety benefit without the gap: ship an enforcing `Content-Security-Policy` today, meeting ASVS's stated floor (`object-src 'none'`, `base-uri 'none'`), while separately running `Content-Security-Policy-Report-Only` with the *stricter*, not-yet-enforced candidate policy the team actually wants to test — the enforcing header protects the baseline the whole time, and the Report-Only header does the rehearsal work the plan wants, concurrently rather than sequentially.

**Banding:** *developing* — recommends delaying the enforcing header without naming what is unprotected in the meantime. *competent* — correctly states Report-Only blocks nothing and names the exposure window. *transfer-ready* — proposes the concurrent enforcing-baseline-plus-stricter-report-only design rather than only critiquing the original plan.

### Item 7 — clinic portal and WebView bridge

**Answer:** C1 (HttpOnly is browser-enforced, not an XSS guarantee), C2 (origin vs. site), C3 (credentials never pair with an unvalidated origin), and C4 (Report-Only is not enforcement) all transfer to the clinic patient-portal session cookie essentially unchanged — nothing about a healthcare context changes what a browser enforces or what a header means. C5 (a new reader needs its own row) is the claim that changes materially for the WebView bridge, and the reasoning must be causal, not by analogy: `HttpOnly` is enforced by the *browser's* cookie jar specifically refusing `document.cookie` a value to any script running in a page the jar is tracking. A WebView bridge is native code the mobile team wrote, exposed to the WebView's JavaScript context through whatever bridging mechanism the platform provides; if that bridge method itself calls `document.cookie` (or an equivalent native cookie-store API) and returns the value to JavaScript, it has created a second reader that the browser's `HttpOnly` enforcement was never positioned to prevent, because the enforcement lives in the browser's own script-execution sandbox, and the bridge method is not subject to that sandbox's cookie-access rules in the way ordinary page script is.

**Banding:** *developing* — states that the WebView "inherits" the browser's protection, or lists C5 as changing without explaining the mechanism. *competent* — correctly identifies the bridge as a separate reader requiring its own argued row, distinct from the browser tab's row. *transfer-ready* — additionally traces the specific mechanism (a bridge method calling a cookie-reading API from inside the WebView's JS context) by which C1's original defect recurs in a different runtime, matching `lessons/07-transfer.md`'s worked example.

### Item 8 — the CORS-misconfiguration signal

**Answer:** Must carry: the caller's `origin` value (public information, not a secret — it identifies who asked, not what they received), the `path` requested, whether credentials were requested, `env`, and a `request_id`. Must never carry: the session cookie's value, or any note body from the response. "We've seen this origin before and it looks benign" is not sufficient justification to skip rotation because "benign so far" describes observed history, not a guarantee about this specific exposure window — an origin can be legitimate-looking and still be a compromised account, a supply-chain-compromised third-party script running on an otherwise-trusted page, or simply the first observed instance of a new attack rather than evidence the origin is safe. The correct response scope is every session live during the window this misconfiguration was deployed, not only the sessions a log happened to retain a request from.

**Banding:** *developing* — includes the required fields but also includes a forbidden one, or accepts "looks benign" as sufficient without challenging it. *competent* — gets both field lists right and states rotation should proceed regardless of the origin's apparent reputation. *transfer-ready* — additionally names the specific reasoning error ("benign so far" conflates observed history with a guarantee about this exposure window) rather than simply asserting rotation is safer.

## Transfer (general note, applies to item 7)

Reject Top 10 / CWE / scanner language as the definition of security in any item's answer. Acceptable direction for original scenarios beyond the clinic/WebView sketch: any setting with a first-party browser context and a second, structurally different reader of the same credential (a desktop Electron wrapper, a browser extension's content script, a server-side proxy that forwards cookies).

## Operate (general note, applies to item 8)

Accept a detect/recover note that does not log the cookie value or note body. Reject "the origin has a good reputation, so we can skip rotation" as an acceptable trade-off in any answer.
