# Examiner notes — 1.4 (not learner-facing)

## Property

A high-impact recovery confirmation is a security control. If a legitimate user cannot complete it with keyboard, named controls, and a non-color cue, the control has failed (lockout or unsafe workaround). Residual risk is owned and dated, not a heat-map leftover. Coercion is residual, not deleted by CSS. Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

## Lab

- `labs/1.4/1.4-risk-register/vulnerable/` must fail 3 of 6 tests: `test_recovery_control_is_usable_and_accessible`, `test_missing_keyboard_flag_is_not_silently_accepted`, `test_whitespace_only_name_is_rejected`.
- `labs/1.4/1.4-risk-register/fixed/` must pass all 6.
- Root cause: designers trusted a pointer and a hue (psychological acceptability omitted); the checker's own logic compounded this by checking for the absence of the bad flag (`mouse_only`) instead of requiring positive evidence of the good guarantee (`keyboard`).
- Anti-fake pair (`test_checker_rejects_a_bad_control_regardless_of_variant`, `test_checker_accepts_a_good_control_regardless_of_variant`) calls the checker on constructed input independent of either module's factory. Verified: a hardcoded `return True` checker fails 4 of 6 tests; a hardcoded `return False` checker fails the module's own normal-case test. Neither fake passes the full suite.

## Seeded review — intended findings

`lessons/08-review.md` hands the learner a submission ("Improve recovery confirm accessibility": a red/green drag-to-confirm slider, plus a register update reading "users should be careful") and a four-question checklist, without stating which questions the submission fails. It should fail all four:

1. **Accessible name — fail.** "Drag-to-confirm slider" names an interaction, not an accessible name; nothing in the PR description adds a `name`/label a screen reader would announce.
2. **More than color alone — fail.** "Red/green" is stated as the *only* distinguishing signal in the PR description itself.
3. **Operable without a pointer — fail.** A drag gesture is a pointer interaction; it does not answer "operable without a pointer" in the affirmative, and Lesson 03/04 already established that drag-to-confirm is lockout in a new costume, not a fix.
4. **Register names harm + owner + trigger — fail.** "Users should be careful" is the exact fake-leftover phrasing Lesson 01 opens by rejecting; it has no owner and no trigger.

A learner who reports the submission as passing any of the four has not yet connected the module's rule to a submission's actual language rather than its confident tone.

**Transfer submission** (`lessons/08-review.md` §Use it somewhere new — "a quick continue button so clinicians can get back to the chart fast"): the correct finding is that the submission is **under-specified for a firm verdict**, not a repeat of the same four failures by assumption. "Quick continue button" does not by itself state whether the button has a name, whether it is color-distinguished from another action, or whether it is pointer-only — a competent answer says which of the four questions the PR description simply does not address, and asks for the actual object (the equivalent of `recovery_confirm_control()`'s return value) before passing or failing it. Banding: *developing* assumes it fails the same four ways without checking; *competent* correctly identifies that questions 1–3 are unanswered by the description as given and asks for the object; *transfer-ready* additionally checks the register-adjacent language ("get back to the chart fast" is friction-reduction language, which Lesson 01's two-effort model says is not itself the failure — the failure would be if that convenience shipped without preserving the who-is-allowed check, which this description also does not state either way).

## Item answers, distractor rationales, and banding

### Item 1 — residual risk vs. a filled-in table

**Answer:** Only **B** names a residual risk in this module's sense. It states a specific harm (coercion by a physically present person), names the mechanism by which it survives the fix (a usable UI does not remove physical control of the device), names an owner (product lead for identity), and names a revisit trigger (a new second factor or safe word).

**Why each distractor is attractive:**
- **A** ("users should be careful") is attractive because it uses the vocabulary of risk acceptance and sounds appropriately humble about a limit. It fails because it names no mechanism, no owner, and no trigger — it is indistinguishable from doing nothing.
- **C** ("we reduced residual risk by adding a CAPTCHA") is attractive because it describes concrete work being done. It fails because a CAPTCHA is a mechanism claim, not a residual-risk claim, and Lesson 01 explicitly names CAPTCHA as a control that "can shut people out the same way" a mouse-only button does — it may *increase* the lockout residual rather than reduce it.
- **D** ("scanner reports green") is attractive because it cites a concrete, checkable-sounding artifact. It fails because a scanner result is a proxy for a different, narrower claim than this module's rule, and Lesson 01 names "the scanner is green" in its very first paragraph as exactly the wrong kind of evidence.

**Banding:** *developing* — picks B but cannot say why A/C/D fail beyond "they're vague." *competent* — identifies B and gives at least two of the three specific reasons above. *transfer-ready* — additionally explains why C is the most dangerous distractor of the four (it looks like progress and may be regressive).

### Item 2 — property vs. mechanism for an accessibility fix

**Answer:** **D** states the property. **A**, **B**, and **C** are all mechanism or proxy claims, each falling short of D in a different, specific way.

**Why each distractor is attractive:**
- **A** ("we use an accessible component library") is attractive because a genuinely accessible library is a real, useful ingredient. It falls short because a library can produce an accessible piece and still be wired up wrong in this specific instance — the library does not know that *this* control is a security-sensitive recovery confirm, and nothing in the claim says the resulting object actually declares `keyboard` and a name.
- **B** ("scanner reports zero violations") is attractive because a scanner result is concrete and machine-checked, which sounds more rigorous than prose. It falls short for the same reason Item 1's distractor D does: a scanner checks a different, narrower thing than this module's rule, and Lesson 03's own checker shows a machine-checked predicate can itself have an undetected gap (the missing positive `keyboard` requirement).
- **C** (the actual declared object, with `is_usable_accessible` returning `True`) is the closest of the three to real evidence — it is a claim about *this specific* control, not a general claim about tooling. It still falls short of being the property itself: it is evidence that one object satisfies the rule today, not the rule that would let you evaluate a *different* object tomorrow without re-deriving it from scratch.

**Banding:** *developing* — picks D but cannot rank A/B/C by how close each comes to real evidence. *competent* — picks D and correctly separates A/B (tooling claims) from C (object-specific evidence). *transfer-ready* — additionally explains that C is evidence *for* the property on one instance, not a restatement of the property, and that this distinction is exactly what lets the property be checked again after the object changes (e.g., after a library upgrade).

### Item 3 — the checker's quiet gap

**Answer:** Root cause: the function checks for the presence of a disqualifying flag (`mouse_only`) rather than requiring the presence of a qualifying one (`keyboard`), so an object silent on keyboard support is treated as acceptable by default. Precondition: a control object that was never explicitly marked `mouse_only` but also never declared keyboard support (e.g., a partial migration, or a component that forgot to set the prop). Impact: a keyboard-only or screen-reader user cannot operate the control, and the checker gives no warning, because from the checker's point of view nothing is wrong.

**Distractor pattern (open-ended item — grade against the rubric, not a fixed list):** Answers that give only "it's missing a check" without identifying *which* check and *why* checking for absence-of-bad differs from presence-of-good should be banded developing. Answers that name the specific field (`keyboard`) but not the "absence vs. presence" distinction are competent. Answers that connect this to the general pattern (a check for a known-bad signal is not equivalent to a check for a known-good guarantee, and the same shape of bug appears in authorization code that checks "is this role denied" instead of "is this role explicitly granted") are transfer-ready.

### Item 4 — reading a "fixed" diff

**Answer:** It does **not** pass. The fixed checker requires `control.get("keyboard")` to be truthy; the diff never adds a `keyboard` key, so `not control.get("keyboard")` evaluates to `True` and the function returns `False`.

**Banding:** *developing* — says it passes (missed the missing `keyboard` key), or says it fails but cites the wrong reason (e.g., "color is still present," which is fine per the fixed checker). *competent* — correctly identifies it fails and cites the missing `keyboard` key. *transfer-ready* — additionally notes that a reviewer scanning only for the two flags named in the original bug report (`mouse_only`, `name`) would have approved this diff, which is the point of Lesson 08's worked example.

### Item 5 — friction theater vs. a convenience hole

**Answer:** This is a **convenience hole**, not friction theater — the proposal reduces user effort (fewer re-confirmations) without re-examining the who-is-allowed check, which now holds for 24 hours instead of 5 minutes. Precondition: the device or browser session is later used by someone other than the account owner (shared device, stolen laptop, a household member). Impact: the who-is-allowed decision, originally scoped to a short window right after authentication, now silently covers a 24-hour window it was never designed for — exactly the "lowering user work without preserving the who-is-allowed check" pattern Lesson 01 names.

**Common wrong answer:** Calling this "friction theater" (raising attacker work without measuring user work) inverts the direction of the proposed change — friction theater is about *adding* difficulty that doesn't help; this proposal *removes* difficulty in a way that doesn't check who benefits. Grade this confusion as developing; a competent answer gets the direction right, transfer-ready explains why the direction matters (each failure mode calls for the opposite fix).

### Item 6 — two candidate fixes

**Answer:** Engineer B's fix should be chosen. Engineer A's fix (`mouse_only: False` alone) fails the stated constraint: a checker that only inspects `mouse_only` cannot be verified independent of the object's own factory in a way that distinguishes "genuinely keyboard-operable" from "merely not flagged mouse-only" — see item 2's root cause. Engineer B's fix still falls short in one specific way worth naming: it verifies the *declared* shape of the object, not whether a real browser and screen reader actually honor that declaration in the shipped frontend — the gap named in Lesson 05's "what it still does not prove" section.

**Banding:** developing picks B without addressing the constraint; competent addresses the constraint explicitly; transfer-ready also names the residual gap between "declared" and "actually rendered."

### Item 7 — actors and the support-read-aloud row

**Answer (indicative, not exhaustive):** A defensible design adds a *checked* alternate path — for example, a time-boxed, logged, dual-control approval (two support staff, both actions independently recorded, neither able to unilaterally complete the recovery) — rather than a single support agent reading a code aloud on an unaudited voice channel. Residual named: this still requires trusting two support staff not to collude, and the audit log itself becomes a new asset requiring protection.

**Distractor pattern:** An answer that allows "support reads the code aloud, but we'll log that it happened" does not satisfy the constraint — logging that a bypass occurred is not the same as making the bypass independently auditable *before* it grants access, and it does not change the who-is-allowed decision at all. Band as developing. An answer that proposes dual control or an equivalent structural check is competent; one that also names the collusion residual is transfer-ready.

### Item 8 — the clinic and bank sketches

**Answer:** C2 (accessibility as a security property) and C5 (degrade paths inherit the same rules) transfer essentially unchanged — the mechanism is identical regardless of what is behind the gate. C1 (residual risk needs an owner and trigger) and C4 (actors by capability and motive) need reworded harm statements: the harm for a locked-out clinician is not "inconvenience," it is potential delay accessing time-sensitive patient information, and the actor table gains a new row (the next clinician on a shared workstation inheriting a confirmed session) that has no notes-app equivalent. C3 (effort trade-off) needs a reworded cost side: "user effort" for a clinician mid-shift is effort under a different, higher-stakes kind of time pressure than an individual recovering a personal account. The coercion residual (part of C1/C4) does not shrink because nothing about changing the protected object changes whether a person can be physically forced to press a button — the mechanism of coercion is independent of what is behind the control.

**Banding:** developing restates "the same rules apply" without identifying which claim needed rewording. competent names at least one claim needing rewording and gives the reworded harm statement. transfer-ready explains the coercion invariance in mechanism terms (physical presence is independent of the protected object), matching the success criteria stated in the item.

### Item 9 — the deny-line signal

**Answer:** Must carry: account id, control id, outcome (fail), and modality/reason (e.g., `not_keyboard_operable`). Must never carry: the recovery code itself, and the note body or any patient/customer content the account protects. Recipient: the on-call or product owner responsible for the identity/recovery journey (named as "product lead for identity" in Lesson 01/02's leftover table) — not a general application log with broad read access.

**Banding:** developing includes the required fields but also includes a forbidden one, or names a diffuse "the team" as recipient. competent gets both field lists right and names a specific-enough recipient role. transfer-ready explains *why* each forbidden field is forbidden (a code in the log is a standing credential sitting in a system many engineers can query; a note body in the log defeats the confidentiality property from an earlier module).

Acceptable direction for original scenarios beyond the two sketches above: any setting where a human confirmation gates a high-impact effect and where a shortcut or lockout has a named, specific harm.
