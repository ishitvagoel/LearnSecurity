# Examiner notes — 3.1 (not learner-facing)

## Property

Five teaching claims, named in `spec.md` §Teaching claims: (C1) classification is a per-field, per-sink rule with a named check and failure behavior, not a label; (C2) an asset inventory that omits authority artifacts is incomplete, and an authority artifact must be classified at least as sensitively as the content it gates; (C3) a security requirement names the sink, the allow/deny decision, and the failure behavior — a classification level alone is not a requirement; (C4) an unclassified field defaults to the most restrictive level, not the least, because every downstream sink already treats an unnamed field as unrestricted; (C5) a fix at one call site is not durable — pair it with a detection signal and a purge/rotation path.

ASVS anchors, live-fetched against the `v5.0.0` tag on 2026-09-26: `v5.0.0-14.1.1` (classify sensitive data into protection levels, C1/C2), `v5.0.0-14.1.2` (documented per-level protection requirements including how data is logged, C3), `v5.0.0-14.2.3` (sensitive data not sent to untrusted parties, e.g. trackers — the log-vendor/shared-observability reader, C1), `v5.0.0-14.2.4` (controls implemented as the protection-level documentation defines them, C3), `v5.0.0-16.1.1` (a logging inventory naming what is logged and who can access it, C5), `v5.0.0-16.2.5` (logging enforced by protection level, C1/C2). ## Item key

**1.** A = false assurance (a label with no sink check). B = mechanism, close to the rule if it is proven to run (the rule itself is the observable outcome: the body/token absent from a specific rendered line). C = false assurance (vendor certification says nothing about whether the sink's own code redacts a field). D = false assurance (a comment is not code any function executes). Banding: *developing* — calls the spreadsheet or the comment "a control" or misreads the vendor claim as evidence. *competent* — correctly sorts all four and names, for B, that the log line's own asserted absence of the string is the actual proof, not the existence of `_redact`. *transfer-ready* — additionally states that B is only the rule if a test proves the deny holds against a fresh value, tying the answer to C1 and to lesson 05's anti-fake reasoning.

**2.** D is the defect: "session token — not listed" leaves an authority artifact entirely off the inventory on the reasoning that it "isn't data the user typed," which mistakes the origin of a value for its power. A, B, C are correctly-shaped entries (right level, right sink). Banding: *developing* — treats the session token as low-priority because it has no readable content, or fails to name why possession (not content) is what matters. *competent* — correctly identifies D and states the possession-versus-content distinction from lesson 01. *transfer-ready* — additionally states that the session token should be classified *at least* as sensitively as the note body specifically because it grants broader access (read and write everything the token's owner could reach) than reading the note body's content alone.

**3.** Root cause: `.get(key, "internal")` treats any field this table has never named as Internal — the least restrictive level, not the most — so an unnamed field passes the `allowed_levels` check for any sink whose policy admits Internal (which is every sink in this fixture). Precondition: a field not present in `CLASSIFICATION` reaches this function at all — true whenever a schema gains a field before someone updates the table, which is the common case, not an edge case. Impact: `draft_billing_note`'s value (potentially real billing content) reaches the application log's rendered line in full, exactly as `vulnerable/app.py`'s failure did, via a different specific line of code. Banding: *developing* — identifies "the default is wrong" without naming the direction of the error (permissive vs. restrictive) or without separating the three answers. *competent* — all three answers correct and distinct. *transfer-ready* — additionally names that this is the identical class of failure as a hardcoded-key-pair fake (item 3 and the lab's own anti-fake test isolate the same underlying mistake from two different angles: a wrong default value vs. a table with an incomplete key set).

**4.** Root cause: `write_audit_export` never calls `_redact`; it appends `dict(context)` directly. Precondition: `note_read_handler` calls it whenever `note_id` is `"note_a"` or `"note_b"`, regardless of whether the context contains a Confidential field. Impact: whoever can read `_AUDIT_EXPORTS` — the compliance team by design, and anyone sharing that access — receives the unredacted note body and session token for those two notes. C1's per-sink framing predicts this: a correct `_redact` proves nothing about a function that never calls it, because the rule is "this sink's policy is enforced when this sink's code runs `_redact`," not "this codebase, once, somewhere, enforces classification." Banding: *developing* — says "the audit export leaks data" without naming the three answers separately, or claims the bug is in `_redact` itself. *competent* — all three answers correct, and the one-sentence tie-back to C1 present. *transfer-ready* — additionally connects this to C5: a detection signal on `application_log`'s redaction misses would never catch this, because `write_audit_export` never touches that sink's code path at all — a second, sink-specific signal is required.

**5.** Expected direction: argue for candidate B (the sink-level allow-list). Under the stated constraint — three new endpoints, three different engineers, none of whom have read this module — candidate A (strip fields at each handler) requires every one of those three engineers to independently remember the same strip-list, with no shared enforcement point; a single omission reproduces the original leak at a new address, and nothing in the codebase would catch it before it ships, because there is no test that watches "did every handler remember." Candidate B requires those same three engineers to route their new endpoint's output through the existing `log_event`/`write_error_dump` (or a new sink correctly registered in `SINK_POLICY`), which is a much smaller, more auditable surface, and it is the one this fixture already tests. A strong answer distinguishes this from claiming B is "just generally more secure" — it must tie the argument specifically to the three-new-endpoints-by-different-engineers constraint. Banding: *developing* — picks B without engaging the constraint, or picks A and defends it only by ease of implementation without addressing the multi-engineer risk. *competent* — argues for B and states specifically what A does under this constraint (repeats the maintenance burden per new call site). *transfer-ready* — additionally names the one place B's own guarantee still depends on human discipline (every new sink still has to be *registered* in `SINK_POLICY` and *called through* — B narrows the surface, it does not eliminate the need for a human decision entirely).

**6.** The widening is not, by itself, a defect — a compliance audit sink may have a genuine documented need to carry Confidential fields. The defect this item is testing for is procedural, not mechanical: C3 requires that a level-to-sink decision be a *documented, deliberate* choice, and a PR titled "fix: fully redact audit logs" that quietly widens a policy while fixing an unrelated bug has not surfaced that decision for separate review — the widening is buried inside a change whose title suggests it only restricts, not expands, what is logged. A strong answer states this precisely (the problem is that the decision is unnamed and unreviewed, not that widening is inherently wrong) and distinguishes it explicitly from item 4's separate, mechanical finding that `write_audit_export` does not even enforce the (possibly-justified) widened policy it declares. Banding: *developing* — calls the widening itself the bug, full stop, or conflates this with item 4's finding. *competent* — correctly separates "is the widening itself wrong" (no, not necessarily) from "was it surfaced as its own decision" (no), and ties the answer to C3. *transfer-ready* — additionally proposes what would make the widening acceptable (a named owner, a stated operational justification, and — separately — actually wiring `write_audit_export` through `_redact` so the policy is enforced rather than merely declared).

**7.** See `lessons/07-transfer.md`'s own success criteria, restated here with banding. The proposal violates C1 specifically: it replaces a per-field, per-sink decision with a per-record label, which either denies the appointment time from sinks that have a genuine documented need for Internal-level scheduling data (over-restriction, breaking a legitimate operational need) or — the more likely real-world failure — gets "worked around" by loosening enforcement for the whole record, which reintroduces exposure for the chart text as a side effect of accommodating the appointment time. Banding: *developing* — agrees whole-record classification is "simpler" without identifying either failure mode, or names only one of the two possible outcomes. *competent* — names C1 as the violated claim and correctly describes at least one of the two failure directions (over-restriction or loosened enforcement). *transfer-ready* — names both directions, explains why they are the same underlying mistake (conflating "the record contains something sensitive" with "every field on the record needs the same rule"), and connects it back to lesson 02's asset-inventory discipline of naming fields, not records.

**8.** Expected signals: `log_redaction_miss reason=confidential_field event=note_read sink=application_log level=confidential` and `log_redaction_miss reason=confidential_field event=note_read_error sink=error_dump level=confidential` — same shape, different `sink` value, as `lessons/06-operate.md` derives; neither line carries the denied value. Threshold reasoning: `application_log` fires on every successful read, so its baseline rate under normal traffic is high, meaning a sustained-rate threshold has to be set relative to that high baseline to avoid drowning in false positives from routine test/staging traffic; `error_dump` fires only on lookup failures, a much rarer event under healthy operation, so the same absolute miss count is a stronger signal there and can reasonably trip at a lower threshold. Setting both thresholds identically low risks paging on-call constantly for `application_log` misses that are statistically likely to be test artifacts (this module's own `test_unclassified_field_defaults_to_redacted` is exactly such an artifact, run on every test cycle), which trains the team to ignore the alert precisely where a genuine `error_dump` miss — the rarer, often more urgent signal — most needs attention. Banding: *developing* — writes one generic signal without differentiating `sink`, or asserts thresholds should simply be "high" without reasoning about baseline rate. *competent* — both signals correctly shaped and the baseline-rate argument present. *transfer-ready* — additionally connects the identical-threshold failure to alert fatigue as named in lesson 06's own residual-risk section (an ignored alert is operationally equivalent to no alert).

Worth a one-line comment recommending the default be removed to prevent a *future* silent misconfiguration, but not a blocking finding on this diff.

## Transfer

Reject Top 10 / CWE and "just mark the whole record Confidential" as substitutes for the field-level, per-sink derivation. Acceptable direction: chart text and appointment time as two fields, two levels, on one card, exactly parallel to note body and note id/company id. C5 is the one claim that does not transfer by direct analogy — it requires naming a retention obligation this fixture leaves open. WCAG 2.2 SC 1.4.1 (Use of Color) applies to a redaction-miss status badge, not to the classification decision itself.

## Operate

Accept detect/recover that never re-emits the denied value: `log_redaction_miss` naming `event`, `sink`, and `level`, never `value`. Reject a design that carries the denied value "so the alert is easier to verify." Recovery for the session token requires rotation in addition to purging the log line, because a token already read by an unintended party stays valid until revoked regardless of what happens to the log copy; recovery for the note body requires only a purge, because content carries no power of its own.
