## Causal anchors for the intended failures

### Cross-tenant direct read

- **Root cause:** any known identity is granted read authority; no current subject–object tenant relation is evaluated.
- **Preconditions:** Bob is a valid Tenant B user and Note A-1 exists.
- **Impact:** Tenant A note-body confidentiality fails.
- **Structural repair:** resolve active subject and stored note, require matching tenant for `note:read-body`, and enforce before returning fields.
- **Limit:** local in-memory service evidence does not prove HTTP, database, cache, export, or worker mediation.

### Aggregate listing

- **Root cause:** the aggregate path authorizes once by identity and releases all storage results; object and field cells are not mediated.
- **Impact:** cross-tenant identifiers/titles are disclosed; a whole-object serializer could disclose bodies.
- **Repair:** bind query/result projection to server-resolved authority and return only permitted summary fields.

### Cross-tenant admin delete

- **Root cause:** role expansion discards tenant and object scope, creating global ambient admin authority.
- **Impact:** cross-tenant integrity fails.
- **Repair:** current scoped admin membership plus stored object tenant and exact action; enforce before mutation and assert no partial state on denial.

### Revoked member

- **Root cause:** identity existence is treated as current authority; inactive membership state is ignored.
- **Impact:** revocation fails to remove read authority.
- **Repair:** separate authentication from current membership and define effect time across sessions/caches/grants. The fixture models immediate current-state lookup only.

### Unknown object

- **Root cause:** the vulnerable policy grants read authority before resolving whether the object exists. Its wrapper happens to return `None`, but the positive decision is still unsafe for any later path that creates, restores, aliases, or otherwise resolves that identifier.
- **Impact:** enforcement and policy evidence disagree; a missing object can conceal an unsupported allow cell.
- **Repair:** resolve the stored object at the trusted decision point and deny when it is absent, before any protected release.

### Unknown action

- **Root cause:** missing policy rule defaults to allow.
- **Impact:** new or misspelled effects inherit unintended authority.
- **Repair:** explicit positive action branches and terminal deny with stable evidence.

### Approval failures

- **Root cause:** non-empty approval input is treated as separation of privilege; identity, uniqueness, active state, tenant, and scope are ignored.
- **Impact:** one, duplicate, retired, or cross-tenant approver satisfies a high-impact rule.
- **Repair:** two distinct current admins of the target tenant for the exercise’s exact action. A fuller system must also bind artifact/object, time window, revocation, purpose, and execution.

### Export initiator/target mismatch

- **Root cause:** the target tenant is accepted as caller-supplied context and is never related to the initiating administrator's current tenant.
- **Impact:** a Tenant A administrator can obtain a positive export decision for Tenant B.
- **Repair:** resolve the initiator's current scoped administration and compare it with the server-resolved target before counting any approvals.

## Intended seeded-review findings

Strong reviews should find at least six and span four classes. Intended findings include:

1. `is_authenticated` only tests dictionary presence, so inactive membership remains ambient authority.
2. read authorization does not resolve or compare stored object tenant.
3. aggregate list returns every tenant’s summaries; direct-path reasoning is not complete mediation.
4. `note:delete` expands `admin` globally without tenant/object scope.
5. unknown actions end in a fail-open allow.
6. export target tenant is not checked against the initiating admin’s tenant.
7. a single approval is accepted despite the documented two-person property.
8. duplicate approver IDs are not deduplicated or rejected.
9. approver identity, active state, role, and tenant are not evaluated.
10. the vulnerable SECURITY.md describes ambient categories but is not itself enforcement or evidence.
11. decision evidence lacks authority version/time/enforcement point; the fixture therefore cannot establish revocation timing.
12. no HTTP/database/cache/worker enforcement coverage can be inferred from the local service functions.

Accept additional valid findings, especially object-field projection, missing grant lifecycle, common approval dependencies, and mutable global store limits. Do not award depth for merely naming “IDOR,” “BOLA,” “broken access control,” or ASVS chapters.

## Knowledge-check anchors

1. Authentication establishes identity evidence; authorization relates that current subject to an action/object. Bob can authenticate correctly and still lack A-note authority.
2. The matrix is the abstract subject–object–action relation. Roles compress cells by subject attributes; ACLs represent cells near objects. Neither representation proves enforcement.
3. A random ID raises guessing work. It is a capability only if possession intentionally conveys scoped authority and the mechanism addresses unforgeability, distribution, copyability, expiry, and revocation.
4. Ambient authority is available from context rather than an explicit grant for the effect: global current user/admin, process DB role, or broad worker service account.
5. A policy function can be bypassed, invoked with attacker-controlled attributes, consulted after release/mutation, or used with stale state. Complete mediation also needs enforcement coverage.
6. Delegation must derive from issuer authority, attenuate action/object/constraints/time, bind intended grantee or bearer semantics, and define use-time authenticity/current state/revocation/onward delegation.
7. Repeated action by one identity is one failure domain. Separation requires independently meaningful conditions under the modeled threat.
8. Policy coverage tests decision cells/states; enforcement coverage shows every effect path consumes the decision before effect.
9. Sessions, tokens, caches, grants, queued jobs, offline state, or restored records may retain copied authority after role removal.
10. `v5.0.0-8.4.1` can support a bounded claim that selected multi-tenant operations enforce cross-tenant controls. It does not prove every path, identity, session, database, cloud administrator, or product property.

Equivalent bounded answers are acceptable.

## Authority-map and matrix evaluation

Competent work:

- freezes Phase 1 scope and names deferred paths;
- distinguishes originating/effective subjects when applicable;
- splits summary/body and read/list/delete/membership/export effects;
- records positive authority source and trusted attribute source;
- has no blank in-scope cells or ambient global admin;
- includes revoked state and fail-safe unknown behavior;
- treats the export separation rule as an exercise decision, not universal truth;
- maps cells to enforcement points and tests;
- records residual risk and review triggers.

Block competence if client-supplied tenant/role is trusted, random IDs substitute for authority, UI controls are enforcement, revoked identities remain allowed without bounded rationale, or future paths are labeled covered without evidence.

## Build/design evaluation

The smallest acceptable design has an explicit current positive decision plus enforcement before effect. It resolves subject and object authority attributes from trusted sources, preserves action/tenant/object scope when using a role, and denies unknown or unavailable policy state for the scoped effect.

Accept application, query, or persistence enforcement designs if assumptions and evidence are coherent. A central policy service may introduce availability and common-mode risk. Database policy may add independent enforcement or share wrong tenant context. Capability designs must state bearer/identity semantics and lifecycle. No mechanism gets automatic credit.

Rejected-alternative reasoning should explain why denylist, hidden UI, random IDs, authentication middleware, library presence, response-code uniformity, or cosmetic second approval fails to change the authority relation.

## Verification evaluation

Require property/effect oracles, not only decision return values or status codes. Critical deny cases must show absence of partial release/mutation/job. Require at least:

- same-scope allow;
- cross-scope deny;
- revoked/stale state;
- aggregate or alternate path;
- distinct-approval abuse;
- unknown or failed policy;
- counterfactual showing that weakening enforcement breaks evidence;
- stated gaps for HTTP, persistence, cache, worker, transaction, and restore where absent.

## Operations and human-factor anchors

Decision evidence may vary, but should include safe subject/action/object/domain, decision/reason, policy and authority/grant versions, enforcement point, timestamp, and correlation. Reject note bodies, passwords, session/bearer tokens, authorization headers, or unnecessary contact values.

Require a revocation-effect objective across every authority copy in scope, evidence failure behavior, narrow containment, alternate-path scoping, root-cause repair, state/output recovery, retest, communication, and one operator/common-mechanism residual risk.

Where a person grants, revokes, approves, or breaks glass, require keyboard/assistive operation, text labels, visible scope/duration/effect, clear completion/failure, safe cancellation or alternative, and post-use review.

## ReleaseDesk transfer anchors

Transfer-ready evidence should discover rather than merely repeat:

- originating proposer/approvers versus effective CI worker;
- immutable artifact digest and environment as authority-bound objects;
- proposal/approval/queue/execution state and at-least-once delivery;
- two-person independence and shared identity/device/team failure;
- approval expiry, revocation, artifact substitution, cancellation, and replay;
- job as a scoped capability, current re-authorization request, or reference to server-side state, with defended trade-offs;
- machine credential as ability, not product authority;
- execution-time enforcement and idempotent effect;
- break-glass safety/availability trade-off, short scope, notification, automatic expiry, and post-use review;
- accessible approval and revocation.

Require at least four SecureCollab assumptions that fail: human request-time effect, tenant membership relation, stored note object, direct synchronous policy use, confidentiality-dominant harm, or absence of machine/intermediary/retry state are examples. The learner may choose others if justified.

Block transfer-ready if the answer is merely RBAC, signed job, MFA, policy engine, two clicks, or renamed SecureCollab cells.

## Common blockers

- authentication, role, URL secrecy, or identifier randomness substitutes for authority;
- blank/default-allow cells or unscoped admin;
- delegation expands issuer authority or lacks use-time state;
- two approvals are not distinct/current/scoped;
- no aggregate/alternate-path or revocation evidence;
- decision-unit tests presented as complete enforcement evidence;
- status-only or happy-path tests;
- sensitive values in evidence;
- no policy/evidence failure or usable recovery path;
- unsafe target/data scope;
- transfer changes only nouns;
- unversioned/mixed ASVS identifiers or CISA presented as freshly verified;
- examiner material copied into learner work.
