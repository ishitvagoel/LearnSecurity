# Examiner key — Module 1.3 trust boundaries and attack surface

Do not publish or render this file in learner routes. It contains seeded findings, expected lab results, answer anchors, and scoring guidance. Equivalent defensible reasoning is acceptable; require evidence, not vocabulary matching.

## Decision rule

Award **competent** only when every critical rubric dimension is at least competent. Do not average away an unbounded property, false trusted source, incomplete effect mediation, unsafe scope, missing five-mode evidence, or superficial transfer. Award **transfer-ready** only from satisfactory learner PreviewForge evidence; publication of the module itself does not imply learner mastery.

## Knowledge-check anchors

1. **Trust boundary:** a point where a security-relevant assumption or capability changes. A network/TLS hop may preserve the same untrusted semantics; an in-process adapter may create a meaningful new provenance guarantee.
2. **Property-relative TCB:** only components/assumptions that must be correct for the stated property belong. The evidence sink can be outside prevention for export authority but central to accountability; if export blocks on evidence failure, it also affects availability.
3. **Terms:** actor is participant; principal is decision identity; component is execution/data location; channel carries a representation; flow is a directed movement of data/control; entry point is where influence enters in-scope behavior. Credit equivalent concrete SecureCollab mapping.
4. **Attack surface:** all reachable influence paths to a protected effect, including stored state, alternate/admin/worker paths, shared credentials/caches/parsers, configuration, evidence suppression, and lifecycle—not merely exposed routes/ports or known weakness categories.
5. **Transitive trust:** a claim relies on another component/assumption which relies on others. It may stop at an explicit trusted assumption, accepted residual, or named later-module boundary with owner/review trigger—not at “managed service.”
6. **Shared mechanism:** one parser, credential, cache key, runtime, operator, or evidence path connects scopes and permits common-mode failure or cross-scope effects, widening reachable influence and compromise impact.
7. **Correlation:** both checks decide from the same attacker-controlled field and often share parser/routing/operator configuration; one false input or drift can defeat both. Two evaluations are not independent evidence.
8. **Blast radius:** tenants, objects, actions, fields/sensitivity, time/use/retry, egress, resources, policy/control plane, and evidence suppression, each tied to mechanism/evidence/residual.
9. **Provenance vs authority:** provenance establishes caller kind/identity. A current product rule still must grant this worker this action on this tenant/exact object set at this time/use state.
10. **Decision vs mediation:** a correct policy result does not prove every wrapper/helper/retry/admin path calls it before effect, that output/state is unchanged on denial, or that persistent/concurrent use is safe.
11. **Evidence failure:** it changes whether detection/accountability claims hold and may alter high-impact effect behavior. The design must deliberately block, buffer, or degrade with explicit availability/privacy trade-offs.
12. **Bounded lab conclusion:** the fixed local public adapter cannot construct worker provenance and covered wrapper cases enforce fixture grant rules. It does not prove network/proxy/workload identity, queue, persistence/atomicity/concurrency, database isolation, sandbox/egress, durable audit, provider/operator, or ASVS compliance.

Accept concise answers that preserve these distinctions. Reject “zero trust,” “internal vs external,” “use TLS,” “scan endpoints,” or “defense in depth” as stand-alone answers.

## SecureCollab model anchors

A competent diagram/ledger includes equivalents of:

- hostile public caller through conceptual ingress to public adapter;
- explicit boundary where a public-only context is constructed without turning request data into authority;
- server-held worker registry/adapter as the local provenance source;
- scoped grant and current fixture state as authority sources;
- policy/effect enforcement immediately before summary selection;
- exact summary output and evidence sink;
- attacker-controlled metadata/object labels remain untrusted until resolved/authorized;
- IdP/email/object storage/CDN/queue/network/cloud/build/backups/analytics/mobile labeled deferred or residual.

Expected flow logic:

- public path cannot select worker caller kind;
- worker provenance does not bypass grant checks;
- grant binds worker/action/tenant/exact object set/expiry/use;
- stored note relations are rechecked;
- output is summary-only;
- evidence behavior precedes high-impact effect under fixture policy.

TCB membership must change by property. For example:

- export authority: adapter provenance, registry/grant state, policy/effect enforcement, stored relations, runtime assumptions;
- confidentiality: those plus output projection and any output/evidence handler that could copy bodies;
- accountability: evidence producer/schema, correlation/time, delivery/store/access assumptions;
- availability: evidence-block policy, registry/grant/store availability, resource controls when real work exists.

Block a diagram that marks “backend,” “private network,” or “cloud” trusted without property-specific assumptions, or that depicts deferred production components as implemented controls.

## Attack-surface / shared-dependency anchors

Minimum competent rows cover:

1. public metadata and dispatcher;
2. stored tenant/object/membership relations;
3. worker registration/context construction;
4. grant presentation and lifecycle;
5. output construction/projection;
6. evidence availability/content/suppression;
7. configuration/operator influence;
8. shared runtime/store/parser/credential effects, even if some are explicit residuals.

Each row links entry/flow to attacker/failure, protected effect, enforcement/trusted source, oracle, blast radius, closure state, residual, and owner. Endpoint/CVE/product lists are developing.

Good independence analyses are relative to a fault:

- edge header stripping + API header trust: correlated for parser/config/public-assertion failure;
- public adapter type/path + scoped grant check: logically complementary/partially independent for public metadata promotion, but share process/runtime/operator and require enforcement-coverage proof;
- policy prevention + evidence signal: different functions and may be partially independent, but same-process compromise/sink failure can suppress evidence;
- exact grant scope + broad database role: policy narrows modeled product effect, but a code/process/credential compromise retains all-tenant mechanism blast radius.

Do not require a numerical independence score. Reject “different vendors/products means independent.”

## Exact lab verification

Validated author environment: Python 3.12.13, pytest 9.1.1.

Vulnerable command:

    python -m pytest labs/1.3/1.3-trust-boundaries/tests --impl vulnerable

Expected: **exit 1; 10 failed, 10 passed**.

Fixed command:

    python -m pytest labs/1.3/1.3-trust-boundaries/tests --impl fixed

Expected: **exit 0; 20 passed**.

Ten intended vulnerable failures:

| Test | Root cause | Forbidden effect / fixed oracle |
|---|---|---|
| `test_public_metadata_cannot_construct_worker_provenance` | Public mapping supplies both “independent” marker checks and service identity; no trusted worker adapter/grant mediation | Vulnerable returns allowed summaries; fixed denies with empty output |
| `test_grant_is_bound_to_worker_identity` | Registration plus any known grant becomes ambient ability; subject/grant binding absent | Worker B uses Worker A grant; fixed denies/empty |
| `test_grant_cannot_cross_tenant` | Tenant request is not compared with grant | Tenant A grant releases B1 summary; fixed denies/empty |
| `test_grant_cannot_widen_same_tenant_object_scope` | Tenant membership substitutes for exact object scope | A3 added to A1/A2 grant; fixed denies/empty |
| `test_grant_cannot_change_action` | Action is unbound | `export_body` label is allowed through broad helper (fixture still projects summaries); fixed denies before effect |
| `test_expired_grant_denies` | Expiry ignored | Expired grant exports; fixed denies/empty |
| `test_grant_denies_at_exact_expiry_instant` | Expiry boundary is ignored instead of treating `expires_at` as the first invalid instant | Grant works at its expiry instant; fixed denies/empty |
| `test_successful_grant_cannot_be_replayed` | Successful use never consumes lifecycle state | Second export succeeds; fixed first allows and second denies |
| `test_evidence_failure_denies_high_impact_effect` | Effect proceeds silently when required evidence is unavailable | Vulnerable releases; fixed returns empty and leaves grant unused |
| `test_control_independence_claim_names_shared_failures` | Same request field/parser/config plus runtime/operator are labeled independent | Vulnerable classification is dishonest; fixed calls distinct inputs partially independent and names runtime/operator sharing |

Ten valid/regression/safety passes on the vulnerable tree:

- exact scoped worker export remains usable;
- ordinary public request denies;
- service label alone denies;
- unknown registration denies;
- unknown grant denies;
- duplicate object IDs deny as malformed;
- non-collection object scope denies cleanly as malformed;
- allowed output projects only summaries;
- evidence excludes bodies, bearer material, and requester-chosen correlation values while including object count, a server-held non-bearer capability reference, and generated correlation IDs;
- AST safety check finds no network/file/process execution path.

If totals differ, inspect code/environment before grading. Do not accept dependency/import failure as vulnerability evidence. The learner should explain why passing tests matter and why one failed assertion may contain multiple asserts but represents one intended case.

## Causal-diagnosis anchors

Require separate rows for:

- provenance source (public field vs trusted adapter);
- worker-to-grant subject binding;
- tenant, action, and exact object bindings;
- expiry and consumption transitions;
- evidence-outage decision;
- dependency/independence honesty.

Minimum structural repair:

- separate public and worker context construction;
- server-side registry establishes only worker identity;
- current grant binds worker/action/tenant/exact object set/expiry/use;
- stored relation validation;
- decision enforced before exact summary projection;
- successful sequential consumption;
- explicit evidence-before-effect policy;
- common runtime/operator residual acknowledged.

Expected rejected repairs:

- stripping one header spelling leaves negative filtering, alternate paths, parser/config drift;
- private address/route name is not product provenance/authority;
- duplicate check shares the same false input;
- global signature can prove integrity/holder while remaining overbroad and replayable;
- broad store credential remains mechanism ability and large compromise blast radius;
- logging after effect or skipping on outage does not prevent or reliably evidence release;
- deny-all breaks required normal behavior.

## Verification anchors

A competent matrix covers all five modes and observes state/effect, not status alone:

- normal exact summaries and consumed state;
- negative ordinary/unknown/malformed/wrong bindings;
- abuse forged metadata, Worker B grant use, widening, replay;
- failure expiry/evidence outage;
- counterfactual removal of one protection with predicted isolated test change.

Require surface closure labels. Appropriate limits include:

- local public-adapter construction: executable/structural evidence now;
- production proxy/routing/workload identity: deferred/residual;
- grant scope in sequential memory: executable now;
- persistent atomicity/concurrency/queue replay: deferred;
- event schema/outage: executable now;
- durable/tamper-resistant evidence: residual/later.

Counterfactual quality: prediction names causal control, changed oracle, and stable unrelated behaviors. “Changed code and some test failed” is developing.

## Operations anchors

Evidence fields may include caller kind, effective worker ID, trusted adapter, action, tenant, object count, grant reference/digest, allow/deny reason, enforcement/model version, correlation/time, and effect state. Prohibit bodies, raw grants/tokens, authorization headers, arbitrary hostile content, passwords, and unnecessary personal attributes.

Good signals include:

- reserved/internal metadata at public adapter;
- worker action through public path or path/provenance mismatch;
- reason-specific scope/expiry/replay denial changes;
- decision without effect or effect without decision;
- unexpected tenant/object/egress/evidence reach.

Each needs hypothesis, rationale, evidence, owner, false results, and first response. The fixture’s evidence-outage decision is block; learner may critique/trade off but must preserve the stated property or explicitly redefine it.

Runbook must distinguish scope, narrow containment, common-assumption enumeration, revocation/rotation, root-cause repair, output/state reconciliation, evidence restoration, five-mode retest, artifact refresh, and accessible communication. Reject claims that revocation restores already-disclosed confidentiality.

## Seeded-review findings

Learners may organize differently, but strong comments should find at least:

1. two “layers” consume the same public field, so provenance and independence claims fail;
2. public service label is also untrusted;
3. TLS/internal path does not establish product authority;
4. registered worker is treated as permission for all tenant/action/object scope;
5. grant is not bound to worker;
6. expiry/use lifecycle is ignored;
7. broad store credential creates larger compromise blast radius than product authority;
8. evidence outage silently erases the accountability claim while effect proceeds;
9. shared deployment/operator makes additional common-mode failure, not independence;
10. passing local units cannot prove full enforcement or production networking/identity/persistence;
11. out-of-scope declarations contradict “ready for production”;
12. recovery and model-refresh obligations are absent.

Accept eight actionable comments only if all six required classes are covered. Require severity, candidate evidence, property/effect, root cause, minimum structural change, oracle, and residual.

## Standards anchors

Exact ASVS 5.0.0 text/use:

- `v5.0.0-15.1.3` (Level 2): documentation identifies time-consuming/resource-demanding functionality and availability strategy;
- `v5.0.0-15.2.2` (Level 2): defenses against loss of availability from such functionality follow documented decisions;
- `v5.0.0-15.2.5` (Level 3): additional protection around documented dangerous/risky functionality, with examples including sandboxing, encapsulation, containerization, or network isolation to deter pivoting;
- `v5.0.0-15.3.4` (Level 2): proxy/middleware transfer of original IP through trusted fields not manipulable by the end user, with limits on IP reliability.

Module 1.3 uses `15.3.4` as an exact provenance lesson/analogy, not as a claim that client IP is workload identity. It uses the resource/isolation requirements principally in PreviewForge. Label `15.2.5` Level 3. Do not accept generic “V15 compliance,” ASVS 4.x IDs, a claim that ASVS mandates the fixture, or a claim that a container proves isolation.

Saltzer principles are named design reasoning, not compliance clauses. OWASP Threat Modeling guidance is maintained and methodology-neutral; Four Questions are a starting framework, not a mandate to use STRIDE or Threat Dragon.

## PreviewForge transfer anchors

Transfer-ready evidence should discover and model:

- hostile bytes as stored/delayed entry point;
- immutable object key/version/digest binding from upload intent through job and output;
- storage event provenance versus product authority/current state;
- queue duplication, reorder, retry, cancellation, expiry, and idempotency;
- converter/parser as risky or potentially compromised component;
- per-job workspace, narrow object credentials, write/quarantine destination, egress, cleanup;
- CPU/memory/disk/file-count/expansion/output/concurrency/cumulative-retry budgets;
- scan/conversion/moderation/publication lifecycle and race conditions;
- withdrawal plus preview/CDN invalidation and persistent-output recovery;
- shared parser/scanner libraries, identity/configuration, capacity, operators, dependencies, and evidence paths;
- property-relative TCB changes for object binding, containment, availability, accountability;
- five-mode state/side-effect/output/cache/evidence oracles;
- no harmful payload or live system interaction.

At least four SecureCollab assumptions must be shown invalid. Strong comparisons include request-time metadata vs stored hostile bytes; synchronous local call vs asynchronous retry; summary release vs parser/resource/egress/persistent publication effects; one fixture store vs object/event/queue/job/output/cache binding; confidentiality-dominant harm vs containment/availability; and exact in-memory output vs partial/cached persistent output.

Block transfer-ready for renamed headers, “put worker in container,” “scan uploads,” “use signed queue messages,” diagram-only submission, or no revised operations/evidence.

## Common blockers

- boundary follows boxes/network without changed assumption;
- TCB is fixed “backend/cloud” list;
- attack surface is endpoints/ports/CVEs/Top 10;
- client field, private address, route name, registration, or signature substitutes for scoped current authority;
- duplicate/correlated checks counted as independent;
- isolation or blast radius asserted without dimensions/evidence;
- policy tests presented as complete effect mediation;
- missing normal, failure, counterfactual, unchanged-state, or exact-output evidence;
- evidence contains bodies/bearer material or outage behavior is undefined;
- response blocks trigger but not shared root assumption; disclosure claimed reversed;
- deferred production components shown as implemented;
- transfer changes nouns only;
- unsafe target/data/payload practice;
- unversioned/misapplied standards or broad compliance claim;
- examiner content appears in learner submission.
