# Examiner notes — 0.1 (not learner-facing)

## Property

A URL is in scope only if its parsed hostname is exactly one of three written local lab names; reachability, a rendered login page, or a professional-looking TLS certificate is not that fact (C1). A testing-method catalogue, a work-role title, or a governance-outcome label cannot add a host to that list, because none of the three is a record of granted permission (C2). A URL the checker cannot parse, or a non-string argument, must deny rather than raise or default to allowed (C3). Noticing a denial and capturing what the denied host returned are two different controls, and the second one is itself the violation the first one exists to prevent (C4). Allow-list membership is exact-string, not prefix, suffix, or "the connection started there" (C5). Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

Standards, live-checked against their canonical pages on 2026-09-18 (see `content/standards/pins.yaml`): NIST CSF 2.0 (CSWP 29, Govern/Identify as outcome vocabulary, C2), OWASP WSTG 4.2 (stable, a method catalogue for an already-in-scope app, C2), NIST SP 800-181r1/NICE (workforce role language, C2), W3C WCAG 2.2 (Recommendation, keyboard operability of the scope/stop UI). This module mints no ASVS identifiers — it teaches tester authorization, not an application security requirement ASVS catalogues.

## Lab

- `labs/0.1/0.1-orientation/vulnerable/` must fail 4 of 7: `test_public_host_is_out_of_scope`, `test_lookalike_hosts_are_not_authorized`, `test_malformed_and_non_string_url_fails_closed`, `test_case_and_scheme_do_not_change_the_public_verdict`.
- `labs/0.1/0.1-orientation/fixed/` must pass all 7.
- Root cause (C1): `vulnerable/scope.py` returns `True` unconditionally — reachability and authorization were never distinguished in code. Root cause (C3): a naive fix (`urlparse(url).hostname.lower()`, no exception handling) lets `ValueError` (malformed IPv6 bracket) or `AttributeError`/`TypeError` (non-string input) propagate out of `target_is_authorized`, so a caller gets a crash instead of a verdict. Root cause (C5): a naive fix using `host.endswith(allowed)` instead of exact set membership authorizes any host that merely ends with an allowed name.
- The structural fix (`fixed/scope.py`, this pass) wraps the parse in `try/except (ValueError, AttributeError, TypeError)` and returns `False` on any of them, and compares with `host in ALLOWED_HOSTS` — exact membership, never `endswith`/`startswith`/`in`.
- Anti-fake test (`test_anti_fake_generalizes_beyond_the_three_literal_example_urls`) verified by hand against two distinct fakes: (1) a hard-coded lookup of the exact URL strings used elsewhere in the test file passes every other test and fails only this one — 6 of 7, not 7 of 7; (2) a `host.endswith(allowed)` comparison passes every other test and fails only `test_lookalike_hosts_are_not_authorized` — also 6 of 7. Each fake is caught by a different, deliberately separate test.

## Seeded review — intended findings

`lessons/08-review.md` hands the learner `vulnerable/scope.py` described as a PR adding "basic scope checking," with a four-question checklist rather than a stated answer. Applied to the file as it stands:

1. **What would falsify the PR's claim?** `target_is_authorized("https://example.com/")` returns `True`, not `False` — the function ignores its argument entirely. Any URL "passes."
2. **What does the file actually check, versus what the PR description implies?** Nothing. There is no `ALLOWED_HOSTS`, no `urlparse` call, no comparison of any kind — the description implies a check exists; the code is a one-line `return True`.
3. **The disagreement, with a concrete input.** `target_is_authorized("https://example.com/")` → `True` on this file; the module's own stated invariant requires `False`.
4. **The requested change and the test that proves it.** Replace the body with a hostname parse and an exact-membership comparison against a written local allow-list, denying on parse failure. The test that fails today and passes after the change is `test_public_host_is_out_of_scope` (and, once the fix also handles the edge cases correctly, `test_lookalike_hosts_are_not_authorized` and `test_malformed_and_non_string_url_fails_closed` as well).

A learner who names all four, and specifically identifies "the function does not look at its input at all" as the finding (not "it returns a boolean," which is true but not itself a defect), has passed this review.

**Transfer submission** (`lessons/08-review.md` §Use it somewhere new — a colleague's scope-check PR claiming "we now validate hostnames properly" by adding `host.endswith(tuple(ALLOWED_HOSTS))`): the correct finding is that "validate hostnames" is not itself evidence for C5, and the same four-question checklist applies. Banding: *developing* answers accept "it checks the hostname now" as sufficient; *competent* answers trace `"evillab.securecollab.test".endswith("lab.securecollab.test")` to `True` and name the gap; *transfer-ready* answers additionally state the general pattern — any comparison that is not exact-string equality against a finite written set should be read as "this widens the set to something nobody wrote down," and that widening is worth tracing with a concrete adversarial input before trusting it.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **A** is the rule. **B** is a tool. **C** and **D** are false assurances.

**Why each is categorized this way:**
- **B** ("a Burp license and configured proxy") is a tool: real, useful for testing an in-scope app, and entirely silent on which app that is — a proxy will open whatever URL it is given.
- **C** ("answered on 443 with a valid cert and a fast login page") is a false assurance built from three real observations, none of which is permission: TLS validity says the connection is private, not authorized; response speed says the host is healthy, not consented; a login page says the product has an account system, not that this tester may attack it.
- **D** ("the recruiter's email says it's official") is a false assurance that sounds like C2's territory but is actually a C1 failure dressed as one: an unverified claim of officialness is not the same as the written allow-list membership C1 requires, regardless of who asserts it.

**Banding:** *developing* — sorts A correctly but cannot explain why C or D is false rather than merely weak. *competent* — sorts all four correctly with at least one specific reason each. *transfer-ready* — additionally explains why D is more dangerous than C: an unverified claim of authority ("the recruiter says") is designed to be persuasive precisely when a written allow-list is unavailable to check against, which is exactly when the rule needs to hold hardest.

### Item 2 — a vocabulary term vs. a target list

**Answer:** **D** is the only one that would actually add a host to a written allow-list. **A**, **B**, and **C** are, respectively, a testing method (WSTG), a job title (NICE), and a governance activity (CSF Identify) — none of the three is a permission record.

**Why each falls short:**
- **A** ("WSTG has an authentication chapter") names *how* to test authentication once an app is in scope; it says nothing about whether this particular app is.
- **B** ("NICE lists my job title") names a *role category*, not a target — the NICE Framework's own stated purpose is workforce description, confirmed live against the canonical NIST overview on 2026-09-18.
- **C** ("CSF's Identify calls for inventories, and this host showed up") inverts the causality: CSF names an outcome an organization pursues over its *own* assets; a host appearing during an inventory exercise is not the same as that host's owner granting a tester permission to attack it.
- **D** ("a signed statement naming the host, dates, and testers") is the actual shape of written permission this module's allow-list stands in for.

**Banding:** *developing* — picks D but cannot say what specifically each of A/B/C actually is (method, role, governance activity). *competent* — correctly names all three and why each is a category error, not merely "not enough." *transfer-ready* — additionally explains why standards-as-permission is an attractive mistake specifically because all three documents are legitimate and current — the error is not that the cited document is fake or outdated, it is that the document was never in the business of granting scope to begin with.

### Item 3 — a scope checker that crashes instead of denying

**Answer:** Calling this checker with `url = "http://[::1/path"` raises `ValueError: Invalid IPv6 URL` from inside `urlparse`, which propagates straight out of `target_is_authorized` — the function never returns at all. **Root cause:** the function has no exception handling around the parse; a malformed authority is treated as if it cannot occur. **Precondition:** any caller that can supply a URL string it did not construct itself, or a URL a user pasted, can trigger this — a malformed IPv6 bracket is an easy typo, not a crafted attack. **Impact:** depends entirely on what the calling code does when this function raises instead of returning; if that caller wraps the call in a broad `try/except` and defaults to "allowed" on any exception — a common defensive-coding habit aimed at *availability* — the parse failure becomes an authorization bypass by accident, with nobody having decided that outcome anywhere.

**Banding:** *developing* — identifies that the function crashes without tracing the specific exception type or naming root cause/precondition/impact as three separate things. *competent* — correctly names the `ValueError`, traces it to the missing exception handling, and states the impact depends on caller behavior. *transfer-ready* — additionally names the general anti-pattern: a security-relevant boolean function that can raise instead of returning has silently created two ways to fail — with an answer, and without one — and only one of those two ways can be tested for directly.

### Item 4 — a host comparison that is not exact

**Answer:** `target_is_authorized("https://evillab.securecollab.test/")` returns `True` on the `endswith` version, because `"evillab.securecollab.test".endswith("lab.securecollab.test")` evaluates to `True` in Python — the suffix match does not require the character *before* the match to be a domain separator (a `.`), so any string that happens to end in the right letters passes. **Root cause:** the comparison checks "does the string end with these characters," which is a weaker claim than "is this exact hostname a member of this exact set," and the two happen to agree on every input the teammate tested by hand. **Precondition:** whoever controls the hostname portion of a URL a caller passes to this function — which, for a URL pasted by a learner, another engineer, or an attacker crafting a link, is whoever chose the string — can pick any hostname ending in an allowed suffix. **Impact:** a host the written allow-list never named is treated as authorized, which is precisely the forbidden outcome this whole module exists to prevent, reintroduced by a fix that looked like an improvement.

**Banding:** *developing* — states the function is wrong without tracing why `endswith` specifically produces `True` for this input. *competent* — correctly traces the string method and states the returned value. *transfer-ready* — additionally proposes the general fix (a domain-boundary check, or simply exact-set membership as `fixed/scope.py` uses) and explains why exact membership is strictly simpler to reason about than any pattern-based alternative for a finite, three-item allow-list.

### Item 5 — silent deny vs. deny-and-alert under a constraint

**Answer:** Engineer B's proposal should be chosen. Engineer A's `False`-only version satisfies C3 (it fails closed) but is indistinguishable, from the outside, between "working exactly as designed — this host really is unauthorized" and "this checker has a bug that makes it deny things it should not," because both produce the same silent `False` with no signal a human would ever see. Engineer B's version keeps the same fail-closed behavior and additionally writes `scope_check_parse_error` with the host string and exception type, giving a human a place to look if denials spike unexpectedly or a specific, legitimate-looking URL keeps failing to parse. The one thing Engineer A's version can never surface on its own: that the checker itself needs a fix, as opposed to the world simply containing another unauthorized host.

**Banding:** *developing* — picks B without explaining what specifically Engineer A's version cannot detect. *competent* — explains that A's silent `False` is operationally invisible and B's added signal makes checker bugs discoverable. *transfer-ready* — additionally notes the general principle: failing closed is necessary but not sufficient, because a system that always answers "no" to everything, including things that should be "yes," is fail-closed and useless, and only a way to notice that state distinguishes it from a checker that is merely doing its job well.

### Item 6 — the denied-host signal, after a response was already fetched

**Answer:** The log line: `out_of_scope host=<hostname> reason=already_fetched_before_check` — the host string and the reason, and nothing else. The already-fetched body must be discarded immediately and never written to any store the log, a ticket, or a teammate's screen can reach — not summarized, not truncated-and-kept, not attached "for context." The field the log line must never contain is the response body (or any excerpt of it, or a screenshot of it). "We'll log the body too, for the ticket" turns one violation into two: the first violation was fetching a host `target_is_authorized` would have denied; writing that body into a log, ticket, or chat message is a second, independent unauthorized disclosure of the same data, this time to every person and system with access to wherever it was written, which is very likely a larger audience than whatever originally received the fetch.

**Banding:** *developing* — writes a signal but does not address what happens to the already-fetched body, or proposes keeping a redacted or truncated copy. *competent* — writes a correct signal and states the body must be discarded, not stored. *transfer-ready* — additionally explains why discarding must happen even though the fetch already happened and cannot be undone — the goal is not to prevent a fact that already occurred, it is to prevent the number of places that fact's evidence now lives from growing any further.

### Item 7 — the contractor and the staging URL

**Answer:** For the customer WordPress: the required artifact is a signed engagement or scope letter from the customer (not the contractor's own employer) naming that specific host and a testing window — a login page existing, the site running WordPress, or the employer's confidence in the contractor's skill are all C1 failures, none of them a written record of the customer's own consent. For the staging URL: the required artifact is the same shape — written, from whoever owns that staging environment, naming the host — and "it's on our own staging subdomain" is not by itself that artifact if the staging environment is customer-owned or shared infrastructure the tester's own employer does not fully control. **C1** is doing the work in both cases: reachability, a recognizable CMS, or organizational trust in the tester are not the allow-list fact the rule requires. A plausible bad justification — "the WSTG has a whole methodology for testing WordPress, so we're covered process-wise" — violates **C2**: WSTG describes method, and citing it answers a question ("how would we test this") that was never in dispute, while leaving the actual question ("are we allowed to") completely unaddressed.

**Banding:** *developing* — recommends against testing both hosts but cannot name a concrete written artifact for either, or names "permission" without saying from whom or in what form. *competent* — names a concrete artifact for both hosts and correctly identifies C1 as the operative claim. *transfer-ready* — additionally identifies a specific plausible-sounding bad justification and names C2 as the claim it violates, rather than only rejecting the justification as "obviously wrong."
