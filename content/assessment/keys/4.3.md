# Examiner notes — 4.3 (not learner-facing)

## Property

A session cannot start or continue from a value carried in the query string; it may start or continue from an `HttpOnly` cookie or an `Authorization` header (C1). A session identifier must be unguessable and bound to the authentication event that minted it, so a pre-authentication identifier cannot survive login (C2). A session needs both an idle lifetime and an absolute lifetime; activity alone must not extend it past the absolute one (C3). Logout and revocation must invalidate server-side state; a token the server still honours is not revoked (C4). `HttpOnly`, `Secure`, and `SameSite` each defend a different attacker capability, and naming one does not cover the others (C5). Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

ASVS anchors, live-checked against the canonical `v5.0.0` tag on 2026-09-17: `v5.0.0-14.2.1` and `v5.0.0-3.4.5` (C1); `v5.0.0-7.2.4` (C2); `v5.0.0-7.3.1`, `v5.0.0-7.3.2` (C3); `v5.0.0-7.4.1` (C4); `v5.0.0-3.3.1`, `v5.0.0-3.3.2`, `v5.0.0-3.3.4` (C5).

## Seeded review — intended findings

`lessons/08-review.md` hands the learner `vulnerable/token.py` as a PR described as adding "idle-timeout support," with a four-question checklist rather than a stated answer. Applied to the file as it stands:

1. **What would falsify the PR's claim about `session_from_request`?** `session_from_request({"access_token": "secret"}, {}, None)` returns `"secret"`, not `None` — the PR's claim that this behavior is "existing, unchanged" is true about its age, and irrelevant to whether it is correct; it is not.
2. **What does `session_is_active` actually check, versus the "idle-timeout support" description?** It reads `issued_at` and `last_seen_at`, null-checks both, and then computes only `now - last_seen_at < 900` — `issued_at` is fetched and validated for presence but never used in any comparison. The name and PR description are accurate about idle timeout and silent about the absence of any absolute-lifetime check; the description is not false, it is incomplete, and a reviewer checking only "does it do what it says" will miss that a policy needs a second clock the description never promised.
3. **The disagreement, with concrete inputs.** `session_is_active({"issued_at": 1_000_000.0 - 432_000, "last_seen_at": 999_999.0}, 1_000_000.0)` returns `True` on this file. A session minted roughly five days before `now`, far past any reasonable absolute policy, reports active because it was touched one second ago.
4. **The requested change and the test that proves it.** Add `if now - issued_at >= ABSOLUTE_TIMEOUT_SECONDS: return False` after the idle check. The test that would fail today and pass after the change is exactly `test_forbidden_outcome_activity_alone_does_not_extend_the_absolute_limit` in `tests/test_property.py`.

A learner who reports all four answers, and specifically names the missing absolute-lifetime comparison as the finding (not "the function reads two timestamps," which is true but not itself a defect), has passed this review.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **A** is the rule. **B** and **D** are tools. **C** is a false assurance.

**Why each is categorized this way:**
- **D** ("reject if `access_token` specifically appears") is a tool: it is a denylist of one parameter name, checked and then fallen through to cookie/header — real and useful, but narrower than the rule, since it depends on the query parameter being named exactly `access_token` rather than on the query channel being structurally incapable of ever supplying a session value.
- **B** ("`Referrer-Policy: no-referrer`") is a tool that closes one of Lesson 01's four leak paths (the `Referer` header) and has nothing to say about access logs, browser history, or screenshots — a real control, aimed at a narrower target than the rule.
- **C** ("HTTPS everywhere, so interception isn't possible") is a false assurance: it answers a question about the wire between browser and server, and every one of the four leak paths this module names happens on one side of that wire or the other, never on it.

**Banding:** *developing* — sorts A correctly but cannot explain why C is false rather than merely weak. *competent* — sorts all four correctly with at least one specific reason each. *transfer-ready* — additionally explains why C is more dangerous than B or D: it actively discourages someone from adding either real control, on the reasoning that TLS has already handled the whole problem.

### Item 2 — property vs. mechanism for session binding

**Answer:** **B** states the property (C2). **A**, **C**, and **D** are mechanism or proxy claims, ranked A (closest to real evidence) > C (weakest but at least implementation-adjacent) > D (irrelevant to this specific property).

**Why each falls short, ranked:**
- **A** ("256-bit random identifiers") is the closest to evidence for a *different* property — unguessability — and is frequently mistaken for evidence of C2 specifically. It says nothing about whether the identifier changes at login; a random value that survives login unchanged is fixed exactly as effectively as a predictable one.
- **C** ("no two-IP collision observed in logs") is weaker: absence of an observed anomaly is not evidence a binding check exists, only that no input has yet exposed whatever behavior is currently present, safe or not.
- **D** ("HTTPS and a CSRF token") addresses transport confidentiality and cross-site request forgery, both real and unrelated to whether login mints a fresh identifier — a reviewer who accepts D as covering C2 has been shown controls for two different attacker capabilities and asked to certify a third.

**Banding:** *developing* — picks B but cannot rank A/C/D. *competent* — picks B and correctly explains why A (entropy) does not substitute for binding. *transfer-ready* — additionally names session fixation by its mechanism (an attacker plants a known pre-authentication value, then waits for the victim to authenticate it) rather than only by name.

### Item 3 — a lifetime checker's gap

**Answer:** Root cause: the function computes only `now - last_seen_at < 900` and never reads or compares `issued_at` in any conditional — the field is fetched and null-checked but has no role in the actual decision. Precondition: a session whose total age exceeds any reasonable absolute-lifetime policy, but which continues to be touched inside the 900-second idle window. Impact: the function returns `True` — the session is reported active — for a session fourteen days old, because the only clock consulted is "seconds since last touch," and five seconds passes that check regardless of the fourteen-day history.

**Banding:** *developing* — identifies that the function is wrong without tracing the specific input through it. *competent* — correctly traces the computation and states the returned value. *transfer-ready* — additionally notes that `issued_at` being read and null-checked at all is what makes this gap easy to miss on a skim: a reviewer who confirms "it checks for a missing `issued_at`" may stop before noticing the value, once present, is never used.

### Item 4 — reading a candidate fix

**Answer:** This fix does **not** pass. Tracing the input (no `issued_at` key, `last_seen_at` five seconds before `now`) through this exact function: `session.get("issued_at", now)` returns `now` itself, because the key is absent and `now` is the supplied default. `now - issued_at` is then `now - now = 0`, which is nowhere near the 43,200-second absolute limit, so the second `if` never triggers. The idle check passes (five seconds is under 900). The function returns `True` — active — for a session whose actual age is completely unknown. The default silently converted "we have no idea how old this is" into "this was minted at this exact instant," the single most trusting answer available.

**Banding:** *developing* — says it passes, or says it fails but cites the wrong reason (for example, citing the idle check rather than the default). *competent* — correctly traces the `.get(..., now)` default and concludes the function wrongly reports the session active. *transfer-ready* — additionally names the general pattern: any `.get(key, now)` or `.get(key, default_that_looks_safe)` substitution for a required security-relevant field should be read as "this code has an opinion about what missing data means," and that opinion is worth checking explicitly rather than accepting as boilerplate.

### Item 5 — a cookie-setting call

**Answer:** The call leaves `SameSite` unset, which most browsers then treat with a lenient default rather than the deliberate value the application should choose. The specific class of request this leaves open is a cross-site request — a different site's page causing the victim's browser to attach `sc_session` to a request the victim did not intend, which is the cross-site request forgery and cross-site-leak surface. The one-line change is adding `samesite="Lax"` (or `"Strict"`, depending on whether the notes app needs the cookie present on a cross-site top-level navigation such as an email link).

**Banding:** *developing* — names "the cookie isn't fully protected" without identifying which specific attribute is missing or which capability that gap opens. *competent* — correctly names the missing `SameSite` attribute and the cross-site request capability it would have closed. *transfer-ready* — additionally explains why adding `SameSite` does not make `Secure` or `HttpOnly` redundant, or vice versa — each of the three answers a materially different attacker capability, per C5, and the presence of two does not imply anything about the third.

### Item 6 — logout under a constraint

**Answer:** Engineer B's fix should be chosen. Engineer A's fix fails the stated constraint directly: shortening `Max-Age` changes when a *future* cookie expires on its own timeline; it does nothing about a token already issued and already sitting in a second browser's cookie jar right now, which will continue to validate normally until whatever expiry was already set for it arrives. Engineer B's fix (a server-side revoked-session set every request checks) makes the second browser's copy stop working on its very next request, because the check that decides validity now consults state the logout handler just wrote, rather than trusting the token's self-reported expiry alone. Residual risk Engineer B's fix still leaves open: a request already in flight at the exact moment of revocation, mid-processing on the server, may complete using the session state it read before the revoked-set write landed — a narrow race, but a real one, distinct from the much larger gap Engineer A's fix leaves.

**Banding:** *developing* — picks B without addressing the "immediately, not merely sooner" constraint explicitly. *competent* — explains why A fails the constraint (acts on a future timeline, not the present state) and B satisfies it. *transfer-ready* — additionally names the specific residual (an in-flight request racing the revocation write) rather than claiming B's fix is complete.

### Item 7 — two clocks under a constraint

**Answer (indicative, not exhaustive):** A workable pair is an idle timeout on the order of 15–30 minutes (long enough that normal pauses in active work — reading a document, a short meeting — do not trigger unwanted re-authentication) and an absolute lifetime on the order of 8–12 hours (roughly a working shift, so a session started in the morning cannot be kept alive by activity alone into the next day or week). The absolute number is the one doing the actual work of limiting a stolen token's useful life: an attacker who has a valid token and replays it periodically will always be able to satisfy an idle-only check, by definition, since replaying it *is* the activity that resets the idle clock — the idle number alone can be made arbitrarily generous by an attacker who is willing to replay slightly more often, but the absolute number cannot be extended by activity at all, which is exactly what forces re-authentication regardless of how diligently a stolen token is kept "warm."

**Distractor pattern:** An answer proposing only a longer idle timeout as the fix for "logs people out while working" is developing — it solves the stated friction complaint but does not address the "limits a stolen token" half at all. An answer that proposes both numbers but does not identify which one does the limiting work is competent. An answer that additionally explains *why* an idle-only policy can always be defeated by sufficiently frequent replay — the same reasoning Lesson 03's break demonstrates concretely — is transfer-ready.

### Item 8 — clinic deep link and magic-link email

**Answer:** C1, C3, C4, and C5 transfer essentially unchanged to whatever session results from redeeming a one-time link — the mechanism (URL exposure, dual-clock lifetime, server-side revocation, cookie attributes) does not care how the underlying identity was proven. **C2 is the redemption-specific claim.** Module 6.6 owns whether the *link itself* can be redeemed twice — a materially different, and prior, question from whether the *session issued upon redemption* is a freshly minted identifier or a continuation of the link's own token value. An answer that treats "the link is one-time" as satisfying C2 is conflating two separate guarantees: a one-time link that, on its single permitted use, hands the browser a session built from the *same* token value the link carried has reintroduced exactly the fixation shape C2 forbids, with a one-time code standing in for a password — the attacker's problem is not that the link can be reused, it is that if the attacker sees the link (or the code) even once, before the victim redeems it, and the resulting session is bound to that same value, the attacker's copy becomes live the moment the victim redeems it.

**Banding:** *developing* — restates "the same five rules apply" without identifying which one is redemption-specific, or claims the link's single-use property by itself satisfies C2. *competent* — correctly names C2 as redemption-specific and distinguishes it from 6.6's single-use property in general terms. *transfer-ready* — additionally states the precise attack this distinction closes (an attacker who saw the pre-redemption link/code gets a live session at the moment the victim redeems it, if the resulting session reuses that same value) rather than only naming the two guarantees as separate.

### Item 9 — the expiry and revocation signal

**Answer:** Two lines: `session_expired reason=idle|absolute path=<path> request_id=<id>` for a lifetime limit, and `session_revoked reason=logout|admin path=<path> request_id=<id>` for an explicit action. The `reason` field is what distinguishes the cases — `idle` vs. `absolute` further distinguishes *which* lifetime limit fired, which matters operationally, because a spike in `reason=idle` expirations might indicate a UI bug causing unwanted logouts, while a spike in `reason=absolute` is expected steady-state behavior. Neither line may ever carry the session identifier or token value itself — logging the value defeats the same purpose Lesson 01's query-string argument makes for the token generally, just via a different channel (the log line instead of the URL). A single undifferentiated `session_ended` event is operationally worse than two distinct ones because an operator investigating "why do users keep getting logged out" cannot distinguish "working as designed, twelve hours passed" from "something is expiring sessions early" without the reason code — the single event answers "did a session end," and the operational question is almost always "why."

**Banding:** *developing* — writes one signal without a reason code, or includes the session identifier in the log line. *competent* — writes two distinct signals with a reason field and correctly excludes the token value from both. *transfer-ready* — additionally explains the operational cost of collapsing the distinction (an operator cannot separate expected lifetime enforcement from an unexpected early-termination bug without it).
