# Examiner notes — 2.2 (not learner-facing)

## Property

A shared cache entry for `GET /notes/{note_id}` may be returned only when the key includes the caller's bound company; a cache key that omits it, or that is fooled into using a client-supplied value, lets one company's cached body answer another company's request (C1). The company an authorization decision uses must come only from the caller's own credential-derived resolution, never from a client-supplied `X-Company`/`X-Tenant`/`Host` value (C2). A hop-authentication check must require, together, a trusted CA, an exact hostname match, and an accepted TLS version — an unknown or a definitively failed trust state both fail closed, and they are not the same fact about the world (C3). A TLS handshake authenticates one hop; it does not chain to authenticate a later hop, so each hop needs its own check (C4). A code-level fix does not survive a CDN, edge, or operator config change unless it is paired with a detection signal and a purge path (C5). Five teaching claims (C1–C5) are named in `spec.md` §Teaching claims; every item below maps to at least one.

ASVS anchors, verified against the live `v5.0.0` requirements JSON on 2026-09-23: `v5.0.0-4.1.3` (forwarded headers not end-user overridable, C2); `v5.0.0-12.1.1`, `v5.0.0-12.2.1`, `v5.0.0-12.2.2`, `v5.0.0-12.3.2` (TLS version/hostname/CA requirements, C3); `v5.0.0-14.2.2`, `v5.0.0-14.3.2` (cache/store sensitive-data handling, C1); `v5.0.0-16.3.4` (failure/rejection handling, C3/C5). `v5.0.0-14.2.5` is Level 3 web-cache-deception and is a named residual, not folded into C1's Level 2 property.

## Item answers, distractor rationales, and banding

### Item 1 — rule, tool, or false assurance

**Answer:** **B** is the rule. **A** and **D** are tools. **C** is a false assurance.

**Why each is categorized this way:**
- **A** ("`Cache-Control: private`") is a tool: it is an instruction to HTTP-aware shared caches not to reuse a response for a different requester, but this fixture's own `_CACHE` is application-level in-memory state that never reads or honors that header at all — and even for a real HTTP cache, `private` is advisory, honored inconsistently by intermediaries that cache anyway under their own defaults. Real, narrower than the rule.
- **D** ("clear the whole cache every 60 seconds") is a tool: it shrinks the *window* during which a mis-keyed entry can be served, but does nothing about *whether* the first mis-served response inside that window still happens — a mitigation for blast radius, not a fix for the cause.
- **C** ("HTTPS only, so leakage can't happen") is a false assurance: it answers a question about the browser-to-edge connection's confidentiality and integrity, and says nothing about what the cache's key contains once the (encrypted) request has arrived.

**Banding:** *developing* — sorts B correctly but calls A or D a false assurance rather than a real, narrower tool. *competent* — sorts all four correctly with a specific reason each. *transfer-ready* — additionally explains why A is the more dangerous of the two tools to over-trust: a reviewer who sees `Cache-Control: private` in a diff may reasonably assume the cache-key question has been answered, when the header says nothing at all about this fixture's own in-memory store.

### Item 2 — property vs. mechanism for company resolution

**Answer:** **B** states the property (C2). **A**, **C**, and **D** are mechanism or proxy claims, ranked A (closest to real evidence) > C (weaker, observational) > D (irrelevant to this specific property).

**Why each falls short, ranked:**
- **A** ("looked up in a table only the origin controls, never transmitted in plaintext") is the closest to real evidence — it correctly describes the credential-lookup half of company resolution — but says nothing about whether a *second* channel (a header) is also consulted and allowed to override that lookup. A system can satisfy A completely and still read `X-Company` afterward.
- **C** ("logs have never shown a disagreement") is weaker: absence of an observed disagreement is not evidence that the code path allowing one does not exist, only that no request yet has both held a real key and sent a disagreeing header.
- **D** ("served over TLS 1.3") addresses transport confidentiality and is unrelated to which of two possible sources (credential vs. header) an authorization decision reads from.

**Banding:** *developing* — picks B but cannot explain why A is closer than C or D. *competent* — picks B and correctly explains why A (a true fact about the credential lookup) does not by itself rule out a header also being consulted. *transfer-ready* — additionally names the general shape of the trap: A describes one function behaving correctly in isolation, while the property is about which functions' *outputs* are allowed to reach the decision at all — a correct credential lookup and an unguarded header read can coexist in the same code path.

### Item 3 — a different hop check's gap

**Answer:** Root cause: the function checks only `cert_trusted_ca is None` — failing closed on an *unknown* trust state — rather than `is not True`, which would fail closed on *anything other than an affirmatively verified* `True`. An explicit `cert_trusted_ca=False` (a CA-chain check that completed and failed) is not `None`, so it falls through to the hostname and version checks exactly as `True` would. Precondition: any hop whose chain-of-trust check completes and returns a definite negative — not merely one that could not complete — while the hostname and TLS version happen to be otherwise correct. Impact: `hop_is_trustworthy` returns `True` for `expected_hostname="notes-origin.securecollab.internal"`, `presented_hostname="notes-origin.securecollab.internal"`, `cert_trusted_ca=False`, `tls_version="1.3"` — a hop presenting a certificate that explicitly failed CA validation is treated as trustworthy, solely because its hostname and version happened to be right.

**Banding:** *developing* — identifies that the function is wrong without tracing this exact input through it. *competent* — correctly traces the computation, states the returned value (`True`), and names the `None`-vs-`False` distinction as the cause. *transfer-ready* — additionally names why this gap is easy to miss on a skim: the function *does* fail closed on the malformed/unknown case, so a reviewer who confirms "it handles unknown trust states" may stop there without asking whether it also handles a trust state that was actually determined and failed.

### Item 4 — a cache key that still trusts the header

**Answer:** The fix does **not** close the leak. Tracing both requests through this exact function: company B's legitimate read of `n2` (own key, no header) resolves `company="companyB"`, and `cache_key = (n2, x_company or company) = (n2, None or "companyB") = (n2, "companyB")` — it caches under that key. The attacker's request holds `key-A` and sends `X-Company: companyB`; `_resolve_company(key-A, None)` (hardened) correctly returns `"companyA"` for the *authorization* decision, but `cache_key = (n2, x_company or company) = (n2, "companyB" or "companyA") = (n2, "companyB")`, because `x_company` is truthy and the `or` short-circuits before `company` is ever consulted. That is exactly the key company B's legitimate read wrote. The lookup on `(n2, "companyB")` hits, and the attacker receives company B's cached note body — the authorization check was fixed, but the cache *key's own composition* still trusts the client-supplied header as a tie-break, reintroducing C2's exact defect one layer downstream of where the "fix" looked.

**Banding:** *developing* — says the fix works because `_resolve_company` no longer reads the header, without tracing the cache-key line. *competent* — correctly traces `cache_key`'s composition and identifies the `x_company or company` fallback as the reintroduced defect. *transfer-ready* — additionally states the general lesson: fixing the function a bug report names does not verify every other function that happens to read the same untrusted input, and a cache key is exactly the kind of second consumer a reviewer skimming only the diff's "fixed" function will not check.

### Item 5 — reading a one-hop-covers-all description

**Answer:** The description conflates "TLS 1.3 is used somewhere on this path" with "this specific hop's peer was verified" — exactly claim C4: a TLS handshake authenticates one hop, and does not chain to authenticate a later, structurally distinct connection. The browser-to-edge handshake proves only that the browser reached that edge; it says nothing about the origin's own outbound connection to a downstream audit service, which the origin itself initiates and which needs its own hop-authentication check — an independent `hop_is_trustworthy`-style verification comparing the audit service's presented certificate against the hostname the origin actually meant to reach, run at the moment that specific connection is made. This description violates **C4**.

**Banding:** *developing* — states the description is wrong without naming which claim it violates or what the correct model needs to add. *competent* — names C4 and states that the new hop needs its own hostname/CA/version check. *transfer-ready* — additionally explains why the mistake is easy to make in good faith: `hop_is_trustworthy` genuinely was already built and verified for one hop, and reusing that fact to cover a second, different hop is a natural but incorrect generalization of "we already did the TLS work."

### Item 6 — a new CDN under a constraint

**Answer:** **C1 is reverted; C2 is not**, at least not by this change alone. A CDN sitting in front of the edge, keying purely on method + path + query string, will serve company A's cached `/notes/n1` body to company B's later request for the identical path before that request ever reaches the origin's own, correctly `(note_id, company)`-keyed `_CACHE` — the origin-side fix is never even consulted for a request the CDN itself answers. C2 (header trust) is untouched by a caching-only misconfiguration: nothing about the CDN's cache-key defaults changes whether `_resolve_company` reads `X-Company`, which is still the origin's own, unchanged, fixed code. One CDN-level fix: configure the CDN's own cache key to include a company-identifying dimension the CDN itself can see before the request reaches the origin — for example, varying on the caller's API-key-bearing `Authorization` header — or, more robustly given that the CDN cannot see the *resolved* company at all (that computation happens only inside the origin, after the CDN has already decided whether to serve from its own cache), disabling CDN-layer caching for this route entirely and letting the origin's own cache, which does carry the company dimension, remain the only cache in the path. Detection: the harder point a strong answer must reach is that the origin cannot itself observe every CDN-layer cache hit to compare a served company against a bound one, because a CDN hit never reaches the origin's code at all — `cdn_hit_company_mismatch` as designed in `lessons/06-operate.md` presumes the origin sees the request. A workable design instruments the CDN's own edge-side logs for a served-company signal the origin previously attached at write time (a cache-tagging or surrogate-key mechanism naming the company), rather than assuming the origin's existing signal generalizes for free.

**Banding:** *developing* — proposes only "add `cdn_hit_company_mismatch`" without noticing the origin never sees a CDN-layer hit at all. *competent* — correctly identifies C1 as reverted and C2 as untouched, and proposes a CDN-key or disable-caching fix. *transfer-ready* — additionally names the observability gap (the origin cannot detect a leak in traffic it is never asked to serve) and proposes an edge-side or write-time mitigant rather than restating the origin-only signal unchanged.

### Item 7 — clinic `/patients/me` and `Vary: Cookie`

**Answer:** The proposal satisfies **none** of C1–C5 as a structural fix. `Vary: Cookie` instructs a cache to select *among representations it already has* by matching a request header's raw value — it is a selection rule over whatever the cache already stored, not an identity check. It does not resolve, verify, or bind anything to a session the way C1's `(path, patient)` key, derived from the origin's own session lookup, does. Two capabilities it leaves open even if honored perfectly: a patient who authenticates by bearer token rather than a cookie gets no benefit from this header at all, since there is no cookie value to vary on; and an intermediary that rewrites, shares, or fails to forward a cookie value unchanged across two patients' requests can still cause the cache to treat two different patients' requests as the same "variant," exactly reproducing C1's forbidden outcome under a different mechanism.

**Banding:** *developing* — accepts `Vary: Cookie` as a sufficient fix, or names it as "related to caching" without identifying what it actually does. *competent* — correctly states that `Vary: Cookie` selects among existing representations rather than verifying identity, and names at least one capability it leaves open. *transfer-ready* — additionally connects this back to `01-property.md`'s own rejected alternatives (a header-based or protocol-level claim standing in for the origin's own resolved identity) as the same recurring shape, not a new mistake specific to `Vary`.

### Item 8 — two signals, one boolean

**Answer:** `cdn_hit_company_mismatch path=/notes/n1 bound=companyB served=companyA request_id=req_...` for the cache mismatch, and `hop_rejected reason=hostname_mismatch|version|untrusted expected=<hostname> presented=<hostname> request_id=req_...` for the rejected relay. The `reason` field is what distinguishes the three cases inside a `hop_rejected` line. Collapsing them into one undifferentiated event would be worse because the three causes call for different, often urgent-versus-routine, responses: `version` may be an expected consequence of a planned TLS deprecation; `hostname_mismatch` is far more likely to indicate active misrouting to the wrong backend; `untrusted` may indicate a certificate that expired mid-rotation. `lessons/06-operate.md` names exactly this distinction between a purge drill and a certificate-failure drill as two different investigations with two different urgencies — an operator who only sees "hop rejected, count: 40" cannot even begin that triage.

**Banding:** *developing* — writes one undifferentiated signal, or a `hop_rejected` line with no `reason` field. *competent* — writes both signals correctly, with `reason` distinguishing the three `hop_rejected` causes, and neither line carrying a note body or key material. *transfer-ready* — additionally explains the operational cost of collapsing the distinction in the terms `06-operate.md` uses: a reviewer cannot tell "expected consequence of a planned change" from "active incident" without it.
