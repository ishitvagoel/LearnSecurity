## Item 1 — Mechanism, rule, or neither?

**Expected answer.** A ("we use Argon2id for password storage") is a mechanism: it names a tool, not an outcome, and it could support a narrow rule such as "a database snapshot alone should not reveal a reusable plaintext password" but says nothing about note authorization. B is the only bounded rule: it names asset (note), subject/action (Tenant A member reads), forbidden outcome (a Tenant B member reads it), and channel (API, log, export). C ("the application is secure") is a universal claim with none of the envelope elements and cannot be falsified by any concrete event. D is a mechanism dressed as a rule via "so ... is solved"; it commits the same error [01-property-vs-mechanism.md](../../modules/1/1.1/lessons/01-property-vs-mechanism.md) opens with, treating authentication as if it implied authorization.

**Distractor rationales.** A learner who labels A a "rule" is treating tool adoption as outcome proof — the misconception the lesson calls the single most common way a claim becomes unfalsifiable. A learner who accepts D outright is conflating authentication with authorization, one of `module.yaml`'s named misconceptions. A learner who calls C "a rule, just a strong one" has not yet internalized that universality is not the same as boundedness.

**Banding.** *Developing:* labels all four correctly by gut feel but cannot state which envelope element each mechanism-labeled statement is missing. *Competent:* correctly separates B from A/C/D and names at least the missing attacker, trust, or forbidden-outcome element for each. *Transfer-ready:* additionally proposes the one bounded rule A or D could plausibly support, matching the reasoning chain in [01-property-vs-mechanism.md](../../modules/1/1.1/lessons/01-property-vs-mechanism.md)'s worked example.

## Item 2 — Five rows, one claim

**Expected answer.** No. Field presence, non-empty lists, distinct ids, and absence of slogan phrases together do not establish that five rows are five *distinct* claims about SecureCollab specifically. The additional property is content-specificity/distinctness: each row's `property` and `forbiddenOutcomes` text must name something that would not validate equally well against an unrelated product. A concrete failure: five rows each reading "notes must never leak to an outsider" / "notes leak somehow," with generic filler in every other field ("a bad actor," "the server," "thing works"), passes every field-presence and slogan-phrase check while saying nothing SecureCollab-specific five times over — this is the exact defect found and fixed in `catalogue_validator.py`'s duplicate-signature check while deepening this module (see `content/modules/1/1.1/spec.md`'s changelog).

**Distractor rationales.** "Yes, because every field is filled in" is the field-presence-equals-boundedness error the module exists to correct, one level up from the mechanism-slogan version — the learner has generalized "avoid banned phrases" into "avoid banned phrases and you're done," missing that genericness itself, not any specific phrase, is the failure mode.

**Banding.** *Developing:* says "no" but cannot construct a concrete counterexample catalogue. *Competent:* constructs (or accurately describes) a padded-duplicate catalogue and names the signature-style check needed to catch it. *Transfer-ready:* additionally identifies that a paraphrased duplicate (different wording, same substance) would still slip past a naive text-equality check, and proposes what an automated check can and cannot verify about genuine semantic distinctness.

## Item 3 — Which evidence mode is missing?

**Expected answer.** `failure` is absent. A concrete event it would have to rule out: a policy-lookup dependency times out or the event-schema constructor errors, and the read is granted anyway because the failure path defaults to allow rather than deny. The `abuse` entry is a copy of the `negative` entry, not abuse-specific evidence — it does not show the claim surviving an attacker who deliberately varies identity, ordering, or volume (e.g., guessed identifiers, client-supplied tenant labels), which is what the abuse mode is for; a value being present and non-empty does not make it evidence for the mode its key names.

**Distractor rationales.** A learner who says "abuse is fine, it's non-empty" is repeating the field-presence error from Item 2 at the level of one field's *content* rather than the whole row — the check that catches this in `catalogue_validator.py` is a phrase-based control-presence filter, not a content-duplication filter, so this specific case (identical text under two different mode keys) is a case the validator does not catch mechanically and a human reviewer must.

**Banding.** *Developing:* names `failure` as missing but cannot describe a concrete event it should rule out. *Competent:* both identifies the missing mode with a concrete event and explains why the duplicated `abuse` entry is not real abuse evidence. *Transfer-ready:* proposes a genuine abuse-mode entry for this row and explains why it differs mechanistically from the negative-mode entry (different attacker action, not just different wording).

## Item 4 — Root cause, precondition, or impact?

**Expected answer.** Root cause: the document collapses several unrelated assets (notes, exports, backups, logs, recovery) into one mechanism-only sentence, treating a bounded tool's presence as proof of an unrelated outcome. Precondition: a reader has to accept a mechanism's name as sufficient evidence without asking which forbidden outcome it addresses. Impact: design and review work on note confidentiality, session security, and account recovery can each be marked "covered" while none of the three has a stated forbidden outcome, evidence mode, or mechanism limit — leaving all three genuinely unverified.

**Distractor rationales.** A learner who writes "the root cause is that TLS doesn't hash passwords" has confused two mechanisms with each other rather than identifying the causal error (treating any mechanism as proof of an unrelated outcome). A learner who states the impact as "the app gets hacked" has skipped past the actual mechanism of failure (unverified assumptions accumulate silently) to a generic consequence that could follow from nearly any security defect.

**Banding.** *Developing:* restates the excerpt in different words for one or more of the three categories. *Competent:* three distinct sentences, each adding information not in the excerpt, correctly separated by category. *Transfer-ready:* additionally names which specific SecureCollab claim (from `fixed/security_claim.yaml`) each of the three collapsed assets should have received instead.

## Item 5 — What does the log line actually prove?

**Expected answer.** This fails the `prohibitedFields` requirement in `catalogue_validator.py`'s `detection` check, which requires "note body," "password," and "token" to be explicitly excluded from what an event may contain. The security consequence: the detection design intended to help defend the confidentiality claim has instead become a second, likely less-access-controlled copy of the exact asset (note bodies) the confidentiality claim exists to protect — an incident responder now has to search the evidence store for the same sensitive content the original claim was trying to keep bounded, and a compromise of the log pipeline becomes equivalent to a compromise of note confidentiality itself.

**Distractor rationales.** "It violates the schema" is true but not an answer to the security-consequence half of the question; a learner who stops there has correctly located the mechanical failure without connecting it back to the property, which is exactly the property-vs-mechanism distinction this module is about, applied to operational tooling instead of prose.

**Banding.** *Developing:* names the schema violation only. *Competent:* names the violation and states the consequence in terms of the confidentiality claim specifically. *Transfer-ready:* proposes a corrected detection design using only the seven `eventFields` from the accountability row's worked example (actor, tenant, action, target, decision, authority version, correlation id) and explains why that set is sufficient for the stated signal.

## Item 6 — Prose or schema?

**Expected answer.** The structured schema wins under the stated constraint (independent review by someone who did not write it), because free-form prose gives every future author discretion over which fields to include, so the envelope silently degrades over time even without any single author intending it to; a schema with a validator enforces the same fifteen-plus fields regardless of who writes the next row. What the schema still cannot verify: whether SecureCollab's actual implementation (once one exists) behaves the way any given row claims, or whether the row's content is *true* rather than merely well-formed, specific-sounding, and free of banned phrases.

**Distractor rationales.** A learner who defends prose as "more thorough" is repeating the reasoning [04-smallest-mechanism.md](../../modules/1/1.1/lessons/04-smallest-mechanism.md) explicitly walks through and rejects — more words without a required place for each envelope element is not more rigor, and this is worth surfacing directly if a learner reaches for it, since it is the single most tempting wrong answer to this item.

**Banding.** *Developing:* picks the schema but cannot say what it still fails to verify. *Competent:* picks the schema, defends it against prose specifically under the reviewability constraint, and names one real verification limit. *Transfer-ready:* additionally describes a concrete fake (such as the five-padded-row catalogue from Item 2) that a shape-only version of the schema would miss, and what an additional check would need to look for.

## Item 7 — CivicClinic: guardian access after revocation

**Expected answer.** SecureCollab's membership-integrity claim treats current authority as effectively stable within a session and checks it against a transactional store at the moment of the mutating action; an analogous SecureCollab scenario (a tenant-admin demotion mid-session) would predict the demoted member's next authorized *mutation* is denied once the transaction re-checks authority. This does not transfer unchanged because CivicClinic's guardian delegation is explicitly designed to be revoked urgently (custody changes, protective orders), and a *read*-only request is exactly the case SecureCollab's row does not centrally emphasize (transactional re-check on mutation) — the CivicClinic rule has to be stronger: delegation validity must be re-checked at the moment of *every* access, including reads, not only at session start or only on writes, because "the guardian's session is still open" must never be treated as evidence that the guardian's authority still holds.

**Distractor rationales.** A learner who answers "the request should be allowed because the session started before 2:14 p.m." has applied a check-once-per-session model, which is exactly the assumption this transfer is built to break; a learner who says "SecureCollab already handles this the same way" has not identified that SecureCollab's own row is scoped to mutations and a sequential model, not to the read-at-any-time case revocation urgency in CivicClinic requires.

**Banding.** *Developing:* states the request should be denied but cannot explain why the SecureCollab analogy does not directly cover it. *Competent:* correctly traces the difference between mutation re-check and access-time re-check, and states the CivicClinic rule bound to specific fields (delegation status, checked per-access, not per-session). *Transfer-ready:* additionally proposes evidence for the CivicClinic rule (normal/negative/abuse/failure) and names the accessibility consideration for how the guardian is notified of the revocation.

## Item 8 — Signal, threshold, and the false-positive it creates

**Expected answer.** A reasonable signal is per-tenant queue depth, rejection rate, or worker saturation diverging from ordinary-read latency; a reasonable threshold is a sustained divergence over a stated window rather than any single spike. A legitimate event the threshold would still flag: a large tenant running an authorized, infrequent full-history export at month's end, which genuinely consumes a large share of read capacity without being abusive. The on-call reviewer's correct response is to confirm the workload is attributable to one known, authorized tenant action (not distributed or disguised) and, if so, treat it as a capacity-planning input rather than an incident — never to raise the threshold globally or silence the channel, since either response would also hide the actual abuse case the signal exists to catch.

**Distractor rationales.** A learner who proposes "just raise the threshold" has solved the immediate false-positive at the cost of widening the window in which real abuse goes undetected — this is the alert-fatigue failure mode the operate lesson names directly, and it is worth confirming a learner can articulate the cost rather than only avoid the word "raise the threshold" reflexively.

**Banding.** *Developing:* designs a detection block but does not identify a concrete false-positive case. *Competent:* full detection block, a concrete legitimate event that trips the threshold, and a reviewer response that does not silence or blanket-loosen the alert. *Transfer-ready:* additionally distinguishes this tenant's legitimate spike from the abuse case in the same evidence terms [05-forbidden-outcomes.md](../../modules/1/1.1/lessons/05-forbidden-outcomes.md) uses, and states what evidence would upgrade the false positive to a confirmed incident.

A review that spends its comment budget here and calls the document improved has mistaken a cosmetic pass for a real one — this is deliberately seeded to test whether a learner can distinguish a real finding from a plausible-looking one, per `lab-realism.mdc`'s guidance that at least one plausible non-issue belongs in a seeded review.

## Common blockers

- fewer than five meaningful catalogue rows;
- five rows that are field-complete but content-identical or near-identical (the Item 2 / padded-duplicate failure);
- generic attacker or "the server is trusted" language with no named component;
- mechanisms embedded as properties;
- only happy-path (normal-mode) evidence, or an evidence mode present but not actually observing that mode's forbidden case;
- validator pass presented as application assurance;
- no mechanism limits or residual risk;
- unsafe target or data scope (a live URL, `syntheticDataOnly: false`);
- a CivicClinic transfer case that changes only nouns and not authority, trust, or time-horizon assumptions;
- generated reviewer metadata offered as independent review;
- a detection design that logs a prohibited field "to be thorough."
